# 教訓の記録

ユーザーからの修正や指摘を自動メモリや CLAUDE.md に残して、同じ指摘を繰り返させない
ための skill。自動メモリや CLAUDE.md の仕組みを持たない環境ではこの skill は適用しない。

普段の細かい訂正（「これは feedback メモリに」程度のもの）は、この skill を介さず
その場で自動メモリに記録してよい。この skill が対象にするのは、タスク終盤にまとめて
「今回の教訓をどこに落とすか」を判断する、もう一段重い振り返り作業であり、そのため
毎タスク完了時には自動起動しない。

## いつ使うか

- タスク完了の直前、またはユーザーが「教訓を残して」「skill 化して」と言ったとき
- 試行錯誤の末に解決した（最初の仮説が外れた、ドキュメント不足で時間を食った等）とき
- 今後同種のタスクを再びやりそうなとき

使わないとき:
- 一発で終わった単純なタスク（抽出すべきものが無い）
- プロジェクト固有の一回限りの対応（コミットメッセージで十分）

## この skill が上書きする既定

多くの環境では、ローカルのファイル編集やコミットは自由に行ってよいとされている。
自動メモリへの新規追加や、CLAUDE.md（相当の常設インストラクションファイル）本文への
追記は技術的にはローカル編集の一種だが、この skill はそれを自由に行わせず、必ず
提案 → 確認 → 書き込み の順を踏む。ホスト環境がローカル編集を自由とする方針でも、
逆にできる限り自律的に進めることを推奨する方針でも、この skill が扱う書き込みだけは
対象外とし、確認を必須にする。理由: 教訓の確定は後から取り消しにくく、誤って
一般化すると以後の全セッションの挙動に影響するため、通常のローカル編集より厳しい
確認要件をこの skill 自身が課している。すでにローカル編集全般に確認が要る方針の
環境では、この要件は既存の方針と自然に一致し、上書きにはならない。

教訓の言語化や分類までは検討や提案の段階であり、まだ書き込みの実行ではない。
書き込みには別途ユーザーの明示的な確認が要る。

## Workflow

1. **失敗と成功を対にする**: 今回のタスクから次の 3 点を書き出す。
   - 最初の試み（何をしてどう失敗したか）
   - 最終的な解決策（何が効いたか）
   - 橋渡しになった気づき（最初の試みが届かなかった理由）
2. **「最初に知っていればよかったこと」を言語化する**: 1〜3 文で、振り返りではなく
   未来の自分への指示として書く（命令形: 「〜しない」「まず〜を確認する」）。
3. **分類する**: 下記の分類表に従って書き込み先を決める。
4. **重複チェック（必須）**: 提案の前に既存の記録と突き合わせる。重複または近い
   記録があれば「新規追加」ではなく「既存への追記や更新」を選ぶ。このステップを
   飛ばすと記録が肥大化する。

   気づきから検索キーを 2〜3 個抽出する（ツール名、API 名、症状の語、対義語）。

   ```
   # 自動メモリの重複確認
   MEMORY.md を読み、関連する既存メモリファイルを開く

   # CLAUDE.md の重複確認（Claude Code 以外では相当する常設ファイルに読み替える）
   Grep "<key>" <グローバルの CLAUDE.md 相当ファイル>
   Grep "<key>" <対象リポジトリの CLAUDE.md 相当ファイル>   # 対応するプロジェクトがあれば

   # skill の重複確認（skill の仕組みを持たない環境ではこの手順は省略）
   ls <skill を保存しているディレクトリ>
   Grep "<key>" 各 skill ファイル
   ```

   結果を 4 段階に分類する:
   - **新規**: ヒット無し → 通常の提案
   - **既存へ追記**: 関連する記録があり、新しい情報が補完的 → 「既存へ追記」を提案
     - 「部分的な重複」（気づきの一部が既存でカバーされ、残りが新規）もこの段階に含める。
       重複部分は「重複検出」、新規部分は「採用候補」に分けて書く。
   - **既存と重複（提案不要）**: 既存の記録が同じ気づきを完全にカバーしている →
     提案はゼロだが、監査のため「重複検出」の行だけは残す。該当する記録の名前と
     セクション（または行番号）を根拠として添える。
   - **判断不能**: 重複かどうか自分では判断できない → 突合結果をユーザーに見せて
     判断を仰ぐ
5. **書き出す**: 選んだ形式のテンプレートに従って成果物を作る（下記）。
6. **確認**: 差分をユーザーに見せて承認を得る。却下された場合は skill 化や
   ルール化をせず、セッションのメモに留める。

## 分類

このユーザーの自動メモリは 4 分類（user / feedback / project / reference）を持つ。
書き込み先の候補には、ソースコードに対して機械的なルールを生成する仕組み（lint 設定や
static analysis のカスタムルールなど）も考えられるが、この環境にはそれに対応する
仕組みが無いため使わない。CLAUDE.md（相当の常設ルール）と新規 skill の 2 分岐は
残しつつ、どちらにも当てはまらない「ユーザー個人の情報」「進行中の作業の背景」
「外部参照先」を拾う分岐として、自動メモリの 4 分類を独自に追加している。下表は
それぞれの分類が何を拾うかを一意に対応づけたものであり、単純な言い換えではない。

| 判断軸 | 書き込み先 | 例 |
|---|---|---|
| ユーザーの役割や好み、責任範囲についての情報 | 自動メモリ `user` | 「ユーザーはデータサイエンティストで observability 領域を見ている」 |
| ユーザーからの修正や指摘、または非自明なやり方の確認 | 自動メモリ `feedback` | 「◯◯ ではモックを使わず実データベースでテストする（理由: 過去に mock と本番の乖離で事故があった）」 |
| 進行中の作業の背景、意思決定、締切 | 自動メモリ `project` | 「認証ミドルウェアの書き直しはコンプライアンス要件が理由で、技術的負債の解消が目的ではない」 |
| 外部システムの参照先 | 自動メモリ `reference` | 「pipeline のバグは Linear の INGEST プロジェクトで追跡している」 |
| 短く、常に当てはまり、判断を要しない | `CLAUDE.md`（ユーザーのグローバル、またはプロジェクト） | 「pnpm は v10 以上を使う（理由: lockfile 形式が非互換で CI 差分が出るため）」 |
| 手順、文脈依存の判断、テンプレートを要する | 新規 skill、または既存 skill への追記 | 「C バインディングを書く手順」 |
| プロジェクト固有で一回限り | 採用しない（コミットメッセージ/PR 説明で十分） | - |

**CLAUDE.md への追記先**: 言語やツール横断の一般ルールはユーザーのグローバル
`CLAUDE.md`（相当の常設インストラクションファイル）へ、特定リポジトリに限る話は
そのリポジトリの `CLAUDE.md` へ。Claude Code 以外の環境では、それぞれの環境が持つ
同等のファイル（例: Codex の `AGENTS.md`）に読み替える。

**自動メモリへの追記先**: 「書くべきでないもの」（コードパターン、git 履歴、
デバッグの解法、CLAUDE.md に既にある内容、エフェメラルな作業状態）は自動メモリの
運用ルールに従い、そもそも書かない。

## 出力テンプレート

### 自動メモリ

この skill を使う環境が持つ自動メモリの保存形式に従う。このユーザーの環境では、
1 メモリ 1 ファイルとして次の frontmatter で保存する。

```markdown
---
name: <短い kebab-case のスラッグ>
description: <このメモリが何についてのものか、1 行>
metadata:
  type: {{user, feedback, project, reference}}
---

{{本文。feedback / project タイプは「ルールや事実」→ `**Why:**`
（なぜそうするか、理由や過去の経緯）→ `**How to apply:**`
（いつ、どこでこの判断を適用するか）の順で書く。}}
```

自動メモリの仕組みを持たない環境では、この形式にこだわらず、その環境が用意する
メモリやノート機構の形式に読み替える。

### CLAUDE.md への追記

```markdown
# <既存セクションへの追記>
- <命令形の一文>（理由: <短い根拠>）
```

理由は必ず括弧で添える（未来の自分が例外を判断できるように）。

### 新規 skill

```markdown
---
name: <kebab-case>
description: Use when <具体的な状況や症状>
---

# <タイトル>

## Purpose
## When to use
## Workflow
## Pitfalls
```

## Red Flags（正当化の兆候）

| 出てきがちな正当化 | 実際 |
|---|---|
| 「プロジェクト固有だけど念のため skill にしておこう」 | skill が肥大化し検索性が落ちる。コミットメッセージ/PR で十分 |
| 「確認を飛ばして先に書いておいて、後で見せればいい」 | CLAUDE.md/skill/自動メモリの無断更新は以後の挙動を予測不能にする。必ず 提案 → 承認 → 書き出し |
| 「気づきは薄いが、何か書かないと格好がつかない」 | 提案ゼロも正しい結論。空の振り返りは害にならない |
| 「重複チェックは面倒だから後で消せばいい」 | 重複した記録が残ると挙動が割れる。重複チェックは必須ステップ |
| 「最終的な解決策だけ書けばいい」 | 失敗側を書かないと、未来の自分が同じ落とし穴に落ちる |

## ユーザーへの提示フォーマット

```
## Retrospective

### Lesson 1: <短いラベル>
- 最初の失敗: <1 行>
- 最終的な解決策: <1 行>
- 気づき: <1 行>

### Lesson 2: <短いラベル>      # 教訓が 1 個だけならこのブロックごと省略
...

## Proposals

採用候補:
- [memory:<type>] <1 行>（from lesson N）
- [CLAUDE.md] <対象>: <1 行>（from lesson N）
- [skill 追記] <既存 skill 名>: <1 行>（from lesson N）
- [skill 新規] <skill 名>: <1 行>（from lesson N）

重複検出（提案不要）:
- lesson N: 既存の <記録名またはセクション名> で完全にカバー済み → 追加不要

不採用:
- lesson N: <不採用の理由を 1 行>（例: プロジェクト固有 / 対象が存在しない）

どれを採用するか、番号または項目名で指示してください。採用候補ゼロも有効な結論です。
```

**書式のルール**:
- 教訓が 1 個だけなら `### Lesson N` の見出しを省略し、1 個の Retrospective ブロックだけ書く
- 「採用候補」「重複検出」「不採用」のいずれかが空なら、そのセクションごと省略する（「無し」とは書かない）
- 各提案行の末尾には必ず「from lesson N」を付ける（複数の教訓にまたがる場合は「from lessons 1, 3」のように列挙してよい）
- 採用候補が空で重複検出だけが残る場合、締めの文を「採用候補はありません。記録としてご確認ください。」に置き換える
- ユーザーが採用を指示した項目だけを書き出す。無断で書き出さない

## よくある失敗

- **粒度が細かすぎる**: 一回限りの固有名詞（特定の関数名や特定のバージョン）をそのまま
  codify する → 「何を確認すべきか」のレベルまで抽象化する
- **プロンプト的に書いてしまう**: 本来は仕組み側で防ぐべきものを、CLAUDE.md や skill の
  自然言語ルールとして書いてしまう → 可能ならこのユーザーの環境にある機械的な仕組み
  （lint、型、CI）に寄せられないか先に検討する
- **理由を書かない**: ルールの根拠を残さず、未来の自分が例外を判断できない → 必ず
  `Why:` を添える
- **無断で書き出す**: ユーザーの承認なしに CLAUDE.md や skill、自動メモリを更新する →
  必ず 提案 → 承認 → 書き出し の順を守る
- **失敗側を省く**: 「最終的な解決策は X」とだけ書き、最初の試みがなぜ届かなかったかを
  残さない → 失敗側の記述が無いと、未来の自分が同じ落とし穴に落ちる
