# CLAUDE.md

ユーザーと対話できるメインセッションを前提とする。
サブエージェントでは、ユーザーとの対話を前提とする指示（セッション名を付ける、ユーザーに確認する・伝える）を適用しない。確認が必要な操作は行わず、報告に含める。
サブエージェントや非対話実行では、必要なツールが使えない指示を適用しない。
サブエージェントは、さらにサブエージェントを起動しない。委譲や独立レビューが必要なら報告に含め、判断をメインに任せる。
適用しなかったことが成果に影響する場合は、完了報告に明記する。

## コア原則

- 一時しのぎで済ませず根本原因を直す。
- 変更は依頼範囲内にとどめ、過剰設計を避ける。範囲外の「ついで修正」や指示のないリファクタリングを混ぜず、必要なら着手前に確認する。
- コメントはコードから自明でないことだけを書く。判断基準は書いた本人ではなく次に読む人とする（既定はコメントなし。周囲のコードのコメント量には合わせない）。
  - 書く内容: 判断の理由（他の案を採らなかった理由を含む）、コードに現れない制約や単位、実装を読まずに使うための情報、消すとバグが再発する箇所。
  - 書かない内容: 直後のコードの逐語訳、手順（How）、予告（「ここでは〜する」）、空虚な形容（「重要」「適切」など）。逐語訳しか書けないならコメントせずコードを改善する（インターフェースの JSDoc など what が必要な箇所は除く）。
  - 理由はコメント本文で完結させる。issue 番号は理由の代用とせず、再現手順や議論の出典としてのみ添える。
  - 変更履歴は VCS（git）に任せ、現在も有効な制約だけをコードに残す（重複するとコード側の更新が遅れて陳腐化する）。
  - コードより一段抽象度を上げて書く（細部をなぞるコメントほど実装変更時に嘘になりやすい）。
- 特に指示がない限り、ユーザーへの応答は日本語で行う。
- 日本語の地の文に英数字を混ぜる際は前後に半角スペースを入れる。
- 日本語の PR・コミット・コメントは、変更と理由を具体的な動詞で直結して書く。
  - 英語直訳調（「〜すること」「〜のための」「〜において」「〜できるようにする」）を避け、長文は文を分ける。
  - 比喩や誇張した評価語（「最適」「劇的」など）を避け、客観的な事実と動作を書く。

## ワークフロー

- セッション開始時の最初の応答で、`session-title` skill に従ってセッション名を付ける。
- Plan モードの要否は、不確実性・設計判断の有無・影響範囲・可逆性で判断する。
  - 既定: 複数ファイルに及ぶ実装やアーキテクチャ変更では Plan モードに入る。
  - 単一ファイルでも、マイグレーション・並行処理・アーキテクチャ変更なら Plan モードに入る。
  - 一括リネーム、既存パターンの定型変更、単一目的の調査・回答は、多数ファイルでもスキップ可。
  - Plan モード中も調査・設計用サブエージェントは起動してよい。
- 同じ手段で 2 回失敗したら続けず、原因と代替案を整理して報告し、指示を待つ。
- 動作を証明するまで完了と報告しない。
  - コード変更: 変更箇所を通るテストがあれば実行結果、なければ動作ログか差分を確認する。
  - 調査・監査: 結論の根拠をファイルと行で示す（指示がない限り不要なテストやログ実行はしない）。
  - 未知の技術: 公式ドキュメントや型定義を直接確認した上で回答する。
- バグ報告は聞き返さず、ログ・エラー表示・失敗テストを見て自律修正する。
  - 原因を絞り込めない場合は推測で直さず、調査結果を示して確認する。
  - ユーザーが修正を禁じている場合は調査報告のみ返す。

## サブエージェント戦略

- 委譲には起動・説明・結果受け取りのコストが伴う。品質・速度・コンテキスト消費を総合し、自力で進めるか委譲するかを判断する。
  - 自力で行う: 小さく明確なタスク、repo 内の短い調査（シンボルの参照箇所、型定義など）。
  - 委譲する: 並列化できる作業、大量の読み込み、独立した視点の確保、メインのコンテキスト保護のいずれかに該当する場合。事前に読む量が不明なら件数や行数を数え、5 ファイルまたは合計 1,000 行を超えるなら委譲する。
  - fan-out（並列調査）: ディレクトリや年月など自然な単位で分割し、1 本が 1 回で完遂できる粒度にする。
  - 並列でファイルを編集させる場合は、担当ファイルを重複させない。重複を避けられなければ、作業ツリーを分けるか直列にする。
- サブエージェントを起動する前に、`model-routing` skill で役割を選び、skill が示す方法で役割を指定して起動する。役割の指定は省略しない。依頼文と報告の受け取りも同じ skill に従う。
- トークン削減のためにレビューを省略しない。削るべきは手戻り（再実装・再レビュー）の回数と、1 本あたりのコンテキスト消費量である。
- 別セッション（worktree + branch）を立てるのは以下に該当する場合に限る（それ以外はサブエージェントで処理する。セッションは起動・報告往復のコストがかさむため、同等作業ならサブエージェントの方が安価）。
  - 複数パッケージにまたがる、または数時間規模に及ぶ作業
  - 開発サーバーや E2E テストの長時間稼働
  - 作業途中にユーザーが介入・確認する可能性がある場合
  - 会話を保存し、後から再開・追加依頼したい場合
- 実装時のコンテキストを引き継ぐ自己レビューは常に行う。その上で、独立レビューの要否と強度は `risk-based-review` skill に従って 4 段階で判断する。
  - 領域ごとのリスク分類は、プロジェクトの `CLAUDE.md` の定義を優先する。
- bias-free 評価（skill、prompt、自己成果物の検証）は新規サブエージェントに任せる。
  - 自身の再読を bias-free 評価や empirical 評価の代用としない。
  - 新規サブエージェントが起動できない環境では bias-free 評価と称さず、`empirical-prompt-tuning` skill の構造審査に切り替える。

## コンテキストとトークン

- ツール出力は必要な行だけ読む。
  - 長い出力はファイルに落とし、`rg -n` / `head` / `wc` で絞り込む。
  - テスト結果は失敗行のみ、diff は `--stat` を先に確認する。
  - ファイル全体を読むのは、そのファイル自体が判断や編集の対象のときに限る。広い探索や要約はサブエージェントに任せる。
- 定期チェック（cron / loop）は「変化の有無を 1 〜 2 回の呼び出しで判定する手順」を先頭に置き、変化がなければ即座に終了する。
  - 出力全体を読み込む手順を cron プロンプトに含めない。
  - 実行間隔は 30 分以上とし、稼働中のセッションがなければ停止する。
- セッション間メッセージは結論と次のアクションのみとする。
  - ログ・diff・ファイル本文は添付せず、参照先（ブランチ名、ファイルと行など）を記載する。
- 完了報告は 1 タスクにつき 1 回とし、結論・検証結果・未確認事項・必要な次のアクションに絞る。

## 外部への書き込み

外部サービスへの変更系操作（GitHub への push / issue 作成 / PR 作成 / コメント投稿、クラウドリソースの変更、外部 API への POST など）は、ユーザーから明示的に指示されたか、実行前に確認して承認を得た場合だけ実行する。

- 参照系操作（読み取り、`terraform plan` など）とローカルでの編集は自由に行う。
- ローカルのコミットは確認を取らずに行う。区切りのよいところで意味のまとまりごとにコミットし、複数コミット分の変更を溜めない（push 前なら後から直せる）。
  - コミットには自分が変更したファイルだけを含める。サブエージェントは依頼文で指示されたときだけコミットする。
  - 既定ブランチへ直接コミットしてよいかは、リポジトリの履歴や規約に従う。
- 「考えて」「まとめて」「整理して」「計画して」などの表現は検討・提案の依頼であり、変更実行の指示ではない。
- Plan モードの承認は計画への合意であり、外部サービスへの書き込みの承認は含まない。

## ブランチと PR

- PR は明示指示がない限り Draft で作成する。PR の作成・更新、PR ブランチへの push、マージ後や作業破棄時の片付けは `pr-workflow` skill に従う。
- 自動命名されたブランチや worktree のまま作業を進めない。最初のコミット前に、作業内容が伝わる名前に切り直す（`git switch -c <名前>`）。
  - 命名形式はリポジトリの `CLAUDE.md` に従う。指定がなければ `git branch -r --sort=-committerdate | head` で既存の命名を確認して合わせる。
  - チップ（worktree セッション）で開始した際は自動命名されているため必ず確認する（worktree のディレクトリ名までは変更不要）。
- push / fetch 実行時は 1Password の SSH 承認が必要となる。
  - サンドボックス外で実行し、timeout は 60 秒に設定する。
  - 実行直前に「承認ダイアログが出たら承認して」とユーザーに伝える。
  - 処理が停止して見える場合は承認待ち状態である。
  - エラー時の判断: `Permission denied` はサンドボックス内での実行、`Connection refused` は 1Password 未起動（`open -a 1Password`）、`signing failed` は承認拒否またはロック中。
