# Empirical Prompt Tuning

指示を書いた本人の再読だけでは、読み手が詰まる箇所を客観的に評価できない。
対象を初めて読むサブエージェントに現実的なシナリオを実行させ、成果物と自己申告の両方から指示を改善する。

## 適用範囲

ユーザーが empirical 評価または構造審査を明示的に依頼し、次のいずれかに該当する場合に使う。

- skill、タスクプロンプト、AGENTS.md の節、自動化プロンプトを新規作成または大幅改訂した直後
- エージェントが期待どおり動かず、指示の曖昧さを原因として検証したい場合
- 頻繁に使う指示を、複数の使用場面に対して堅牢にしたい場合

一回限りのプロンプトや、成功率ではなく書き手の好みだけを調整する場合には使わない。

## 評価モード

- **Empirical 評価**：重要度が高い、変更が大きい、頻繁に使う、または実際の失敗を再現したい対象で、適用場面の境界を定義できる場合に選ぶ。
  skill の発火条件や特定ワークフローのように適用場面を切り分けられる対象に向く。
  AGENTS.md を対象にする場合は、適用場面が明確な節へ絞るか、代表するタスクの母集団を先に定義する。
  新規サブエージェントによる後述のワークフローを実行する。
- **構造審査**：重要度が低い小変更、全域に適用される文書、または短時間で記述の整合性と明瞭性だけを確認したい場合に選ぶ。
  全タスクへ適用される AGENTS.md 全体は、任意のシナリオへの遵守率テストになりやすいため、このモードを既定とする。
  サブエージェントを起動できる環境でも意図的に選んでよい。
  完了報告に「構造審査であり empirical 評価ではない」と明記し、iteration や収束回数には数えない。

ユーザーがモードを指定した場合は、その指定を優先する。
指定がなく判断が分かれる場合は、重要度、変更の大きさ、適用場面の境界を基準に選ぶ。

## Empirical 評価のワークフロー

0. **静的整合チェック**
   - frontmatter の `description` が示す起動条件と、本文が扱う範囲を比較する。
   - frontmatter がない対象では、冒頭に書かれた目的や適用範囲と本文を比較する。
   - 乖離があれば、実行評価の前に `description` または本文を修正する。
1. **ベースライン準備**
   - 現実の使用場面から中央値のシナリオを 1 件、edge case を 1 件から 2 件用意する。
   - 各シナリオに 3 項目から 7 項目の要件チェックリストを作る。
   - 未使用の hold-out シナリオ 1 件と、その要件チェックリストもこの時点で作り、収束まで実行者へ渡さない。
   - 最低ラインとなる項目を一つ以上 `[critical]` に指定する。
   - ベースライン開始後は、要件チェックリストと `[critical]` の指定を変更しない。
   - Empirical 評価を選んだ場合は、対象が小さくてもこの最小件数と後続の再評価、hold-out を省略せず、成果物の規模だけを小さくする。
2. **新規実行者の起動**
   - 対象を読んだことのない新規サブエージェントをシナリオごとに起動する。
   - 独立したシナリオは並列に実行してよい。
   - 同じサブエージェントを次の iteration に再利用しない。
3. **実行と自己申告**
   - 後述の「サブエージェント起動契約」を渡し、指示に従った成果物と自己申告を返させる。
4. **両面評価**
   - `[critical]` 項目がすべて ○ の場合だけ成功とする。
   - 精度は ○ を 1、部分的を 0.5、× を 0 として合計し、全項目数で割る。
   - 閾値との比較には丸め前の精度を使い、表示時だけ小数第一位へ丸める。
   - 不明瞭点、裁量補完、再試行を自己申告から抽出する。
   - 実行環境が返す追加メタデータは、取得できる場合だけ補助指標として記録する。
   - 取得できないメタデータを推測で埋めない。
5. **最小修正**
   - 一つの iteration では、一つの意味的なテーマだけを修正する。
   - 修正前に、要件チェックリストのどの項目へ効く修正かを明示する。
   - 「失敗パターン台帳」に同じ原因があれば、新しい項目を増やす前に既存の修正が効かなかった理由を調べる。
6. **再評価**
   - 新規サブエージェントで同じシナリオを再実行する。
   - シナリオを修正内容に合わせて簡単にしない。
7. **収束判定**
   - ベースラインを iteration 1 とし、iteration 2 以降は各シナリオを直前の iteration と比較する。
   - 新規の不明瞭点がなく、各シナリオの精度が悪化せず、改善が 0 から 3 パーセントポイントという比較結果が 2 回連続したら収束とする。最短の収束は iteration 3 である。
   - 表現が違っても `Cause` と `General Fix Rule` が実質的に同じ不明瞭点は、台帳上の既出パターンとして扱う。
   - 収束時は、ベースライン準備で確定した未使用の hold-out シナリオを実行する。
   - 直近平均は、収束判定に使った直近 2 iteration の各シナリオ精度を等重みで算術平均する。
   - hold-out の精度が直近平均より 15 パーセントポイント以上低い場合は過適合とし、新しい評価サイクルとしてシナリオと要件チェックリストの設計からやり直す。
   - 3 iteration 以上続けても新規の不明瞭点が減らない場合は、小修正を止めて指示の構造を見直す。

質的な不明瞭点と裁量補完を主に評価し、精度を補助とする。
Codex のサブエージェント呼び出しから標準化された `tool_uses` と `duration_ms` を取得できないため、本スキルの評価表と収束条件では扱わない。
実行環境が同等の値を明示的に返す場合は参考値として別記してよいが、シナリオ間の正式な比較には使わない。

## 修正の伝播パターン

一つの修正が複数の評価項目へ及ぼす効果は、線形とは限らない。

- **Conservative swing**：複数項目へ効くと見積もった修正が、一項目だけを改善する。
- **Overshoot**：コマンド、設定、期待出力のような一つの構造的な情報が、複数項目を同時に改善する。
- **Zero-shoot**：評価軸の名前から推測した修正が、具体的な判定文言のどれにも届かず、効果が出ない。

修正前に「要件チェックリストのどの判定文言を、なぜ満たすのか」を書き出す。
評価軸の名前だけに修正を対応づけない。
評価項目は、何があれば達成と判定できるかが分かる粒度で書く。

## サブエージェント起動契約

サブエージェントには、次の構造で依頼する。

```text
あなたは <対象プロンプト名> を初めて読む実行者です。

## 対象プロンプト
<全文、または読み取り可能なパス>

## シナリオ
<現実的な状況設定>

## 要件チェックリスト
1. [critical] <最低ライン>
2. <通常項目>
3. <通常項目>

## タスク
対象プロンプトに従ってシナリオを実行し、成果物を生成してください。
終了時に次のレポートを返してください。

## レポート
- 成果物: <生成物または実行結果の要約>
- 要件達成: 各項目を ○、×、部分的のいずれかで判定し、理由を添える
- Trace: Understanding、Planning、Execution、Formatting を OK、stuck、skipped で示す
- 不明瞭点: 各項目を Issue、Cause、General Fix Rule の三つで示す
- 裁量補完: 指示で決まっておらず、自分の判断で埋めた箇所
- 再試行: 同じ判断をやり直した回数と理由
```

四つの Trace がすべて OK なら `Trace: all OK` の一行でよい。
stuck または skipped があれば、該当 phase の理由を一行で添える。
失敗時は、どの `[critical]` 項目が落ちたかを不明瞭点に含めさせる。

## 環境制約

新規サブエージェントを起動できない環境では empirical 評価を実行しない。
自己再読を empirical 評価の代用にしない。
依頼の範囲内であれば構造審査へ切り替え、empirical 評価ではないことを完了報告に明記する。

## 失敗パターン台帳

対象プロンプトごとに、iteration をまたぐ失敗パターンを記録する。

```text
- Pattern: <短く具体的な名前>
  - Example: <観測された Issue>
  - Cause: <原因>
  - General Fix Rule: <同種の失敗を防ぐ一般則>
  - Seen in: iter N, iter M
```

修正前に台帳を確認する。
`Cause` と `General Fix Rule` が実質的に同じ問題が再発した場合は `Seen in` を更新し、既存の修正が再発を防げなかった理由を記録する。
的を絞った修正後も三回以上再発するパターンは、指示の構造上の問題として扱う。

## 提示フォーマット

```text
## Iteration N

### 変更点
- <前回からの最小修正>
- Pattern applied: <Pattern 名または new>

### 実行結果
| シナリオ | 成功 | 精度 | retries | Weak phase |
| --- | --- | --- | --- | --- |
| A | ○ | 100% | 0 | なし |

### 今回新出の不明瞭点
- Issue: ...
  Cause: ...
  General Fix Rule: ...

### 今回新出の裁量補完
- ...

### 台帳更新
- Added または Re-seen: ...

### 次の修正案
- ...

収束判定: 連続 X 回クリア
```

## Red flags

| 合理化 | 実際の問題 |
| --- | --- |
| 「自分で読み直せば同じ効果がある」 | 直前に書いた指示へのバイアスを除けないため、新規サブエージェントが必要である。 |
| 「1 シナリオで十分」 | 一つの例へ過適合しやすいため、中央値と edge case が必要である。 |
| 「不明瞭点が一度ゼロになったから終える」 | 偶然の成功を除外できないため、連続二回と hold-out で確かめる。 |
| 「複数の問題を一度に直す」 | どの修正が効いたか判別できなくなる。 |
| 「関連する微修正も別 iteration にする」 | 一つの意味的なテーマを分割しすぎると iteration が増える。 |
| 「数値が良いので質的な指摘を無視する」 | 指示から必要な説明を削りすぎた可能性を見落とす。 |
| 「同じサブエージェントを再利用する」 | 前回の指示と結果を学習済みで、白紙の評価にならない。 |

## よくある失敗

- **シナリオが簡単すぎる、または難しすぎる**：どちらも指示の品質に由来する差が現れない。
- **精度だけを見る**：達成率が高くても、不明瞭点や裁量補完が多ければ指示は脆い。
- **一つの iteration に修正を詰め込みすぎる**：改善の原因を追跡できなくなる。
- **シナリオを修正に合わせる**：失敗を隠す方向に評価条件が変わり、改善を測れなくなる。
