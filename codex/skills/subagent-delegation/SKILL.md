# サブエージェントの役割選択と委譲

サブエージェントを起動する前に役割を選び、その役割に割り当てたモデルと起動設定で起動する。
エージェントごとの例外は、選択の原則より優先する。

## 役割

| 役割 | 担当 |
|---|---|
| 調査 | 探索、調査、fan-out。ファイルを編集しない |
| 実装 | 機械的な修正、通常の実装、執筆の起草・書き換え |
| 上位実装 | `risk-based-review` の高リスク以上の実装、複数パッケージにまたがる実装、難度の高い実装・原稿、「実装」が複数回失敗したタスク |
| 設計・分析 | 設計判断（高リスク変更の事前検討を含む）、構成の検討、難度の高い原因分析（複数回の失敗、原因の特定不能など）。大量生成や定型作業には使わない |
| 標準レビュー | レビュー（skill や prompt の検証を含む）、指摘だけを返す推敲（原稿を書き換える推敲は起草と同じ扱い） |
| 高強度レビュー | 高リスク以上の変更のレビュー、上位の段が作った成果物のレビュー |

## 選択の原則

- 「段」は割り当てたモデルの価格の段を指し（性能の順位は課題で入れ替わり、一通りに決まらないため）、上の表の役割の並びではない。同じモデルを割り当てた役割は同じ段とする。
- セッション自身のモデルは選択に影響させない。
- 通常リスクでは、正しさは実装の役割の格上げではなくレビュー強度で担保する。設計・分析を上位の段に任せても、実装の役割は上の表で選び直す。
- 迷ったら安価な段から試し、品質が足りなければ一段上げる。上の段がない、または起動に失敗した場合は元の段のまま続ける。
- レビューの段は、`risk-based-review` で決めた強度に対応する役割と、作成側の一段上のうち高い方にする。同じ段のレビューは、作成時の誤った前提を引き継ぎやすい。
- 作成側の段は、委譲したなら起動したモデルの段、メインセッションが自分で作ったなら同じ作業を委譲するときに上の表で選ぶ役割の段とする。
- 作成側に一段上の段がなければ、同じ段の新規サブエージェントに依頼してコンテキストを分ける。高リスク以上では、一段上げられない代わりに観点 A / B の 2 本に分けて依頼する（観点の定義は `risk-based-review`）。
- 委譲したら、作成に使った役割をリポジトリの慣習（plan ファイルやコミット trailer など）に従って記録する（レビューの段を決めるときに使う）。
  モデルは役割から割り当て表で引けるので、記録するのは割り当て表と異なるモデルで起動した場合（代替の起動や例外）だけでよい。

## 依頼と報告の受け取り

- 依頼文の冒頭で、サブエージェントとして起動したことを伝える。伝えないと自身をメインと誤認し、親からの追加指示をプロンプトインジェクションとみなして拒むことがある。
- 1 本に独立した複数タスクをまとめない。実行が長引くほど、利用上限に達したときの損失が大きくなる。
- fan-out（並列調査）は、ディレクトリや年月など自然な単位で分け、1 本が 1 回で完遂できる粒度にする。
- 並列でファイルを編集させるときは、担当ファイルを重ねない。重なりを避けられなければ、作業ツリーを分けるか直列にする。
- 実装を委譲するときは、起動前の HEAD を記録し、そこからの範囲を検証・レビューする。コミットしてよい作業（規則ファイルかユーザーが許している）なら、依頼文でコミットまで指示する。
  未コミットの変更と未追跡ファイルが残っていれば、それも範囲に含める（コミットを指示しないときは必ず残る）。
- 完了条件を明示し、作業だけでなく判断と責任も任せて完遂させる。曖昧な点は判断基準を添え、確認の往復で止めない（真に必要な相談は除く）。
- 報告はメインの判断に必要な情報だけに絞らせる。
  - 調査: 結論、根拠（ファイルと行）、リスク、未解決点、次のアクション。
  - 実装: 変更概要、変更ファイル、設計判断、検証結果、懸念点。
  - ログ、ファイル全文、diff 全文、思考過程は返させない。
- メインは結論、根拠、不確実な点と、判断に使う該当行だけを確かめ、サブエージェントと同じ手順で調べ直さない（差分とテスト結果の確認は除く）。情報が足りなければ追加指示で補う。
- 利用上限に達した（そのことを示すエラーが出た）と判断できたら、同じセッションやタスクで再投入せず、上限に達したことと未完了の範囲をユーザーに報告して指示を待つ。
  上限で中断したレビューを「指摘なし」と解釈しない。

## 割り当て（Codex）

段は `~/.codex/agents/*.toml` の `model` の価格順で決まる（通常の起動で使うモデルと reasoning effort は TOML で管理し、この skill には書かない）。
現在の TOML では `explorer` と `implementer` が最も安価で、`senior_implementer` と `reviewer` がその上、`architect` と `frontier_reviewer` が最上位になる。

| 役割 | エージェント |
|---|---|
| 調査 | `explorer` |
| 実装 | `implementer` |
| 上位実装 | `senior_implementer` |
| 設計・分析 | `architect` |
| 標準レビュー | `reviewer` |
| 高強度レビュー | `frontier_reviewer` |

- 役割（エージェント名）の指定がモデルの指定に当たり、カスタムエージェントの TOML のモデルと effort は起動時の指定より優先される。
  モデルを直接指定するのは、役割指定が使えない場合と、下記の例外で TOML と異なる設定を使う場合に限る。
- 委譲ツールが役割指定に対応しない（または使えない）場合は、対象 TOML の `model` と、`model_reasoning_effort` に対応する effort 引数を明示し、`developer_instructions` の行動制約を依頼文に含める。
- `sandbox_mode` を指定できる環境では TOML と同じ値を渡す。指定できなければ、その役割の TOML の `developer_instructions` に従う制約を依頼文に明記する。
  read-only の役割では編集と再委譲の禁止を明記し、その禁止が技術的な書き込み制限ではないことを結果に記録する。
- 独立レビューと empirical 評価の実行者は `fork_turns="none"` で起動し、必要な文脈と完了条件を依頼文に明記する。履歴継承とモデル上書きを併用できないツールでは、ほかの委譲も同じ方法で起動する。
- 作成に使った役割を記録するときは effort も記録する。モデルを明示的に上書きしたときは effort も指定する。

## 例外と制約（Codex）

- `architect` には実装させない。実装が複数回失敗したときだけ、組み込みの `worker` に `architect` の TOML のモデルと `senior_implementer` の TOML の effort を明示して委譲する。
  役割は上位実装として記録し、`senior_implementer` の `developer_instructions` を依頼文に含める。
  `sandbox_mode` は `senior_implementer` の TOML に指定があれば従い、なければ親の設定を継承する（`architect` の TOML の read-only に従うと `worker` が実装できないため）。
- `architect` と同じモデルの成果物は、新規の `frontier_reviewer` にレビューを依頼する（同じモデルでもコンテキストは必ず分け、高リスク以上では選択の原則どおり 2 本に分ける）。
- `frontier_reviewer` は TOML の effort を既定とする。
  非常に高リスクな変更、複雑な論理や境界条件の検証、初回の判断が不確かな場合だけ、組み込みの `default` に `frontier_reviewer` の TOML のモデルと effort `high` を明示する。
  このときは同 TOML の `developer_instructions` を依頼文に含め、`sandbox_mode` は「割り当て（Codex）」の規則に `frontier_reviewer` の TOML を当てはめて扱う（指定できれば同じ値を渡し、できなければ制約を依頼文に明記する）。
- 該当する TOML がない環境（現在のエージェント一覧にも `~/.codex/agents/`、`.codex/agents/` にもない）では、レビューを組み込みの `explorer` の新規起動で代替する。
  - 起動 API で sandbox を指定できれば read-only にし、できなければ編集と再委譲の禁止を依頼文に明記する。
  - モデルや effort を確実に指定できなければセッションの値を継承し、強度は新規コンテキスト、観点の特化、高リスク以上での 2 本立てで担保する。
