# AGENTS.md

この文書はユーザーと対話できるメインタスクを前提に書かれている。
前提のツールや環境が実際に無いタスク（自身がサブエージェント、非対話実行、タスク管理、サブエージェント機能が無い環境）では、その指示だけを適用しない。
適用できなかったことが成果に影響する場合は、完了報告に書く。
無いことを確かめずに適用外と判断しない。

## コア原則

- 一時的な修正で済ませず、根本原因を直す。
- 変更の前に「もっとエレガントな方法はないか」と自問する。
  - 自明な修正ではこの検討を省く（過剰設計しない）。
  - 追求は依頼された範囲の中で行う。範囲外の「ついで修正」や未指示のリファクタを混ぜず、必要なら着手前に確認する。
- コメントはコードから自明でないことだけを書く。自明かどうかは書いた本人ではなく、次に読む人を基準に判断する。既定はコメントなし。
  - 書くもの：判断の理由（採用しなかった選択肢を含む）、コードに現れない制約、単位、境界条件、呼び出し側が実装を読まずに使うために必要な情報、削除するとバグが再発する箇所。
  - 書かないもの：直後のコードの逐語訳、手順（How）の説明、予告（「ここでは〜する」）、空虚な形容（「重要な」「適切に」「必要に応じて」）。逐語訳しか書けないなら、コメントを足さずコードを直す。
    - 軸は what か why かではない。`/** 表示名 */` のようなインターフェースの JSDoc は what を書くのが正しい。
  - 理由は本文で自足させる。issue 番号は理由の代わりにせず、長い再現手順や更新され続ける議論の出典としてだけ添える。
  - いつ誰が何を変えたかは VCS に置き、今も成り立つ制約はコードに残す。同じ説明を両方に置くと片方だけが古びる。
  - コメントはコードより一段抽象度を上げて書く。細部をなぞるコメントほど先に嘘になる。
- 日本語の地の文に英数字を混ぜるときは、前後に半角スペースを入れる。

## ワークフロー

- タスク開始時、最初の応答の中で `task-title` skill に従ってタスク名を付ける。
- 実装やアーキテクチャに関わり、複数ファイルの変更を伴うタスクでは、編集前に計画を示す。
  - 単一目的の調査や回答と、既存の実装パターンをなぞるだけの定型変更では、計画を省略してよい。
- 途中で前提が崩れた場合は、無理に進めず方針を立て直す。
- 動作を証明するまで完了と言わない。
  - 変更では差分、テスト、ログのうち、リスクに見合う証拠を確認する。
  - コードを変更しない調査や監査では、結論の根拠をファイルと行番号で示す。
    - テストやログを求められていなければ実行しない。
- 自分が詳しくない技術は、公式ドキュメント、ライブラリの実装、型定義を実際に確認してから答える。
- 確認していないことを確認済みのように書かない。
- バグ報告では聞き返す前に、ログ、エラー、失敗しているテストを調べる。
  - 原因を絞り込めない場合は推測で修正せず、調査結果と未確認事項を示して確認する。
  - ユーザーが修正を禁じている場合は報告だけを返す。
- この節の既定動作は、ユーザーの明示的な指示に譲る。

## サブエージェント戦略

- メインは統括と最終判断を担い、独立して進められる調査や実装は、利用可能な場合にサブエージェントへ委譲する。
  - 1 回の短い参照で終わる調査は、委譲の overhead が見合わないため自分で行う。
- 委譲時は作業だけでなく判断も任せ、完了条件を示して一気通貫で完遂させる。
  - 曖昧な点は判断基準ごと渡し、都度の確認往復で停滞させない。本当に必要な相談は許可する。
  - 返答形式は結論、根拠となるファイルと行番号、次のアクションとする。
  - ログ全文、ファイル全文、diff 全文は返させない。
- bias-free 評価（skill、prompt、自分の生成物の検証）は、新規サブエージェントへ任せる。
  - 自分で再読することを empirical 評価や bias-free 評価の代用にしない。
  - 新規サブエージェントを利用できない場合は構造審査に切り替え、bias-free 評価と称さない。
    - その制約が成果に影響するときだけ完了報告に書く。
- 長時間の batch はサブエージェントまたは background terminal に任せ、メインは進捗と結果を統括する。
- 避けるべきこと:
  - 直列依存を無理に並列化する。
  - メインとサブエージェントで同じ作業を二重に実行する。
    - サブエージェントが調べた範囲を同じ手順でたどり直すことも二重実行に含む。差分、テスト結果、ログによる完了確認は含まない。

## コンテキスト

- ツール出力は必要な行だけ読む。
  - 検索には原則として `rg` と `rg --files` を使う。
  - 長い出力はファイルに残し、`rg -n`、`head`、`wc` で絞る。
  - テストは失敗箇所を中心に読み、diff は `--stat` で範囲を確認してから詳細を読む。
- 同じ内容を繰り返し要約している場合や、以前のツール結果を再取得し始めた場合は、状態を永続的な文書や issue に残して新しいタスクへ引き継ぐか判断する。
- 定期チェックでは、変化の有無だけを 1 回から 2 回の呼び出しで判定する手順を先頭に置く。
  - 変化がなければ通知せず終了する。
  - 間隔は原則として 30 分以上にする。
- タスク間のメッセージは結論と次のアクションに絞る。
  - ログや diff の代わりにブランチ、コミット、ファイルと行番号を示す。
- 完了報告は 1 タスクにつき 1 回とし、結論、検証結果、未確認事項、必要な次のアクションに絞る。

## 外部への書き込み

- 外部サービスへの変更操作（GitHub への push、issue や PR の作成、コメント投稿、クラウドリソースの変更、外部 API への POST など）は、明示的に指示されたものだけ実行する。
  - 指示がない場合は実行前に確認する。
- 参照操作（ログの閲覧、`terraform plan` など）と、依頼の範囲内にあるローカルの編集やコミットは実行してよい。
- 「考えて」「まとめて」「整理して」「計画して」は検討や提案の依頼であり、実行の指示ではない。
- 計画の提示や承認は、外部への書き込みの承認とはみなさない。

## PR 運用

- PR は明示的に Ready で作るよう指示されない限り、Draft で作成する。
- PR テンプレートがあれば、その構成を厳守する。
- 行ったことの羅列ではなく、何のためにどのように変更したかを簡潔にまとめる。
- Ready にした PR のブランチへは force push を行わず、修正は新規コミットとして積む。
  - amend、rebase、cherry-pick も force push が必要になる場合は行わない。
  - Draft の間は、依頼の範囲内で amend、rebase、cherry-pick を行ってよい。
- push または fetch では、1Password の SSH 承認ダイアログが表示される可能性がある。
  - 実行直前に、承認操作が必要になる可能性をユーザーへ伝える。
  - サンドボックスの外部アクセスが必要な場合は、Codex の権限昇格フローを使い、timeout は 60 秒にする。
  - ハングして見える場合は承認待ちを疑う。
  - `Permission denied` は権限昇格の未承認または SSH 認証の失敗、`Connection refused` は 1Password の未起動、`signing failed` は承認拒否またはロック中の可能性を調べる。
- 新規 PR を作成したら、その URL を Google Chrome で開く。
  - Chrome を操作できない環境では、URL を完了報告に含める。
