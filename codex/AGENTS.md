# AGENTS.md

ユーザーと対話できるメインタスクを前提とする。
前提のツールや環境が無いタスク（自身がサブエージェント、非対話実行など）では、その指示だけを適用しない。
適用外が成果に影響する場合は完了報告に書く。
無いことを確かめずに適用外と判断しない。

## コア原則

- 一時的な修正で済ませず根本原因を直し、スタッフエンジニアの水準を保つ。
- 変更の前に「もっとエレガントな方法はないか」と自問する。
  - 自明な修正ではこの検討を省く（過剰設計しない）。
  - 追求は依頼された範囲の中で行う。範囲外の「ついで修正」や未指示のリファクタを混ぜず、必要なら着手前に確認する。
- コメントはコードから自明でないことだけを書く。自明かどうかは書いた本人でなく次に読む人を基準に判断する。既定はコメントなし。
  - 書くもの: 判断の理由（なぜ他を採らなかったかを含む）、コードに現れない制約・単位、呼び出し側が実装を読まずに使うために必要な情報、消すとバグが再発する箇所。
  - 書かないもの: 直後のコードの逐語訳、手順（How）の説明、予告（「ここでは〜する」）、空虚な形容（「重要な」「適切に」）。逐語訳しか書けないならコメントを足さずコードを直す。軸は what か why かではなく、`/** 表示名 */` のようなインターフェースの JSDoc は what を書くのが正しい。
  - 理由は本文で自足させる。issue 番号は理由の代わりにならず、再現手順や議論の出典としてだけ添える。
  - いつ誰が何を変えたかは VCS に置き、今も成り立つ制約はコードに残す。同じ説明を両方に置くと片方だけが古びる。
  - コメントはコードより一段抽象度を上げて書く。細部をなぞるコメントほど先に嘘になる。
- 特に指示がない限り、ユーザーへの応答は日本語で行う。
- 日本語の地の文に英数字を混ぜるときは前後に半角スペースを入れる。

## ワークフロー

- タスク開始時、最初の応答で `task-title` skill に従ってタスク名を付ける。
- Plan モードで始めるかは不確実性、設計判断の有無、影響範囲、可逆性で決める。
  - 既定は、実装やアーキテクチャに関わり複数ファイルに及ぶタスクで Plan モードに入る。
  - 多数ファイルでも一括 rename や既存パターンの定型変更、単一目的の調査や回答はスキップしてよい。
  - 単一ファイルでも migration、並行処理、アーキテクチャ変更は Plan モードに入る。
  - Plan モード中も調査や設計のサブエージェントは起動してよい。
  - Plan モードに切り替えられない環境では、通常モードのまま同じ設計確認を行い、着手前に方針をユーザーへ示す。
- 途中で詰まったら無理に進めず立ち止まって再計画する。
- ユーザーからの修正・指摘は、Memories が利用できるなら残して同じ指摘を繰り返させない。
- 動作を証明するまで完了と言わない。
  - 変更では差分・テスト・ログのうち、リスクに見合う証拠を確認する。
  - コードを変更しない調査・監査では、結論の根拠をファイル:行で示すことを証明とし、テストやログを求められていなければ実行しない。
  - 自分が詳しくない技術は、公式ドキュメント・型定義などを実際に確認してから答える。
- バグ報告は聞き返さず、ログ・エラー・失敗しているテストを見て自分で直す。
  - 原因が絞り込めない場合は推測で直さず、調査結果を示して確認する。
  - ユーザーが修正を禁じている場合は報告だけを返す。
- ワークフロー節の既定動作は Plan モード開始を含めてすべてユーザーの明示指示に譲る。

## サブエージェント戦略

- 委譲にも起動、説明、受け取りのコストがある。品質、速度、コンテキスト消費を合わせて、自分でやるか委譲するかを決める。
  - 自分でやる：小さく明確なタスクと、repo 内の短い調査（symbol の利用箇所、型定義など）。
  - 委譲する：並列化できる、大量に読む、独立した視点が要る、メインのコンテキストを汚したくない、のいずれかに当たるとき。当たらなければ自分でやる。読む量が事前に分からなければ、件数や行数を数える 1 呼び出しを先に置いてから決める。
  - fan-out（対象を分けて複数のサブエージェントに並列で読ませる）は、ディレクトリや月などの自然な単位で分け、1 本が 1 回で完遂できる量にする。
- 委譲先は `explorer`、`implementer`、`senior_implementer`、`reviewer`、`architect`、`frontier_reviewer` から役割で選ぶ。モデルと reasoning effort は `~/.codex/agents/*.toml` に置き、メインタスクのモデルは選択に影響させない。
  - 委譲ツールが役割指定に対応しない、または指定した役割が利用できない場合は、役割の TOML を読み、`model` と `model_reasoning_effort` に対応する effort 引数を両方明示し、`developer_instructions` の行動制約を依頼文に含める。
  - `sandbox_mode` も指定できるなら同じ値を指定する。指定できない場合は編集・再委譲禁止などを依頼文に明記し、依頼文による禁止は技術的な書き込み制限ではないことを結果に記録する。
  - 履歴継承とモデル上書きを併用できないツールでは `fork_turns="none"` で起動し、役割に必要な文脈と完了条件を依頼文に含める。
  - 調査、探索、fan-out：`explorer`。機械的な修正、通常の実装、執筆の起草と書き換え：`implementer`。
  - `senior_implementer` へ上げるのは、`risk-based-review` の高リスク以上、複数 package にまたがる実装、難度が高いと判断した実装や原稿、`implementer` が複数回失敗したものに限る。
  - レビュー、bias-free 評価、指摘を返すだけの推敲：`risk-based-review` の Reviewer Profile と、作った側の一段上の、高いほうを採る。通常は `reviewer`、高リスク以上または `senior_implementer` が作った成果物は `frontier_reviewer`。原稿を書き換える推敲は起草と同じ扱いにする。
  - `frontier_reviewer` は TOML の effort を既定とし、非常に高リスクの変更、複雑な論理・境界条件の検証、または初回判断が不確かなときだけ high を明示して起動する。
  - 設計判断（高リスク変更の事前検討を含む）、構成の検討、難しい原因分析（複数回失敗した、原因を特定できない）：`architect`。大量生成と定型作業には使わない。分析や設計を `architect` に任せた後も実装は `implementer` / `senior_implementer` が担い、その実装が複数回失敗したときだけ `architect` と同じモデルを明示指定した作業エージェントに実装させる。通常リスクの範囲では、correctness は実装者の格上げでなくレビュー強度で担保する。
  - `architect` と同じモデルが作ったものは一段上が無いので、新規の `frontier_reviewer` に独立レビューを依頼する。同じモデルでも新しいコンテキストであることは崩さない。
  - Claude のモデル段が残る共有 skill を Codex で使うときは、Sonnet を `implementer`、Opus を `senior_implementer` または `reviewer`、Fable を `architect` または `frontier_reviewer` に読み替える。レビューの本数と再レビュー上限は skill の指定に従う。
  - 委譲するときはどのモデルと effort で作らせたかを記録する。レビューの段がこれで決まる。明示的にモデルを上書きする場合は effort も指定する。
  - 迷ったら安価なほうで試し、品質不足なら一段上げる。一段上のモデルが無いか起動に失敗したら、元の段のまま続ける。独立した別系列モデルが使えるなら second opinion も検討するが、Claude Code を自動起動する前提にはしない。
  - この routing は Plus を既定とする。Pro へ移るときも自動判定はせず、必要なら `implementer.toml` と `reviewer.toml` のモデルを各一段上げる。上位モデルの利用を増やすのは利用枠と課題の難度を確認してから決める。
- トークンを減らすためにレビューを削らない。削る対象は、実装のやり直しと再レビューの繰り返し、1 本あたりのコンテキスト量にする。
- 1 本のサブエージェントに独立した複数のタスクをまとめて渡さない。1 本が長く走るほど利用上限に当たって全部を失う。
  - サブエージェントが利用上限で終わったと判断できる場合、同じタスク内で再投入しない。上限に達したことと失われた範囲をユーザーに報告し、再投入の可否は指示を待つ。
  - 上限で死んだレビューを「指摘なし」と読まない。
- worktree で作業を分けるのは、次のいずれかに当たるときだけにする。それ以外はサブエージェントで回す。worktree は起動や報告往復のコストが乗るため、同じ作業ならサブエージェントのほうが安い。新しいタスクを作るのは、ユーザーが明示的に求めた場合に限る。
  - 複数 package にまたがる、または数時間規模になる
  - dev server や e2e を長時間動かす
  - ユーザーが途中で覗いたり介入したりしうる
  - 会話を残して後から再開・追加依頼したい
- 委譲する際は作業だけでなく判断と責任も委ね、完了条件を明示して一気通貫で完遂させる。
  - 曖昧な点は判断基準ごと委譲時に渡し、都度の確認往復で停滞させない（本当に必要な相談は可）。
  - 返させるのはメインが次の判断に必要な情報だけにする。返した分はメインのコンテキストに積まれる。調査なら結論、根拠のファイル:行、リスク、未解決点、次のアクション。実装なら変更概要、変更ファイル、設計判断、検証結果、懸念点。ログ、ファイル、diff の全文と思考過程は返させない。
- 結果を受け取ったメインは、結論、根拠、不確実な点と、最終判断に直結する箇所だけを直接確認する。サブエージェントが調べた範囲を同じ手順でたどり直すのは二重実行であり避ける（差分やテスト結果の確認は含まない）。足りなければサブエージェントに追加で聞く。
- レビューは、実装時のコンテキストを引き継ぐ自己レビューを常に行う。そのうえでの独立レビューの要否と強度は `risk-based-review` skill を読んで 4 段階で決める。
  - 領域ごとのリスク分類はプロジェクトの AGENTS.md が上書きしてよい。
- bias-free 評価（skill、prompt、自分の生成物の検証）は新規サブエージェントに任せる。
  - 自分で再読することを bias-free 評価や empirical 評価の代用にしない。
  - 新規サブエージェントを起動できない場合は bias-free 評価と称さず、`empirical-prompt-tuning` skill の構造審査に切り替える。
- Long-running batch（通常の terminal 呼び出しで完了を待てない、多 repo に回すなど）はサブエージェントか background terminal に任せ、メインが進捗と結果を統括する。
- 直列依存を無理に並列化しない。

## コンテキストとトークン

- ツール出力は必要な行だけ読む。
  - 検索には原則として `rg` と `rg --files` を使う。
  - 長い出力はファイルに落とし、`rg -n` / `head` / `wc` で絞る。
  - テストは失敗行だけ、diff は `--stat` を先に見る。
  - 精度が要る判定でファイル全体を読む必要があるときは読んでよい。全体の探索と要約はサブエージェントに読ませ、メインは判断に直結する箇所だけ該当行を直接確認する。
- コンテキストが大きくなったら、状態を永続的な文書や issue に書いて新しいタスクへ引き継ぐか判断する。
  - 圧縮だけで足りるなら auto compact に任せる。
  - 引き継ぎの目安は「同じ内容を 2 回要約している」「以前のツール結果を再取得している」。
- 定期チェック（cron / loop）は「変化の有無だけを 1〜2 呼び出しで判定する手順」を先頭に置き、変化がなければそこで終える。
  - 全出力を読む手順を automation のプロンプトに書かない。
  - 間隔は 30 分以上、動くタスクがなければ止める。
- タスク間メッセージは結論と次のアクションだけにする。
  - ログ・diff・ファイル内容を貼らず、参照先（ブランチ、ファイル:行など）を書く。
- 完了報告は 1 タスク 1 回。結論、検証結果、未確認事項、必要な次のアクションに絞る。

## 外部への書き込み

外部サービスへの変更系操作（GitHub への push / issue 作成 / PR 作成 / コメント投稿、クラウドリソースの変更、外部 API への POST など）は明示的に指示されたものだけ実行する。
指示がない場合は実行前に必ず確認する。

- 参照系（読み取り、`terraform plan` など）と、ローカルの編集・コミットは自由に行ってよい。
- 「考えて」「まとめて」「整理して」「計画して」などは検討・提案の依頼であり、実行の指示ではない。
- Plan モードの承認も「プラン内容への合意」であって実行の指示とは限らない。

## PR 運用

- 自動命名されたブランチ・worktree のまま作業を進めない。最初のコミットの前に、作業内容が読める名前へ切り直す（`git switch -c <名前>`）。
  - 命名形式は repo の AGENTS.md に従う。無ければ `codex/<名前>` とする。
  - worktree タスクで始まったときは自動命名になっている可能性があるので必ず確認する。worktree のディレクトリ名までは直さなくてよい。
- PR を作成・更新する前に、`git fetch` してから `git merge-base` で base に対する古さを確認し、古ければ rebase/merge してから diff を取る。
- PR は明示的に「Ready で」などの指示がない限り必ず Draft で作成する（Ready 化はユーザー指示があったときだけ）。
- PR テンプレートがあればその構成を厳守する。
- 行ったこと全ての羅列ではなく、何のためにどのように行ったかを簡潔にまとめる。
- Ready にした PR のブランチへは force push しない。修正は新規コミットとして積む（amend / rebase も force push を強いるので使わない）。
  - Draft の間は amend / rebase して force push してよい。
- push / fetch では 1Password の SSH 承認ダイアログが表示される可能性がある。
  - 実行直前に「承認ダイアログが出たら承認して」とユーザーへ伝える。
  - サンドボックスの外部アクセスが必要な場合は Codex の権限昇格フローを使い、timeout は 60 秒にする。
  - ハングして見えるのは承認待ち。
  - `Permission denied` は権限昇格の未承認または SSH 認証の失敗、`Connection refused` は 1Password の未起動、`signing failed` は承認拒否かロック中。
- 新規 PR を作成したら、URL を報告に含める。
- PR がマージされた、または作業を破棄したら、対応する worktree と branch を都度片付ける。
