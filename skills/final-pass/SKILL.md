# 仕上げ

ファイルを変更する作業を完了と報告する前に、以下を順に行う。
各手順の詳細は参照先の skill に従う。
該当しない手順は飛ばす。

## 手順

1. **検証**: `completion-verification` skill で、変更が動くことを確かめる。
   要修正なら直してから次へ進む（壊れたものをレビューに出さない）。
2. **独立レビュー**: `risk-based-review` skill のリスク分類（着手時の分類を実際の変更で見直したもの）に従い、必要なら独立レビューを依頼して指摘に対応する。
   独立レビューが必要なのにサブエージェントを起動できない環境では、同 skill の観点別の自己点検に切り替える。
3. **文章の見直し**: 今回の作業の diff に含まれるコメントと文章を見直す。
   - コメントは、ユーザー設定の指示（`~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`、`~/.gemini/config/GEMINI.md` に当たるもの）のコア原則にあるコメントの規範に照らす。
   - 日本語の地の文（文書、コミットメッセージ、PR 本文）は、同じくコア原則の日本語の規範に照らす。
   - 日本語の散文ドキュメント（README、SKILL.md、設計文書など）には、加えて `japanese-tech-writing` skill を適用する。
     一文一行や脚注などの原稿向けの整形がリポジトリの既存の書式と食い違う場合は、既存の書式を優先する。
   - リポジトリの規約がコメントやコミットの言語・形式を定めていれば、それを優先する。
   - コミットメッセージはここで規範に照らし、直す場合は 5 でまとめて行う。
4. **再検証**: 2 の指摘対応のうち確かめていない変更と、3 で変更した分を `completion-verification` skill で確かめる。
   コメントと文章だけの変更なら差分の確認で足りる。
   確かめたあと、3 の修正のうちコミット済みの箇所への修正をコミットする。
   コミットする前に、書き換えてよいかを `tidy-commits` の判定で決める。
   書き換えてよければ、直す箇所を入れたコミットに対する fixup コミットにして 5 で畳む。
   書き換えなければ通常のコミットとして積む。
5. **コミット整理**: 2 と同じ範囲（作業開始前に記録した HEAD から現在の HEAD まで）のコミットに、手直しのコミット、意味の切れ目と合わないコミット、メッセージが規範に合わないコミットがあれば、`tidy-commits` skill で整理する。
   書き換えてよいかは同 skill の判定に従う。
   書き換えない場合は、3 で見つけたコミットメッセージの問題を直さず、完了報告に書く 5 の理由の行に添える。

## 報告

- 1・3・4 は、飛ばした場合も実施して変更がなかった場合も、完了報告に理由を書かない。
- 2 と 5 は、行わなかった場合に理由を 1 行ずつ書く。2 の理由にはリスク分類の名前を含める。

## 適用範囲

- 3 の手直しが誤字や言い換えに留まる場合は、2 のレビューをやり直さない（`risk-based-review` の「軽微」に当たる）。
  3 でコードの挙動や指示の意味が変わる修正をした場合は、同 skill の再レビューの規定（修正分のみ、上限の回数まで）に従う。
  再レビューは、4 で修正をコミットしたあと、5 で履歴を書き換える前に依頼する（書き換えると SHA が変わり、修正分の範囲を指定できなくなる）。
- サブエージェントとして動いている場合は 1・3・4 だけを行う。
  2 と 5 は行わず、それぞれの 1 行に、理由の代わりに要否の見立てを書いてメインに任せる。
  3 の修正をコミットするのは、依頼でコミットを指示されている場合だけとする。
  fixup コミットは畳まずに残し、3 で見つけたコミットメッセージの問題とあわせて報告に書く。
