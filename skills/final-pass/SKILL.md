# 仕上げ

ファイルを変更する作業を完了と報告する前に、以下を順に行う。
各手順の詳細は参照先の skill に従う。
該当しない手順は飛ばす。

## 手順

1. **検証**: `completion-verification` skill で、変更が動くことを確かめる。
   要修正なら直してから次へ進む（壊れたものをレビューに出さない）。
2. **独立レビュー**: `risk-based-review` skill のリスク分類（着手時の分類を実際の変更で見直したもの）に従い、必要なら独立レビューを依頼して指摘に対応する。
   独立レビューが必要なのにサブエージェントを起動できない環境では、同 skill の観点別の自己点検に切り替える。
3. **文章の見直し**: 今回の作業の diff に含まれるコメントと文章を見直す。
   - コメントは、ユーザー設定の指示（`~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`、`~/.gemini/config/GEMINI.md` に当たるもの）のコア原則にあるコメントの規範に照らす。
   - 日本語の文章（文書、コミットメッセージ、PR 本文、コード内のコメント）は、同じくコア原則の日本語の規範に照らす。
   - 日本語の散文ドキュメント（README、SKILL.md、設計文書など）の変更は、加えて `japanese-tech-writing` skill での点検を新規サブエージェントに任せる。
     同 skill の本文は長く、毎回メインのコンテキストに読み込むと消費がかさむため。
     - 役割は `subagent-delegation` の標準レビュー（指摘だけを返す推敲）とし、編集させない。
     - 依頼文には次を渡す。
       - 同 skill を読み、その規範で点検すること
       - 範囲：`risk-based-review` の開始時の HEAD から HEAD までと未コミットの変更のうち、日本語の散文ドキュメントのファイル。
         範囲のファイルは名前を挙げて渡し、diff にあるほかのファイル（英語のコメントを含むスクリプトなど）は点検しないと伝える。
       - リポジトリの書式（規約やメモリにある行の規則、既存ファイルの整形）。一文一行や脚注などの原稿向けの整形と食い違う指摘は、リポジトリの書式を優先させる。
       - 返し方：指摘ごとに 1 行で、箇所（ファイルと行番号。行番号は作業ツリーのファイル全体での行で、diff の行ではない）、当たる規範、直し方の案。
         メインは指摘を 1 件ずつ採否を決めてファイルを直すだけなので、`risk-based-review` の返却フォーマット（Strengths / Issues / Recommendations / Assessment）は使わせない。
         役割の定義（Claude Code の `reviewer` など）が返却フォーマットを定めていても、それに代えてこの形式で返すよう依頼文に明記する。
     - 指摘のどれを直すかはメインが決める。
     - 散文の変更が誤字や言い換えだけなら、任せずに同 skill での点検を飛ばす（`risk-based-review` の「軽微」に当たる）。
       誤字や言い換えに当たるのは、誤字の訂正、活用や語形の訂正（「見れる」を「見られる」に）、表記の統一、同じ意味の言い換え。
       意味や論旨の変わる言い換え、常体と敬体の切り替えのような文体の変更、文や項目の追加・削除は当たらない。
       飛ばすのは同 skill での点検だけで、上のコア原則の日本語の規範には照らす。
     - サブエージェントを起動できない環境では、自分で同 skill を適用する。
   - リポジトリの規約がコメントやコミットの言語・形式を定めていれば、それを優先する。
     定めがなければ、周囲の既存コメントと既存のコミットメッセージの言語・形式に合わせる。
     コメントの量と内容は周囲に合わせず、上のコメントの規範に従う。
   - コミットメッセージはここで規範に照らし、直す場合は 5 でまとめて行う。
4. **再検証**: 2 の指摘対応のうち確かめていない変更と、3 で変更した分を `completion-verification` skill で確かめる。
   コメントと文章だけの変更なら差分の確認で足りる。
   確かめたあと、3 の修正のうちコミット済みの箇所への修正をコミットする。
   コミットする前に、push 済みのコミットを書き換えてよいかを規則ファイル（`CLAUDE.md` / `AGENTS.md` / `GEMINI.md`）に従って決め、規則ファイルが許していなければユーザーに確かめる。
   書き換えてよければ、直す箇所を入れたコミットに対する fixup コミットにして 5 で畳む。
   書き換えなければ通常のコミットとして積む。
5. **コミット整理**: 2 と同じ範囲（`risk-based-review` の開始時の HEAD から現在の HEAD まで）のコミットに、手直しのコミット、意味の切れ目と合わないコミット、メッセージが規範に合わないコミットがあれば、`tidy-commits` skill で整理する。
   起点には `risk-based-review` の開始時の HEAD を渡す。
   書き換えてよいかは 4 と同じく決める。4 で確認して承認を得ていれば、確かめ直さない。
   書き換えない場合は、3 で見つけたコミットメッセージの問題を直さず、完了報告に書く 5 の理由の行に添える。

## 報告

- 1・3・4 は、飛ばした場合も実施して変更がなかった場合も、完了報告に理由を書かない。
- 2 と 5 は、行わなかった場合に理由を 1 行ずつ書く。2 の理由にはリスク分類の名前を含める。
  2 を観点別の自己点検に切り替えた場合も独立レビューは行っていないので、理由の行を書き、自己点検に切り替えたことを添える。

## 適用範囲

- 3 の手直しが誤字や言い換え（3 で定めたもの）に留まる場合は、2 のレビューをやり直さない（`risk-based-review` の「軽微」に当たる）。
  3 でコードの挙動や指示の意味が変わる修正をした場合は、同 skill の再レビューの規定（修正分のみ、上限の回数まで）に従う。
  再レビューは、4 で修正をコミットしたあと、5 で履歴を書き換える前に依頼する（書き換えると SHA が変わり、修正分の範囲を指定できなくなる）。
- サブエージェントとして動いている場合は 1・3・4 だけを行う。
  2 と 5 は行わず、それぞれの 1 行に、理由の代わりに要否の見立てを書いてメインに任せる。
  3 の `japanese-tech-writing` は、さらにサブエージェントを起動せず自分で適用する。
  3 の修正をコミットするのは、依頼でコミットを指示されている場合だけとする。
  fixup コミットは畳まずに残し、3 で見つけたコミットメッセージの問題とあわせて報告に書く。
