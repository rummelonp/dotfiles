# Empirical Prompt Tuning

プロンプトの品質は書いた本人には分からない。書き手が「明瞭だ」と思うものほど、別エージェントが読むと詰まる。本 skill は、**バイアスを排した実行者に実際に動かしてもらい、両面で評価して反復する**。改善が頭打ちになるまで止めない。

## 適用範囲

ユーザーが empirical 評価または静的審査を明示的に依頼し、次のいずれかに該当する場合に使う。
通常のスキルやプロンプトの編集・改訂後に自動起動しない（オペレーターが明示的にトリガーするワークフロー）。

- skill / slash command / タスクプロンプト / AGENTS.md 節 / 自動化プロンプトを新規作成または大幅改訂した直後
- エージェントが期待どおり動かず、指示の曖昧さを原因として検証したい場合
- 頻繁に使う指示を、複数の使用場面に対して堅牢にしたい場合

一回限りの使い捨てプロンプトや、成功率ではなく書き手の主観的好みだけを調整する場合には使わない。

## 評価モード

- **Empirical 評価**: 重要度が高い、変更が大きい、頻繁に使う、または実際の失敗を再現したい対象で、適用場面の境界を定義できる場合に選ぶ。新規サブエージェントによる後述のワークフローを実行する。
- **静的審査モード**: 重要度が低い小変更、全域に適用される文書、または短時間で記述の整合性と明瞭性だけを確認したい場合に選ぶ。サブエージェントを起動できる環境でも意図的に選んでよい。
  完了報告に「静的審査であり empirical 評価ではない」と明記し、iteration や収束回数には数えない。

## 実行者の起動

実行者は評価対象の指示を実際に読んで動く立場なので、その指示の利用者に当たる役割（`subagent-delegation`）で起動する。
レビュアーの役割（「標準レビュー」）に固定しない。たとえば実装手順の指示なら「実装」、レビュー手順の指示なら「標準レビュー」にする。

- **Claude Code**: `Agent`（`subagent_type` に役割名を指定）。usage meta から `tool_uses` と `duration_ms` が取れる。
- **OpenAI Codex**: `spawn_agent`（該当する TOML がなければ汎用エージェント）。標準化されたメトリクスは返らない。
- **Antigravity (Gemini)**: `invoke_subagent`。親に返るのはテキストメッセージのみで、メトリクスは返らない。

### メトリクス階層化の原則

- **全環境共通のコア指標**: 「成功/失敗（`[critical]` 全達成）」「精度 %」「質的不明瞭点（新出 0 件）」「裁量補完」「再試行回数（自己申告）」。どの環境でもこれらを主として評価する。
- **環境固有の定量指標**: `tool_uses`（ステップ数）と `duration_ms` が取れる環境（Claude Code）では、シナリオ間の偏り検知と、収束判定の変動率（steps ±10%、duration ±15%）の算出に使う。
  取れない環境（Codex / Gemini）では、これらの値を推測で埋めず、評価表・収束条件から除外し、自己申告の再試行回数と精度・不明瞭点を基準にする。

## ワークフロー

0. **Iteration 0 — description と body の整合チェック**（静的、dispatch 不要）
   - frontmatter `description` が謳う trigger / 用途と、body がカバーする範囲を読み比べる。
   - 乖離があれば iter 1 に進む前に description か body を合わせる。例: description に「navigation / form filling / data extraction」とあるが、body は `npx playwright test` の CLI ref のみ。
   - この確認を飛ばすと、subagent が description に合わせて body を「再解釈」し、skill が要件を満たしていないのに精度が出る（false positive）。

1. **ベースライン準備**: 対象プロンプトを確定し、次を用意する。
   - **評価シナリオ** 2 〜 3 種（中央値 1 + edge 1 〜 2）。楽すぎず難しすぎないものにする（どちらに寄ってもシグナルが出ない）。現実に起こりうるタスクで、対象プロンプトを実際に適用する場面を想定する。
   - **要件チェックリスト**（精度算出のため）。シナリオごとに「成果物が満たすべき要件」を 3 〜 7 項目で列挙する。精度 % = 満たした項目数 / 全項目数。事前に固定する（後から動かさない）。
   - **hold-out シナリオ 1 件**: 未使用の検証用シナリオとそのチェックリストもこの時点で確定し、収束判定まで実行者に渡さない。
   - チェックリストには `[critical]` タグ付き項目を **最低 1 つ** 含める（0 件だと成功判定が vacuous になる）。事後に付け外ししない。

2. **バイアス排除読み**: 指示を「白紙」の実行者に読ませる。「実行者の起動」に従い **新規 subagent を dispatch** する。自己再読で済ませない（直前に書いた文章を客観視することは構造的に不可能）。
   複数シナリオは単一メッセージまたは配列指定で並列に起動する。dispatch 不能環境の扱いは「環境制約」節を参照。

3. **実行**: 実行者を起動する前に `<この skill のディレクトリ>/references/templates.md` を読み、その「subagent 起動契約」に従った依頼文でシナリオを実行させる。
   依頼文には対象プロンプトの全文か読み取れるパス、シナリオ、要件チェックリストをそのまま渡し、依頼する側の解釈や期待する答えを足さない。
   実行者は成果物を生成し、最後に自己申告レポートを返す。

4. **両面評価**: 戻ってきた結果から次を記録する。
   - **実行者の自己申告**: 不明瞭点 / 裁量補完 / テンプレ適用で詰まった箇所。
   - **Trace 解釈**: 各不明瞭点に、発生したフェーズタグ（Understanding / Planning / Execution / Formatting）を付ける。
     フェーズ局所的な修正の方が、全体的に「指示が不明瞭だった」と片付ける修正より、不明瞭点を解消しやすい。Understanding フェーズの 1 つの曖昧さが、Execution フェーズの連鎖的な失敗として表面化することが多い。
   - **構造化された振り返り**: 各不明瞭点を `Issue / Cause / General Fix Rule` の 3 点で返させる。
     `General Fix Rule` は失敗パターン台帳に供給するクラスレベルの抽象化で、これが無いと修正がその場限りのパッチに留まり、同じ誤りを後で再発見する。
   - **指示側の計測**:
     - 成功/失敗: `[critical]` 要件が **全て ○** のときのみ成功（○）。1 つでも × または部分的なら失敗（×）。ラベルは ○ / × の 2 値のみ。
     - 精度: チェックリストの達成率 %。○ = 満点、× = 0、部分的 = 0.5 で合算し、全項目数で割る。
     - 再試行回数: subagent が同じ判断をやり直した回数（自己申告から抽出）。
     - 定量メトリクス（取得可能環境のみ）: ステップ数（`tool_uses` をそのまま使い、Read / Grep も除外しない）、所要時間（`duration_ms`）。
     - **失敗時は、どの `[critical]` 項目が落ちたかを提示フォーマットの「構造化された振り返り」に 1 行添える**（原因追跡のため）。

5. **差分適用**: 不明瞭点を解消する最小修正をプロンプトに入れる。1 イテレーション 1 テーマ（関連する複数修正は OK、無関係な修正は次回に回す）。
   - **修正前に「この修正が要件チェックリスト / 判定文言のどの項目を満たすか」を明示する**。軸名から推測した修正は判定文言を満たさないことが多く、閾値文言レベルで紐付けないと見積もりが外れる。
     評価軸を新設するときも、各点の判定基準を閾値文言レベルまで具体化する。
   - **まず失敗パターン台帳を参照する**。`General Fix Rule` が既存エントリと一致するなら、最初に問うべきは「既存の修正はなぜ再発を防げなかったのか」。
     新しいエントリを足す前に、修正の位置をプロンプト冒頭寄りに移す、あるいは文言を書き直す必要があるかもしれない。
   - **記録と提示**: ワークフロー 4 の記録に台帳の更新と次の修正案を加え、`<この skill のディレクトリ>/references/templates.md` の「提示フォーマット」でイテレーションごとにユーザーに示す。

6. **再評価**: 新しい subagent で再度 2 → 5 を回す（同一 agent は再利用しない: 前回の改善を学習している）。並列度は、イテレーションを進めても改善が頭打ちにならない場合に増やす。

7. **収束判定**:
   - ベースラインを iteration 1 とし、iteration 2 以降は各シナリオを直前の iteration と比較する。
   - **収束（停止）条件**:
     - 新規不明瞭点: 0 件
     - 精度の悪化がなく、前回比改善が 0 〜 3 ポイント以下（飽和状態）
     - （取得可能環境のみ）ステップ数変動が ±10% 以内、duration 変動が ±15% 以内
     - 上記が **2 回連続** 成立したら収束（重要度が高いプロンプトは 3 連続）。最短の収束は iteration 3。
   - **過適合チェック**: 収束判定時に、ベースライン準備で確定した hold-out シナリオを実行する。精度が直近 2 iteration の平均から 15 ポイント以上落ちたら過適合で、ベースラインシナリオ設計に戻って edge を足す。
   - **発散（設計を疑う）**: 3 回以上イテレーションしても新規不明瞭点が減らない場合は、設計方針自体が間違っている可能性がある。パッチで直すのをやめ、構造を書き直す。
   - **停滞**: 頭打ちに近いのに収束基準を満たさないときは、局所最適を疑い、`<この skill のディレクトリ>/references/variant-exploration.md` を読んで 2 バリアントを比較する（任意）。
   - **リソース打ち切り**: 重要度と改善コストが釣り合わなくなったら止める（80 点で出す判断）。

## 評価軸

| 軸 | 取り方 | 意味 | 必須環境 |
|---|---|---|---|
| 成功/失敗 | `[critical]` 要件が全て ○ か（二値。判定は「ワークフロー 4. 両面評価」節に定義） | 最低ライン | 全エージェント |
| 精度 | 成果物が要件を何 % 満たしたか | 部分成功の程度 | 全エージェント |
| 再試行回数 | 同じ判断を何度やり直したか | 指示の曖昧さのシグナル | 全エージェント（自己申告） |
| 不明瞭点（自己申告） | 実行者が箇条書きで列挙 | 質的な改善材料 | 全エージェント |
| 裁量補完箇所（自己申告） | 指示で決まっていなかった判断 | 暗黙の仕様の洗い出し | 全エージェント |
| ステップ数 | ツール呼び出し / 判断ステップ数 | 指示の無駄遣いの指標 | Claude Code のみ |
| 所要時間 | 実行者の duration_ms | 認知負荷の代替指標 | Claude Code のみ |

**重み付け**: 質的（不明瞭点・裁量補完）を主、量的（精度・ステップ数・時間）を補助とする。時間短縮だけを指標にすると、必要な説明が削られる。

### `tool_uses` の質的解釈

`tool_uses` が取れる環境では、シナリオ間の相対値が構造的欠陥の手がかりになる。
他シナリオ比 **3 〜 5 倍以上** のシナリオがあれば、skill が decision-tree index 寄りで自己完結性が低く、実行者が references descent を強いられているサインである。
典型例は、全シナリオが 1 〜 3 なのに 1 シナリオだけ 15 以上で、そのシナリオ用の recipe が skill 内に無く references/ を横断探索している場合。
iter 2 で「最小完成例 inline」や「いつ references を読むかの指針」を SKILL.md 冒頭に足して対処する。
精度 100% でも偏りがあれば iter 2 の根拠になる。精度だけで打ち切ると構造的欠陥を見逃しやすい。

### 修正効果の見積もり

修正の効果は線形ではない。見積もりは次の 3 通りに外れうる。

- **保守的に振れる**（見積もり > 実測）: 複数軸を狙った修正は、見積もりを外しやすい。
- **上振れ**（見積もり < 実測）: コマンド + 設定 + 期待出力のような情報の組合せが、複数軸の判定文言を同時に満たしうる。
- **ゼロ振れ**（見積もり > 0、実測 = 0）: 軸名と判定文言は別物で、軸名から推測した修正はどの判定文言も満たさないことがある。

## 環境制約

新規 subagent を dispatch できない環境（既に subagent として動作している、ツールが無効化されている等）では、本 skill の empirical 評価は **適用しない**。

- 代替案 1: 親セッションのユーザーに別セッションを起動して依頼してもらう
- 代替案 2: 評価を諦め、ユーザーに「empirical evaluation skipped: dispatch unavailable」と明示報告する
- 代替案 3: 依頼の範囲内であれば **静的審査モード** へ切り替え、empirical 評価ではないことを完了報告に明記する
- **NG**: 自己再読で代替する（バイアスが入るので評価結果は信用できない）

## 失敗パターン台帳

対象プロンプト単位で、イテレーション横断の失敗モードを累積的に記録する（empirical-prompt-tuning 全体のグローバル台帳ではない）。エントリの書式は `<この skill のディレクトリ>/references/templates.md` にある。

- ワークフロー 5 で修正を生成する前に台帳をスキャンする。現在の `General Fix Rule` が既存エントリと一致するなら、`Seen in` を更新し、新エントリを足す前に「既存の修正はなぜ再発を防げなかったか」を調査する。
- 的を絞った修正にもかかわらず 3 回以上再発するパターンは構造的シグナルで、パッチを続けず「発散」基準にエスカレートする。

## Red flags（合理化に注意）

| 出てくる合理化 | 実態 |
|---|---|
| 「自分で読み直せば同じ効果がある」 | 直前に書いた文章を客観視はできない。必ず新規 subagent を dispatch する。 |
| 「1 シナリオで充分」 | 1 シナリオは過適合する。中央値 1 + edge 1〜2 の最低 2 本。 |
| 「不明瞭点ゼロが 1 回出たから終わり」 | 偶然なこともある。連続 2 回と hold-out で確定判定する。 |
| 「複数の不明瞭点を一気に潰そう」 | どの修正で改善したか分からなくなる。1 イテレーション 1 テーマ。 |
| 「関連する微修正も純粋に 1 件ずつ別 iter に分けよう」 | "1 テーマ" は意味単位。関連する 2〜3 件の微修正は 1 iter にまとめて良い。 |
| 「メトリクスが良いから質的フィードバックは無視」 | 時間短縮は、必要な説明が削られたサインにもなる。質的評価を主とする。 |
| 「書き直した方が早い」 | 3 回以上不明瞭点が減らないなら正解。それ以前の段階では、反復を避ける口実にすぎない。 |
| 「同じ subagent を使い回そう」 | 前回の改善を学習している。毎回新規に dispatch する。 |
| 「シナリオを簡単にすれば不明瞭点が消える」 | シナリオを簡単にすると、指示の不明瞭さが残ったまま不明瞭点だけが報告されなくなる。現実の中央値と edge を用意する。 |
