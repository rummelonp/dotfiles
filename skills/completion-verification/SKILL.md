# 検証チェックリスト

完了を宣言する前の自己検証ゲート。独立レビュアーによる出荷可否判定（別のペルソナが
査読するリリースゲート）ではない。判定は 2 値（完了 / 要修正）のみで、SHIP /
SHIP WITH FIXES / DO NOT SHIP のような多値判定は使わない。

## Iron Law

```
証拠なしに完了を宣言しない
```

このメッセージの中で検証コマンドを実行していなければ、通過したと主張できない。

## ゲート手順

```
完了、修正、成功を宣言する前に:

1. 特定: この主張を証明するコマンド/確認手段は何か
2. 実行: そのコマンドを今このメッセージの中で完全に実行する（過去の実行結果の流用は不可）
3. 確認: 出力全体を読み、終了コードや失敗件数を確認する
4. 判定: 出力は主張を裏付けるか
   - 裏付けない → 証拠付きで実際の状態を述べる（要修正）
   - 裏付ける → 証拠付きで主張する（完了）
5. 横展開チェック（必須）: 今回直した/実装した問題と同種の問題が、他のファイルや
   他の箇所にも存在しないかを確認する。1 箇所だけ直して終わらせない。
6. ここまで終えて初めて完了を宣言する
```

完了を宣言する前に満たすべき基準は次の通り:

- コードを変更した場合: 差分、テスト、ログのうち、リスクに見合う証拠を確認する。
- コードを変更しない調査や監査の場合: 結論の根拠をファイル:行で示すことが証拠になる。
- テストやログの実行を求められていなければ、新たに実行しない（既存の証拠で足りるか判断する）。
- 自分が詳しくない技術については、公式ドキュメント、実装、型定義を実際に確認してから
  主張する。

## よくある言い訳とその却下

| 言い訳 | 実際 |
|---|---|
| 「たぶん動く」 | 検証コマンドを実行する |
| 「自信がある」 | 自信は証拠ではない |
| 「今回だけは」 | 例外は無い |
| 「lint は通った」 | lint はコンパイルや実行結果の代わりにならない |
| 「サブエージェントが成功したと報告した」 | 独立して検証する。VCS の diff を見る |
| 「一部だけ確認した」 | 部分的な確認は何も証明しない |
| 「時間が無い」 | systematic な検証の方が手戻りより速い |
| 「今回は同種の問題は無いはず」 | 横展開チェックを飛ばさない。同じ漏れが複数箇所で独立発生することは珍しくない |

## Red Flags（立ち止まる兆候）

- 「〜のはず」「たぶん」「〜と思う」という言葉を使っている
- 検証前に満足の表現（「よし」「完璧」「できた」）をしている
- 検証せずに commit / push / PR 作成をしようとしている
- サブエージェントの成功報告をそのまま信じている
- 横展開チェックを省略しようとしている

これらに気づいたら、証拠を取ってから続ける。

## スコープの境界

この skill は自分の完了宣言前の自己チェックであり、独立レビュアー用のサブエージェント
ペルソナ定義（コードレビュー担当の agent persona ファイル等）とは別物。独立レビューが
必要な場合は `risk-based-review` skill（git diff range を渡して読み取り専用の
レビュアー subagent を dispatch し、Strengths/Issues/Recommendations/Assessment 形式で
結果を受け取る手順）を使う。
