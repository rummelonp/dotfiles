# 検証チェックリスト

タスク完了を宣言する前の自己検証ゲート。
独立レビュアーによる出荷可否判定（リリースゲート）ではなく、作業者自身による検証手順を定める。判定は「完了」または「要修正」の 2 値のみとし、SHIP / SHIP WITH FIXES / DO NOT SHIP 等の多値判定は用いない。

## Iron Law

```
証拠なしに完了を宣言しない
```

現在のセッション・メッセージ内で検証コマンドを実行し結果を確認していなければ、検証を通過したと主張してはならない。

## ゲート手順

完了、修正、成功を宣言する前のチェック手順:

1. **特定**: 主張を客観的に証明するコマンドや確認手段を特定する。
2. **実行**: そのコマンドを今この場で実行する（過去の実行結果の流用は不可）。
3. **確認**: 出力全体を精読し、終了コードや失敗件数を確認する。
4. **判定**: 実行結果が主張を裏付けているか判定する。
   - 裏付けない場合: 証拠を添えて現状を報告する（判定: 要修正）。
   - 裏付ける場合: 証拠を添えて主張する（判定: 完了）。
5. **横展開チェック（必須）**: 修正・実装した問題と同種の問題が、他ファイルや別箇所に潜在していないか確認する（1 箇所だけ直して満足しない）。
6. 上記をすべて経て初めて完了を宣言する。

完了を宣言する前に満たすべき基準:

- **コード変更時**: 差分・テスト結果・ログのうち、リスクに見合う証拠を確認する。
- **調査・監査時**: 結論の根拠を `ファイル:行` で提示する（指示がない限り不要なテストやログ実行はしない）。
- **未知の技術**: 公式ドキュメント、実装コード、型定義を実際に確認してから回答・主張する。

## よくある言い訳とその却下

| 言い訳 | 実際 |
|---|---|
| 「たぶん動く」 | 検証コマンドを実行して確かめる |
| 「自信がある」 | 主観的な自信は客観的証拠にならない |
| 「今回だけは」 | いかなる例外も認めない |
| 「lint は通った」 | lint の通過はコンパイル成功や実行時挙動の保証にならない |
| 「サブエージェントが成功と報告した」 | 鵜呑みにせず VCS の diff や成果物を独立検証する |
| 「一部だけ確認した」 | 部分的な確認は全体の動作を証明しない |
| 「時間がない」 | 手戻りの修正コストに比べれば検証の方が圧倒的に速い |
| 「今回は同種の問題はないはず」 | 横展開チェックを省略しない。同一の考慮漏れが複数箇所で独立発生することは珍しくない |

## Red Flags（立ち止まる兆候）

- 「〜のはず」「たぶん」「〜と思う」などの推測表現を使用している
- 検証前に「できた」「完璧」などの安堵・満足の表現を使っている
- 検証を経ずに commit / push / PR 作成を行おうとしている
- サブエージェントの成功報告を検証なしに信じ込んでいる
- 横展開チェックを省略しようとしている

これらの兆候に気付いた場合は、直ちに立ち止まり、客観的証拠を採取してから作業を再開する。

## スコープの境界

本スキルは作業完了前の自己検証手順であり、独立レビュー（外部視点による客観審査）とは明確に分離する。独立レビューが必要な場合は `risk-based-review` スキルを使用する。
