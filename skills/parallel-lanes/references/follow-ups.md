# follow-up を候補にする

`parallel-lanes` skill の 1 で、follow-up を候補にする条件のどれかに当たったときに読む。
節の番号（0〜7）は SKILL.md の節を指す。

follow-up かどうかは種別（5 で付ける改善候補）で見分け、記録には頼らない（記録は 6 で消え、次の実行に残らないため）。

## ID か条件で選んだ follow-up

ユーザーが ID か条件（「手間が小さいもの」「デスクトップの主要な場面で踏むもの」など）で選んだ follow-up は、元の範囲の項目として候補にし、`backlog` skill のとおり種別を実装に変える。
変えるのは、その項目の状態を更新するときに合わせる（起動の前に変えると、追跡する文書ではレーンと別のコミットが要るため）。
issue のバックログでは種別のラベルを変えない（閉じた issue は `ready` に出ず、ラベルの書き込みは 0 で得る承認の範囲にないため）。
起動の時点では行が元のままなので、レーンへの依頼に、ユーザーが着手すると決めたことを書く。
条件で選んだときは、各項目の `### <ID>` 節の場面と手間の目安で当てはまるかを決め、当てはまった ID と、節に材料がなく決められなかった ID を記録の「判断と理由」に書く。
決められなかった項目は候補にしない（推測で範囲を広げないため）。
条件で選ぶ対象は依頼の時点で表にある項目とし、実行中に足した follow-up は、条件に合っても条件では選ばない（受け入れのたびに範囲が広がるため）。

## 不在の告知、範囲の明示、repo の宣言で含める follow-up

SKILL.md の 1 に挙げた条件のうち、次のどれかに当たる実行では、`ready` にある改善候補の項目も候補にする。

- ユーザーが不在を告げ（「寝る」「起きるまで」など）、その間に進めるよう頼んだ
- ユーザーが、ID や条件で絞らずに、follow-up も範囲に含めると明示した（絞った依頼は、上のとおり元の範囲の項目にする）
- repo の宣言が、follow-up を候補に含めると定めている

上の 3 つのどれかで候補にした follow-up は、空きがあり、元の範囲の項目に起動できるものがないときだけ、`ready` の順に引く。
種別は実装に書き換えない（実行が途中で切れると、実装のまま次の実行の候補に入るため）。
上の 3 つのどれかに当たる実行では、元の範囲のレーンがその実行中に足した follow-up も、同じ引き方で候補にする。
ID か条件で選んだ項目のレーンも、元の範囲のレーンとして数える。
上の 3 つのどれかで候補にした follow-up のレーンがこの実行で足した follow-up は、ID を記録の「判断と理由」に書き、この実行の候補にしない（1 回の実行の中で連鎖を 1 世代に止めるため）。
