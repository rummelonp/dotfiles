# 再開

`parallel-lanes` skill の 0 の「実行の記録」と「再開」で、前の実行の記録、対象のブランチ、進行中の項目のどれかが残っているときに読む。
節の番号（0〜7）は SKILL.md の節を指す。

## 記録を引き継ぐ

前の実行の記録が残っていれば、新しく作らずに最も新しい記録（`<実行名>` の日付で決める）を引き継ぐ。
記録が複数残っていれば、引き継がない記録の項目とブランチも再開の対象と持ち主の確かめに含め、6 で引き継いだ記録と一緒に消す（マージを待つ PR が残る記録は残す）。
引き継がない記録の項目の結果（5 を終えたことを含む）はその記録に書き、レーンを起動し直す項目は引き継いだ記録に移して元の記録から消す（同じブランチが 2 つの記録に載らないようにするため）。
記録が複数あれば、各記録の項目はその記録の「worktree とブランチ」にあるブランチとだけ結び付ける（バックログがない実行どうしでは、ID が重なることがあるため）。
バックログがなければ、引き継がない記録の項目の状態はその記録の表で更新し、未着手の項目は開始時の確認に載せる（1 の候補は、この実行の記録からだけ引くため）。

## 残りを分ける

記録にあるブランチが消えていれば、取り込み済みかを、記録の「受け入れ結果」と、PR で取り込む repo では `gh pr list --state merged --head <ブランチ>` で確かめる。
squash や fast-forward で取り込むと、基準ブランチの履歴にブランチ名が残らないためである。
取り込み済みで、記録の「受け入れ結果」に 5 を終えたと書いていない項目は、下の表の 1 行目と同じく扱う（状態が未更新だと `ready` に残り、同じ項目のレーンを再び起動するため）。
書いてあれば何もしない（5 を繰り返すと、follow-up を二重に足すため）。
取り込み済みと分からなければ、その項目を起動し直すかを開始時の確認で尋ねる。
ここでは分けるだけにし、分けた結果は開始時の確認で示して、確認の後でそれぞれの節に進む。
ただし、追跡しないファイルやメモリのバックログと 1 の表の状態は、確認を待たずにここで更新してから 1 に進む（更新しないと、後続の項目が候補に出ないため）。
確認の後で起動する続きのレーンと、4 に回して受け入れを終えていないブランチは、2 の同時に動かす数に含める（3 の数え方と同じ）。
記録にあるブランチ（続きのレーン、マージ待ちの PR、4 に回すもの）の「触るファイルの見積もり」は、2 の前に見積もり直す（前の実行の後で、基準ブランチやレーンの作業が進んでいることがあるため）。
見積もりの材料は、ブランチの差分（`git diff --name-only <基準ブランチ>...<ブランチ>`）、worktree の未コミットの変更（`git status --porcelain`）、残りの作業である。
まだ起動していない項目は、基準ブランチの今の先端から見積もり直す。
次の表を上の行から順に当て、最初に当たった行に進む。

| 残りの状態 | 確認の後に進む先 |
|---|---|
| ブランチで作ったコミットが基準ブランチに入った（マージ済みの PR を含む） | 5。追跡する文書のバックログで状態が未更新なら、4 の 10 のとおり完了にする（PR で取り込んだ項目は、`pull-requests.md` の「4. 受け入れる」のとおりまとめて） |
| 未コミットの変更がある（コミットと開いた PR の有無を問わない） | 同じ worktree とブランチで続きを頼むレーンを起動する。開いた PR があれば、マージ待ちとしても数える |
| 開いた PR がある | マージ待ちとして扱い、3 の重なりの判定に数える |
| 基準ブランチにないコミットがある | 4 で受け入れる。完了の条件を満たしていなければ、同じブランチで続きを頼むレーンを起動する |
| ブランチを作ってからのコミットがない | 7 の規則で worktree とブランチを消す。項目の状態は変えず、進行中のまま残る項目は、未着手に戻すかを開始時の確認で尋ねる。戻したら、確認の後で 1 から引き直す |

1 行目の「基準ブランチに入った」かは、squash でマージした PR なら `gh pr list --state merged` で見分ける。ローカルで取り込んだものなら、`git reflog <ブランチ>` に commit、merge、rebase の行があるかで、作っただけのブランチと見分ける。
reflog が残っておらず、1 行目と最後の行を見分けられなければ、開始時の確認で尋ねる。
4 行目ではレーンの報告がないので、4 の 2 はレーンの種類によらず行い、作成に使った役割が記録になければ上位実装として扱う。4 の 7 のレビューの証跡は、4 の 2 で統括が決めたレビューで代える。
最後の行で進行中のまま残るのは、issue の担当者など、この skill の外で変わった項目である。未着手に戻すかを尋ねるのは、戻さないと `ready` に出ないためである。
