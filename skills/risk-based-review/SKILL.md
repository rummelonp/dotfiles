# リスクに応じたレビュー依頼

サブエージェント（Task/Agent 相当のツール）を持たない環境ではこの skill は適用しない。

## レビューを依頼するかどうかの判定

毎タスク後に必ずレビューする、という前提は採らない。以下の 4 段階で決める。
複数の段階に当たるときは高い方を採る。着手前は分かっている範囲で分類し、調査の途中で
migration 等が判明したら分類を上げる。

| リスク | 例（コード / 文章） | 独立レビュー | レビュアー | 再レビューの上限 |
|---|---|---|---|---|
| 軽微 | 文言、CSS、明白な小修正 / 誤字、言い換え | 依頼しない。自分で確認する | — | — |
| 通常 | 一般的な feature、refactor、test / 記事 1 本、章の部分改稿 | 誤りがすぐ捕まらなければ 1 本 | Opus | 0 回 |
| 高リスク | DB schema、migration、認証と認可、データ整合性 / 他が依存する章の構成変更 | 1 本 | Fable | 1 回 |
| 非常に高リスク | データ損失、race condition、security boundary / 撤回できない公開物 | 観点を分けて 2 本 | Fable 2 本 | 2 回 |

判定軸: 誤りが機械的な検査やひと目で捕まるか（test、型、lint、通読）、戻せるか（可逆性）、
他の箇所に波及するか。分類を決めるのは例ではなく判定軸のほうで、例はどちらの欄も目安。

レビュアーの段は、表の段と「作った側の一段上」の高いほうを採る。作った側が人間でも、
メイン自身でも、委譲したサブエージェントでも、表の段は動かない。同じ段のレビューは、
作ったときの誤った前提をそのまま引き継ぐので、一段上げるほうを優先する。
「非常に高リスク」の 2 本は観点（正しさ / 設計と可逆性）で分ける。
Fable が作ったものは一段上が無いので、同じ Fable の新規サブエージェントに観点を分けて
依頼する。段は据え置きでも、新しいコンテキストであることは崩さない。
段の判定に要るので、委譲する時点でどのモデルに作らせたかを記録する。記録先は
プロジェクトの慣習に従う（plan doc、コミット trailer、decisions-log など）。

実装時のコンテキストを引き継ぐ自己レビューは常に行う。そのうえで、上記の表に従って
独立レビューの強度を変える。独立レビューは、その設計や実装に関わっていない新規の
サブエージェントに、新しいコンテキストで行わせる（自分で再読することを独立レビューの
代用にしない）。新規サブエージェントを起動できない環境では、独立レビューや bias-free
評価と称さず、代わりに構造的な自己審査に切り替える。

「簡単だから」を理由に軽微でない変更のレビューを省略しない。トークンを節約する目的で
省略するのも同じく認めない。独立レビュー 1 本は実装 1 本より小さく、省いても総消費は
ほとんど動かない。抑えるべきは初回のレビューではなく、下の「再レビュー」の繰り返しのほう。

## 依頼手順

1. **diff range を決める**:
初回は作業全体を見せる。再レビューは下の「再レビュー」に従い修正コミットだけに絞る。

```bash
HEAD_SHA=$(git rev-parse HEAD)
BASE_SHA=$(git merge-base origin/HEAD HEAD)  # 初回。起点は repo の既定ブランチ
```

2. **レビュアーをディスパッチする**: 新規サブエージェントに以下を渡す。
   - 何を作ったか（DESCRIPTION）
   - 期待する要件や元になった plan（PLAN_OR_REQUIREMENTS）
   - BASE_SHA / HEAD_SHA
   - モデルは作った側の一段上を明示的に指定する
   - 差分が全面的に書き換わる成果物（章構成の入れ替えなど）は、diff だけでなく HEAD の
     全文も読ませる。diff では論の通りを判定できない
   - レビュアーは read-only（コードを変更しない）
   - レビュアーは自分自身が更にサブエージェントを起動しない
   - 返却フォーマット: Strengths / Issues / Recommendations / Assessment
   - Issues は blocking と non-blocking に分け、両者を通した番号を振らせる。再レビューで
     その番号をそのまま参照する

3. **結果に対応する**:
   - Critical/Important な指摘はすぐに直す
   - Minor な指摘は後回しでよいが記録する
   - レビュアーが誤っていると判断したら、根拠（コードやテスト結果）を示して押し返す

## 再レビュー

指摘を直したコミットをもう一度レビューに掛けるときは、初回と同じ依頼をしない。
初回と同じ依頼をすると、レビュアーは差分ではなく実装全体を読み直し、毎回新しい
non-blocking を掘り当てて終わらなくなる。

再レビューは次の形に固定する。

- **diff range は修正コミットだけ**にする。BASE_SHA は前回のレビュアーが見た HEAD。
  実装全体を渡さない。
- **前回の指摘一覧を必ず添える**。直した分だけでなく、前回挙がった全件を状態つきで渡す。
  判定させるのは 2 点だけ。
  1. 挙がっていた指摘それぞれが直っているか（直っていないものは番号で挙げさせる）
  2. その修正が新たに blocking を作っていないか
- **新しい non-blocking を探しに行かせない。** この 1 文を依頼文に明記する。修正の範囲外で
  気づいた点は「follow-up 候補」として 1 行だけ挙げさせ、そのラウンドの判定には含めない。
- **ラウンド数は上表の上限まで**（上限値は暫定、運用しながら見直す）。上限に達しても
  non-blocking が残っているときは、残りを follow-up として記録（plan doc、issue、
  decisions-log のいずれか）したうえで受け入れる。記録せずに受け入れるのは握り潰しで、
  follow-up 記録とは別物になる。必ず記録を残す。
- **上限に達しても blocking が残るときは受け入れない。** 上限は non-blocking を打ち切る
  ためのもので、blocking を通すためのものではない。ユーザーに報告して判断を仰ぐ。分類を
  上げてラウンド数を稼ぐ抜け道にはしない（分類を上げても消費済みの回数は戻らない）。
- **再レビューは初回と同じ段のモデルにする。** 上限に達していないのに段を上げて回数を
  稼がない。2 本出していた場合、再投入するのは指摘を出したレビュアーの観点だけでよい。

## Red Flags

- 「簡単だから」で軽微でない変更のレビューを省く
- Critical な指摘を無視する
- Important な指摘を未修正のまま進める
- 妥当な技術的指摘に理由なく反論する
- 再レビューに実装全体の diff を渡し、新しい non-blocking を集めて次のラウンドを回す
- トークン節約を理由に初回の独立レビューを省く
- 上限に達したことを理由に、blocking を残したまま受け入れる

## スコープの境界

この skill はレビュー依頼の手順であり、完了前の自己検証とは別物で 1 ファイルに
統合しない。完了前の自己検証は `completion-verification` skill（完了を宣言する直前に
検証コマンドを実行し直し、出力と終了コードを確認する自己チェックゲート）を使う。
