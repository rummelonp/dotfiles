# リスクに応じたレビュー依頼

変更のリスクに応じて独立レビューの要否と強度を決め、レビュアーに依頼する。

## 用語

- **自己レビュー**：作った本人が、作成時のコンテキストのまま見直すこと。
- **独立レビュー**：作成に関わっていない新規サブエージェントが、新しいコンテキストで行うレビュー。コードと文章のほか、skill や prompt の変更も対象とする。
- **観点別の自己点検**：サブエージェント（Task / Agent / Subagent 相当のツール）を起動できない環境で、独立レビューの代わりに、観点 A / B ごとに自分で点検すること。独立レビューとは称さない。
  手順は `<この skill のディレクトリ>/references/self-check.md` に従う。
- **開始時の HEAD**：ファイルを変更する作業に着手したときの HEAD。規則ファイル（`CLAUDE.md` / `AGENTS.md` / `GEMINI.md`）の指示で、着手時に記録する。
  記録がなく、ブランチ全体が今回の作業なら `git merge-base HEAD origin/<base>` で代える。
  どちらでもなければ、範囲をユーザーに確かめる。
- **作成側**：レビュー対象を作った主体（人間、メインセッション、サブエージェント）。
- **依頼者**：レビューを依頼し、指摘への対応と範囲外の論点の扱いを決める主体。
- **blocking / non-blocking**：レビュアーが付ける指摘の分類。blocking は受け入れる前に直す指摘、non-blocking は記録して後回しにしてよい指摘。

## レビューを依頼するかどうかの判定

毎タスク後に一律でレビューを行う前提は採らない。以下の 4 つのリスク分類で要否と強度を判断する。
- 複数の分類に該当する場合は高い方を採用する。
- 着手前は判明している範囲で分類し、作業途中でマイグレーション等の存在が判明した場合は分類を引き上げる。

| リスク | 例（コード / 文章） | 独立レビュー | レビュアー強度 | 再レビューの上限 |
|---|---|---|---|---|
| 軽微 | 文言、CSS、明白な小修正 / 誤字、言い換え | 依頼しない（自分で確認する） | — | — |
| 通常 | 一般的な feature、refactor、test / 記事 1 本、章の部分改稿 | 誤りがすぐ検知できなければ 1 本 | 標準レビュアー (Standard) | 0 回 |
| 高リスク | DB schema、migration、認証・認可、データ整合性 / 他が依存する章の構成変更 | 1 本（`subagent-delegation` で観点を分けて 2 本にする場合を除く） | 高強度レビュアー (Strong) | 1 回 |
| 非常に高リスク | データ損失、race condition、security boundary / 撤回できない公開物 | 観点を分けて 2 本 | 高強度レビュアー 2 本（観点 A / B） | 2 回 |

判定軸: 誤りが機械的な検査や一読で検知できるか（テスト、型検査、lint、通読）、容易に戻せるか（可逆性）、他箇所へ波及するか。
テストは、変更した振る舞いを確かめているものだけを数える（通っても、確かめていない箇所の誤りは見つからないため）。
そのうち、作成側が同じ作業で足したり期待値を書き換えたりしたテストは数えない（仕様を読み違えていれば、これらのテストは実装と同じ読み違えに沿って書かれ、誤った実装でも通るため）。
型検査と lint は、変更前からあるものを数える。
分類の決定根拠は具体的な例示ではなく判定軸とし、表中の例はあくまで目安とする。
文章では、意味を変えない修正（誤字、表記の統一、同じ意味の言い換え）を軽微とし、主張・規則・手順の内容が 1 文でも変わる修正は通常以上とする。

## レビュアーの選び方

レビュアーの役割とモデルは `subagent-delegation` skill で選ぶ。

- 標準レビュアー (Standard) には「標準レビュー」、高強度レビュアー (Strong) には「高強度レビュー」の役割を使う。作成側が人間・メインセッション・サブエージェントのいずれでも、表の強度は変えない。
- 作成側の一段上の段がこれより高い場合は、そちらを優先する（`subagent-delegation` の選択の原則）。
- 高強度レビュアーには、観点を特化した重点検証の依頼文を渡す。
- 一段上の段がなく同じ段で依頼する場合も、強度はモデルの格上げではなく、新規コンテキストと観点の特化で担保する。

### 観点分割（観点 A / B）の定義

「非常に高リスク」で 2 本依頼する際、`subagent-delegation` の選択の原則で一段上の段がないため 2 本に分ける際、または一段上の段がない環境で多角的に検証する際は、以下の 2 観点に分けて依頼する。

- **観点 A: 正しさ・仕様適合性 (Correctness & Edge Cases)**:
  - 期待される要件や仕様を過不足なく満たしているか。
  - ロジックの正確さ、型・シグネチャ・契約の整合性。
  - エッジケース、境界値、異常系・エラーハンドリングの妥当性。
  - race condition、デッドロック、並行処理の安全性。
- **観点 B: 設計・安全性・可逆性 (Architecture, Safety & Reversibility)**:
  - 既存アーキテクチャや設計方針と整合しているか、過剰設計や責務違反がないか。
  - 他のモジュールや外部システムへの波及影響・後方互換性破壊がないか。
  - 障害や不具合が発生した際にロールバックや切り戻しができるか（可逆性）。
  - セキュリティ境界、権限昇格、意図しない外部書き込み、認証・認可の穴がないか。

## 独立レビューの前提原則

実装時のコンテキストを引き継ぐ自己レビューは常に行う。その上で、上記のリスク分類に従って独立レビューの強度を決定する。
独立レビューを自己レビューで代用しない。新規サブエージェントを起動できない環境では、観点別の自己点検（`references/self-check.md`）に切り替える。

「簡単だから」「トークン節約のため」を理由に、軽微でない変更のレビューを省略することは認めない。
独立レビュー 1 本の消費量は小さく、省略しても全体のトークン消費はほとんど変わらない。抑制すべきは初回のレビューではなく、再レビューの繰り返しである。

## 依頼手順

1. **diff range を決める**:
   初回は今回の作業全体を対象とする。再レビュー時は修正コミットのみに絞る（再レビューの規定は `<この skill のディレクトリ>/references/re-review.md` にある）。
   base の取り込みより前に依頼する（取り込み後は base 側の変更が範囲に混ざる）。

   ```bash
   HEAD_SHA=$(git rev-parse HEAD)
   BASE_SHA=<開始時の HEAD>  # 初回
   ```

2. **レビュアーに依頼する**: 新規サブエージェントに以下を渡す。
   - 作業内容の概要（DESCRIPTION）
   - 期待する要件や元になったプラン（PLAN_OR_REQUIREMENTS）
   - BASE_SHA / HEAD_SHA
   - レビュー観点（通常は総合、2 本に分ける場合は観点 A または観点 B を明示）
   - レビュアーの強度と、`subagent-delegation` で選んだ役割・モデル
   - 差分が全面的に書き換わる成果物（章構成の入れ替えなど）は、diff だけでなく HEAD の全文も読ませる（diff だけでは論旨の整合性を判定できないため）。
   - レビュアーは read-only（コードを変更しない）。
   - レビュアー自身はさらにサブエージェントを起動しない。
   - 返却フォーマット: Strengths / Issues / Recommendations / Assessment
   - Issues は blocking と non-blocking に分類し、通し番号（#1, #2...）を付与させる（再レビューでその番号を参照するため）。
   - Assessment の前に、検討したうえで計画や要件の範囲外として判定を見送った挙動や論点を、理由付きで 1 行ずつ挙げさせる（なければ「なし」と書かせる）。
     範囲外としてよいかをレビュアーだけで確定させず、依頼者が決めるため。

3. **結果に対応する**:
   - blocking の指摘は直ちに修正する。
     - 再レビューの上限が 0 回なら、修正を `completion-verification` で確かめて受け入れる。解消できなければユーザーに報告する。
   - non-blocking の指摘は後回しにしてよいが記録を残す。
     - 記録先の既定は完了報告の次のアクションとし、follow-up として指摘の番号と 1 行の要約を書く。
     - リポジトリに plan doc や decisions-log があれば、そこにも書いてよい。
     - PR 本文や issue への書き込みは外部への書き込みなので、ユーザーから明示的に指示されていなければ承認を得てから行う。
   - 判定を見送った挙動や論点は 1 行ずつ、範囲外のままでよいかを決める。
     - 範囲外のままにしたものは、番号を振らずに完了報告の次のアクションへ 1 行ずつ書く。
     - 範囲内と判断したものは、指摘と同じく blocking か non-blocking に分けて扱う。
       直したものは再レビューで自己発見の修正として一覧に加える。再レビューの上限が 0 回なら、blocking の修正と同じく `completion-verification` で確かめて受け入れる。
   - レビュアーの指摘が誤っていると判断した場合は、客観的根拠（コードやテスト結果）を示して反論する。
   - 再レビューの上限が 1 回以上で、blocking の修正か、意味の変わる自己発見の修正があれば、`<この skill のディレクトリ>/references/re-review.md` に従って再レビューを依頼する。
     観点別の自己点検に切り替えた場合は、再レビューの代わりに `references/self-check.md` の 5 に従う。

## Red Flags

- 「簡単だから」を理由に軽微でない変更のレビューを省く
- blocking の指摘を無視する、または未修正のまま進める
- 妥当な技術的指摘に理由なく反論する
- 再レビューに実装全体の diff を渡し、新しい non-blocking を集めてラウンドを繰り返す
- トークン節約を理由に初回の独立レビューを省く
- 上限到達を理由に、blocking を残したまま受け入れる

## スコープの境界

本 skill は独立レビューの依頼手順であり、完了前の自己検証とは別物として扱う。完了前の自己検証には `completion-verification` skill を使う。
