# 計画のレビュー

実装の前に計画をレビューするときに、`dispatch.md` に加えて読む。

`dispatch.md` の「依頼手順」を次のように読み替える。ここにないことは diff のときと同じにする。

- 範囲：diff range の代わりに計画のファイルのパスを渡す。ファイルがなければ計画の全文を依頼文に入れる。BASE_SHA / HEAD_SHA は渡さない。
- 依頼文：ユーザーの依頼を要約せずに引用し、制約と、計画が触るファイルのパスを添える（要約すると、計画が依頼から外れたことを見抜けないため）。
- 観点：観点 A / B の箇条に加えて、A では要件を満たすか、手順に抜けがないか、検証の方法で誤りが見つかるかを、B では設計、波及、戻しやすさを見させる。
  観点 A / B の箇条は置き換えない（置き換えると、計画に書かれた並行処理やセキュリティ境界の誤りを誰も見ないため）。
- 箇所：Issues の箇所は計画の節と行で書かせる。
- 既存の問題：「差分が持ち込んでいない既存の問題」を「計画が持ち込んでいない既存の問題」と読み替える。
- AI レビュアー向けの指示ファイル：`applyTo` は、計画が触るファイルのパスで当てる。
- 再レビュー：`re-review.md` の形式で依頼し、diff range の代わりに直した節を範囲にする。
  直した節に加えて、指摘ごとに何を変えたかを 1 行ずつ渡す（計画は git で追跡しないことが多く、差分で変更を示せないため）。
- 受け入れ：再レビューの上限が 0 回なら、直した節を読み直し、指摘の場面が残っていないことを確かめて受け入れる（計画には `completion-verification` で動かす対象がないため）。
