# 再レビュー

再レビューの上限が 1 回以上で、blocking の修正か、レビュー後に自分で見つけて直した意味の変わる修正があるとき、再レビューを依頼する前に読む。
リスク分類の表（再レビューの上限）は `SKILL.md` に、「依頼手順」と「結果に対応する」は `dispatch.md` にある。

指摘を修正したコミット、または依頼者や作成側がレビュー後に自分で見つけて直した意味の変わる修正を再レビューにかける際は、初回と同じ依頼を行わない（実装全体を読み直して新たな non-blocking を見つけるループを防ぐ）。
再レビューは以下の形式に固定する。

- **依頼文には「依頼手順」の 2 の項目を初回と同じく含める**。read-only、再委譲の禁止、概要、要件、強度と役割はそのまま引き継ぐ（Antigravity や Claude Code の `general-purpose` での代替では、read-only を依頼文でしか守れない）。
  置き換えるのは、BASE_SHA / HEAD_SHA、2 本に分けた場合の観点、返却フォーマットと Issues の番号付け、判定を見送った論点の列挙だけにし、それぞれ以下の項目に従う。
  概要と要件は要約しない（要約すると blocking の根拠になった制約が落ちる）。plan ファイルがあればそのパスを渡し、初回のあとに要件が変わったときは変わった点を添える。
  HEAD の全文を読ませるかは、修正コミットの差分が全面的な書き換えかで決める。読ませる場合も diff range は修正コミットのままにし、全文は論旨の整合の判定にだけ使わせる。
- **diff range は修正コミットのみ**にする。BASE_SHA は前回のレビュアーが確認した HEAD とし、実装全体を渡さない。
  修正が未コミットなら、`dispatch.md` の手順 1 と同じく作業ツリーとの差と未追跡ファイルを渡す。前回も未コミットで差が実装全体になるときは、修正した箇所の差だけを抜き出して渡す。
- **前回の指摘一覧を必ず添付する**。修正分だけでなく、前回挙がった全件をステータス付きで渡す。
  - 依頼者や作成側がレビュー後に自分で見つけて直した修正は「自己発見の修正」として一覧に加え、前回の番号と区別して S1, S2... を振る。
  - 意図的に対応しなかった non-blocking は、`SKILL.md` の用語でいう follow-up 記録済みに当たるので、一覧に「follow-up 記録済み・判定対象外」と書いて参考に添える。
  - 初回で範囲外のままにした論点（判定を見送り、「結果に対応する」で範囲外のままと決めたもの）は、指摘ではないので一覧にも依頼文にも入れず、完了報告の次のアクションにだけ書く。
  - 判定させる項目は以下の 2 点のみとする。
    1. 前回の blocking が解消されているか（未解消のものは番号で指摘させる）と、自己発見の修正が妥当か。
    2. その修正によって新たな blocking が生じていないか。
  - 前回の blocking が 0 件なら、判定は新たな blocking の有無と自己発見の修正の妥当性だけになる。
- **「新しい non-blocking を探しに行かないこと」を依頼文に明記する**。修正の範囲外で気づいた点は「follow-up 候補」として 1 行のみ挙げさせ、当該ラウンドの判定には含めない（記録先は「結果に対応する」の non-blocking と同じ）。
  初回の依頼にある判定を見送った挙動や論点の列挙も求めず、気づいた点は follow-up 候補に含めさせる。
- **返却フォーマットは初回と同じ**（Strengths / Issues / Recommendations / Assessment）にする。
  Issues には、前回の blocking と自己発見の修正の番号ごとに判定（解消 / 未解消、妥当 / 要修正）を書かせ、新たな blocking には前回の続きの番号を振らせる。
  未解消と要修正は blocking として扱わせる。自己発見の修正そのものの欠陥はその S 番号で要修正とし、新たな blocking として重ねて数えさせない。
  Recommendations は blocking として扱うもの（未解消、要修正、新たな blocking）の直し方に限らせ、follow-up 候補は Assessment の直前に別の見出しを立てて 1 行ずつ挙げさせる。
  Assessment では受け入れてよいかと、残っている blocking の番号（#n と S 番号）だけを答えさせる。上限に達したかの判断とその後の対応は依頼者が行うので、レビュアーには求めない。
- **ラウンド数は表の上限までとする**。上限到達時に non-blocking が残存している場合は、follow-up として記録（記録先は「結果に対応する」の non-blocking と同じ）した上で受け入れる（記録せずに受け入れると指摘の握り潰しになるので不可）。
- **上限到達時であっても blocking が残存している場合は受け入れない**。上限は non-blocking を打ち切るための規定であり、blocking を通過させるためのものではない。
  ユーザーに報告して指示を仰ぐ。分類を引き上げてラウンド数を増やす行為は禁止とする。
- **再レビューは毎回、初回と同じモデル、同じ役割（同じ強度）の新規サブエージェントに、新しいコンテキストで依頼する**。上限に達する前にモデルの段を引き上げたり、途中でモデルを変えて新たな視点を持ち込ませない。
  前回のレビュアーに続けさせない（前回に気づいた non-blocking をまた挙げ、冒頭で防いだ繰り返しに戻る）。前回の指摘の意図を前回のレビュアーに確かめる質問は妨げない。
  2 本出していた場合は、指摘を出した観点（観点 A / B）のみに再投入し、その観点を依頼文に明記する。指摘元がない（自己発見の修正）か不明な場合は、修正の性質に最も近い観点に再投入する。
