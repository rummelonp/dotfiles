# 独立レビューの依頼

独立レビューを依頼するとき、その指摘に対応するとき、再レビューを行うとき、観点別の自己点検に切り替えるときに読む。
リスク分類の表（レビュアー強度と再レビューの上限）と用語は `SKILL.md` にある。

## レビュアーの選び方

`subagent-delegation` skill があれば、レビュアーの段と、上位のモデルがないときに 2 本に分けるかはそちらに従う。ない環境では以下で決める。

- 「段」はモデルの価格の段で（性能の順位は課題で入れ替わり、一通りに決まらないため）、同じモデルは同じ段とする。作成側の段は作成に使ったモデルの段とし、メインセッションが自分で作った場合はそのセッションのモデルとする。
- 「上位のモデル」は作成側の次に価格の高い段のモデルを指し、作成側が人間なら使える中で最も価格の高いモデルを指す。モデルを選べない環境では、上位のモデルはないものとする。
- 「標準レビュー」の役割（標準レビュアー）は総合の観点で、「高強度レビュー」の役割（高強度レビュアー）は観点を特化した重点検証の依頼文で依頼する。
  作成側が人間・メインセッション・サブエージェントのいずれでも、表の強度は変えない。
- どちらの役割も、上位のモデルの新規サブエージェントに依頼する。
- 上位のモデルがない場合（上位のモデルでの起動に失敗した場合を含む）は、作成側と同じ段の新規サブエージェントに依頼し、コンテキストを分けて独立性を保つ。
  強度はモデルの格上げではなく、新規コンテキストと観点の特化で担保する。高リスク以上は 1 本では足りないので、観点 A / B の 2 本に分けて依頼する。

### 観点分割（観点 A / B）の定義

「非常に高リスク」で 2 本依頼する際と、上位のモデルがないために高リスクのレビューを 2 本に分ける際は、以下の 2 観点に分けて依頼する。

- **観点 A: 正しさ・仕様適合性 (Correctness & Edge Cases)**:
  - 期待される要件や仕様を過不足なく満たしているか。
  - ロジックの正確さ、型・シグネチャ・契約の整合性。
  - エッジケース、境界値、異常系・エラーハンドリングの妥当性。
  - race condition、デッドロック、並行処理の安全性。
- **観点 B: 設計・安全性・可逆性 (Architecture, Safety & Reversibility)**:
  - 既存アーキテクチャや設計方針と整合しているか、過剰設計や責務違反がないか。
  - 他のモジュールや外部システムへの波及影響・後方互換性破壊がないか。
  - 障害や不具合が発生した際にロールバックや切り戻しができるか（可逆性）。
  - セキュリティ境界、権限昇格、意図しない外部書き込み、認証・認可の穴がないか。

## 依頼手順

1. **diff range を決める**:
   初回は今回の作業全体を対象とする。再レビュー時は修正コミットのみに絞る（再レビューの規定は `re-review.md` にある）。
   base の取り込みより前に依頼する（取り込み後は base 側の変更が範囲に混ざる）。
   コミットしてよい作業（規則ファイルかユーザーが許している）なら、HEAD_SHA を取る前に今回の作業の変更をコミットする（コミットしないと、再レビューで修正分だけの範囲を取り出せないため）。

   ```bash
   HEAD_SHA=$(git rev-parse HEAD)
   BASE_SHA=<開始時の HEAD>  # 初回
   ```

   それでも範囲に未コミットの変更か未追跡ファイルが残れば（HEAD が BASE_SHA と同じで diff が空になる場合を含む）、`git diff <BASE_SHA>`（作業ツリーとの差）を範囲とする。
   未追跡ファイルは `git ls-files --others --exclude-standard` の一覧を添えて、レビュアーにそれも読ませる。

2. **レビュアーに依頼する**: 新規サブエージェントに以下を渡す。
   - 作業内容の概要（DESCRIPTION）
   - 期待する要件や元になったプラン（PLAN_OR_REQUIREMENTS）
   - BASE_SHA / HEAD_SHA（未コミットの変更か未追跡ファイルがあるときは、手順 1 の作業ツリーとの差と未追跡ファイルの一覧も）
   - レビュー観点（通常は総合、2 本に分ける場合は観点 A または観点 B を明示）
   - レビュアーの強度と役割（標準レビュー / 高強度レビュー）、モデルを指定できる環境ではそのモデル
   - 差分が全面的に書き換わる成果物（章構成の入れ替えなど）は、diff だけでなく HEAD の全文も読ませる（diff だけでは論旨の整合性を判定できないため）。
   - レビュアーは read-only（コードを変更しない）。
   - レビュアー自身はさらにサブエージェントを起動しない。
   - 返却フォーマット: Strengths / Issues / Recommendations / Assessment
   - Issues は blocking と non-blocking に分類し、通し番号（#1, #2...）を付与させる（再レビューでその番号を参照するため）。
   - Assessment の前に、検討したうえで計画や要件の範囲外として判定を見送った挙動や論点を、理由付きで 1 行ずつ挙げさせる（なければ「なし」と書かせる）。
     範囲外としてよいかをレビュアーだけで確定させず、依頼者が決めるため。

3. **結果に対応する**:
   - blocking の指摘は直ちに修正する。
     - 再レビューの上限が 0 回なら、修正を `completion-verification` で確かめて受け入れる。解消できなければユーザーに報告する。
   - non-blocking の指摘は後回しにしてよいが記録を残す。
     - 記録先の既定は完了報告の次のアクションとし、follow-up として指摘の番号と 1 行の要約を書く。
     - リポジトリに plan doc や decisions-log があれば、そこにも書いてよい。
     - PR 本文や issue への書き込みは外部への書き込みなので、ユーザーから明示的に指示されていなければ承認を得てから行う。
   - 判定を見送った挙動や論点は 1 行ずつ、範囲外のままでよいかを決める。
     - 範囲外のままにしたものは、番号を振らずに完了報告の次のアクションへ 1 行ずつ書く。
     - 範囲内と判断したものは、指摘と同じく blocking か non-blocking に分けて扱う。
       直したものは再レビューで自己発見の修正として一覧に加える。再レビューの上限が 0 回なら、blocking の修正と同じく `completion-verification` で確かめて受け入れる。
   - レビュアーの指摘が誤っていると判断した場合は、客観的根拠（コードやテスト結果）を示して反論する。
   - 再レビューの上限が 1 回以上で、blocking の修正か、意味の変わる自己発見の修正があれば、`re-review.md` に従って再レビューを依頼する。
     観点別の自己点検に切り替えた場合は、再レビューの代わりに `self-check.md` の 5 に従う。
