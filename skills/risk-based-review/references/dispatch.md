# 独立レビューの依頼

独立レビューを依頼するとき、その指摘に対応するとき、再レビューを行うとき、観点別の自己点検に切り替えるときに読む。
リスク分類の表（レビュアー強度と再レビューの上限）と用語（観点 A / B の定義を含む）は `SKILL.md` にある。

## レビュアーの選び方

`subagent-delegation` skill があれば、レビュアーの段と、上位のモデルがないときに 2 本に分けるかはそちらに従う。ない環境では以下で決める。

- 「段」はモデルの価格の段で（性能の順位は課題で入れ替わり、一通りに決まらないため）、同じモデルは同じ段とする。作成側の段は作成に使ったモデルの段とし、メインセッションが自分で作った場合はそのセッションのモデルとする。
- 「上位のモデル」は作成側の次に価格の高い段のモデルを指し、作成側が人間なら使える中で最も価格の高いモデルを指す。モデルを選べない環境では、上位のモデルはないものとする。
- 「標準レビュー」の役割（標準レビュアー）は総合の観点で、「高強度レビュー」の役割（高強度レビュアー）は観点を特化した重点検証の依頼文で依頼する。
  作成側が人間・メインセッション・サブエージェントのいずれでも、表の強度は変えない。
- どちらの役割も、上位のモデルの新規サブエージェントに依頼する。
- 上位のモデルがない場合（上位のモデルでの起動に失敗した場合を含む）は、作成側と同じ段の新規サブエージェントに依頼し、コンテキストを分けて独立性を保つ。
  強度はモデルの格上げではなく、新規コンテキストと観点の特化で担保する。高リスク以上は 1 本では足りないので、観点 A / B の 2 本に分けて依頼する。

## 依頼手順

1. **diff range を決める**:
   初回は今回の作業全体を対象とする。再レビュー時は修正コミットのみに絞る（再レビューの規定は `re-review.md` にある）。
   base の取り込みより前に依頼する（取り込み後は base 側の変更が範囲に混ざる）。
   コミットしてよい作業（規則ファイルかユーザーが許している）なら、HEAD_SHA を取る前に今回の作業の変更をコミットする（コミットしないと、再レビューで修正分だけの範囲を取り出せないため）。

   ```bash
   HEAD_SHA=$(git rev-parse HEAD)
   BASE_SHA=<開始時の HEAD>  # 初回
   ```

   それでも範囲に未コミットの変更か未追跡ファイルが残れば（HEAD が BASE_SHA と同じで diff が空になる場合を含む）、`git diff <BASE_SHA>`（作業ツリーとの差）を範囲とする。
   未追跡ファイルは `git ls-files --others --exclude-standard` の一覧を添えて、レビュアーにそれも読ませる。

2. **レビュアーに依頼する**: 新規サブエージェントに以下を渡す。
   - 作業内容の概要（DESCRIPTION）
   - 期待する要件や元になったプラン（PLAN_OR_REQUIREMENTS）
   - BASE_SHA / HEAD_SHA（未コミットの変更か未追跡ファイルがあるときは、手順 1 の作業ツリーとの差と未追跡ファイルの一覧も）
   - レビュー観点（通常は総合で、観点 A と B の箇条をすべて渡す。2 本に分ける場合は観点 A または観点 B を明示）
   - レビュアーの強度と役割（標準レビュー / 高強度レビュー）、モデルを指定できる環境ではそのモデル
   - 差分が全面的に書き換わる成果物（章構成の入れ替えなど）は、diff だけでなく HEAD の全文も読ませる（diff だけでは論旨の整合性を判定できないため）。
   - レビュアーは read-only（コードを変更しない）。
   - レビュアー自身はさらにサブエージェントを起動しない。
   - 返却フォーマット: Issues / 範囲外の論点と見なかった範囲 / Assessment の 3 つの見出し
   - Issues は blocking と non-blocking に分類し、通し番号（#1, #2...）を付与させる（再レビューでその番号を参照するため）。各項目には直し方の案も添えさせる。
   - Issues の各項目には、箇所（ファイルと行）と、どの入力・状態で何が起きるかを書かせる。文章ならどの読み手がどの場面でどう読み違えるか、設計ならどの変更や運用で誰が何に困るかを書かせる。
     箇所と何が起きるかを書けない指摘は挙げさせない（「確認してください」だけの指摘では、依頼者が直すかを決められないため）。
   - 差分が持ち込んでいない既存の問題は Issues に入れさせない。差分によって新たに実行経路に乗った既存の問題と、差分が影響範囲を広げた既存の問題は、差分が持ち込んだものとして扱わせる。
     それ以外の既存の問題は、データの損失・破損、脆弱性、主要な場面で使えなくなるものだけを、「既存」と明記して範囲外の論点に挙げさせ、それ未満のものは挙げさせない。
     既存の問題を直すかは、今回の変更を受け入れるかとは別に依頼者が決めるため。
   - 「範囲外の論点と見なかった範囲」には、検討したうえで計画や要件の範囲外として判定を見送った挙動や論点を、理由付きで 1 行ずつ挙げさせる（なければ「なし」と書かせる）。
     範囲外としてよいかをレビュアーだけで確定させず、依頼者が決めるため。
   - 同じ見出しに、見なかった範囲（読めなかったファイル、実行できなかったテスト、途中で打ち切った箇所）も 1 行ずつ挙げさせる（なければ「なし」と書かせる）。
     指摘がないことを、見なかった範囲に不具合がないことと取り違えないため。
   - Assessment には、受け入れてよいかと、残っている blocking の番号だけを答えさせる。

3. **結果に対応する**:
   - データの損失や脆弱性につながる指摘は、レビュアーが non-blocking と付けていても blocking に上げる（戻せない損害の可能性を残したまま変更を受け入れないため）。
   - エッジケースや異常系への備えを求める指摘は、防ぐ不具合と起こりやすさで扱いを決める。
     起こりにくく、起きても損害が小さいものは、blocking と付いていても non-blocking に下げる（起こりにくい場面への備えは、防げる損害に比べて読む量と保守の手間を大きく増やすため）。
     下げた指摘の記録には、blocking から下げたことと、防ぐ不具合・起こりやすさ・増える行数を添える（直すかをユーザーが判断できるようにするため）。
     前の項に当たるものと、要件やプランが明示しているものは、起こりにくくても下げない。
   - 何が起きるかが書かれていない指摘は、non-blocking なら直さず、理由を添えて記録する。
     blocking（データの損失や脆弱性の項で blocking に上げたものを含む）なら、次の項の確認に回す（書き方が足りないだけの本物の blocking を見送らないため）。
   - blocking の指摘は、書かれたことが実際に起きるかを確かめてから修正する。
     - コードなら実行経路をたどり、テストで再現できるなら失敗するテストを先に書く。文章なら該当の記述を読む。
     - 起きないと示せたものは、下の反論の項に従う。確かめきれなければ修正する（誤指摘を直す損より、本物の blocking を見送る損のほうが大きいため）。
     - 再レビューの上限が 0 回なら、修正を `completion-verification` で確かめて受け入れる。解消できなければユーザーに報告する。
   - non-blocking の指摘は後回しにしてよいが記録を残す。
     - 記録先の既定は完了報告の次のアクションとし、follow-up として指摘の番号と 1 行の要約を書く。
     - リポジトリに plan doc や decisions-log があれば、そこにも書いてよい。
     - PR 本文や issue への書き込みは外部への書き込みなので、ユーザーから明示的に指示されていなければ承認を得てから行う。
   - 判定を見送った挙動や論点は 1 行ずつ、範囲外のままでよいかを決める。
     - 範囲外のままにしたものは、番号を振らずに完了報告の次のアクションへ 1 行ずつ書く。
     - 「既存」と付いたものは、範囲外のままにするなら、次のアクションでなく完了報告の先頭に書く（重い問題を埋もれさせないため）。
     - 範囲内と判断したものは、指摘と同じく blocking か non-blocking に分けて扱う。
       直したものは再レビューで自己発見の修正として一覧に加える。再レビューの上限が 0 回なら、blocking の修正と同じく `completion-verification` で確かめて受け入れる。
   - 見なかった範囲は、種類ごとに次のように扱う。
     - 読めなかったファイルと途中で打ち切った箇所は、同じ役割の新規サブエージェントに、その部分だけを範囲として依頼する（作成側が自分で読み直しても独立レビューの代わりにならないため）。
       見なかった範囲を出したラウンドと同じ形式（初回なら初回の形式、再レビューなら `re-review.md` の形式）で頼み、範囲を絞る。そのラウンドの続きなので、再レビューの回数に数えない。
       再レビューの形式で頼むときは、判定させる番号も、絞った範囲に修正か反論の根拠があるものに限る（修正も反論の根拠も範囲の外にある番号を、未解消や見なかった範囲と書かせないため）。
       この依頼は見なかった範囲を出したレビュアー 1 本につき 1 回までとし、依頼したレビュアーがまた見なかった範囲は、もう依頼せず完了報告の未確認事項に書く（再レビューの回数に数えず、上限では止まらないため）。
     - 実行できなかったテストは、自分で実行する。
     - 上の対処ができなかったものは、完了報告の未確認事項に書く。
   - レビュアーの指摘が誤っていると判断した場合は、客観的根拠（コードやテスト結果）を示して反論する。
     反論して直さなかった blocking は、番号と根拠を完了報告に書く。再レビューを依頼するなら、前回の指摘一覧に「反論」として根拠と一緒に添え、判定させる。
   - 再レビューの上限が 1 回以上で、blocking の修正か、反論して直さなかった blocking か、意味の変わる自己発見の修正があれば、`re-review.md` に従って再レビューを依頼する。
     観点別の自己点検に切り替えた場合は、再レビューの代わりに `self-check.md` の 5 に従う。
