# 独立レビューの依頼

独立レビューを依頼するとき、その指摘に対応するとき、計画をレビューするとき、再レビューを行うとき、観点別の自己点検に切り替えるときに読む。
リスク分類の表（レビュアー強度と再レビューの上限）、用語、観点 A / B の定義は `SKILL.md` にある。

## 依頼手順

### 1. diff range を決める

初回は今回の作業全体を対象とする。再レビュー時は修正コミットのみに絞る（再レビューの規定は `re-review.md` にある）。
base の取り込みより前に依頼する（取り込み後は base 側の変更が範囲に混ざる）。
コミットしてよい作業（規則ファイルかユーザーが許している）なら、HEAD_SHA を取る前に今回の作業の変更をコミットする（コミットしないと、再レビューで修正分だけの範囲を取り出せないため）。

```bash
HEAD_SHA=$(git rev-parse HEAD)
BASE_SHA=<開始時の HEAD>  # 初回
```

それでも範囲に未コミットの変更か未追跡ファイルが残れば（HEAD が BASE_SHA と同じで diff が空になる場合を含む）、`git diff <BASE_SHA>`（作業ツリーとの差）を範囲とする。
未追跡ファイルは `git ls-files --others --exclude-standard` の一覧を添えて、レビュアーにそれも読ませる。

### 2. レビュアーに依頼する

新規サブエージェントに、次の 2 つを依頼文に含めて依頼する。

#### 渡すもの

- 作業内容の概要（DESCRIPTION）
- 期待する要件や元になったプラン（PLAN_OR_REQUIREMENTS）
  plan ファイルや要件の文書がなければ、ユーザーの依頼を要約せずに引用し、作成側が置いた前提を添える（要約すると、変更が依頼から外れたことを見抜けないため）。
  依頼が直前の提案への承諾（「それで進めて」など）なら、承諾された提案の該当部分も引用する。
- BASE_SHA / HEAD_SHA（未コミットの変更か未追跡ファイルがあるときは、手順 1 の作業ツリーとの差と未追跡ファイルの一覧も）
- レビュー観点（2 本に分けない場合は総合として観点 A と B の箇条をすべて渡し、2 本に分ける場合は観点 A または観点 B を明示する）
- リポジトリに AI レビュアー向けの指示ファイルがあれば、読んで観点に加えさせる（PR に付く Copilot などの AI レビューと基準をそろえるため）。
  指示ファイルには、`REVIEW.md`、`.github/copilot-instructions.md`、`.github/instructions/*.instructions.md`（差分のパスが `applyTo` に当たるものだけ）などがある。
  書式、優先度の段階、既存の問題の扱いは、指示ファイルでなくこの依頼に従わせる（以降の対応手順が、この依頼の書式、blocking / non-blocking の分け方、既存の問題の挙げ先を前提にするため）。
  指示ファイルは観点を足すのにだけ使わせ、挙げない指摘の一覧のような指摘を減らす定めには従わせない。
  差分が指示ファイル自体を変えていれば、BASE_SHA の版も読ませる（作成側が今回の変更で緩めた基準のまま、今回の変更を見させないため）。
- レビュアーの強度と役割（標準レビュー / 高強度レビュー）、モデルを指定できる環境ではそのモデル（モデルは `SKILL.md` の「読むファイル」に従って決める）
  - 「標準レビュー」の役割（標準レビュアー）は総合の観点で、「高強度レビュー」の役割（高強度レビュアー）は観点を特化した重点検証の依頼文で依頼する。
    高強度レビュアーを 2 本に分けない場合は、観点を絞らず、変更の性質から重点を置く箇条を明示して特化する（片方の観点に絞ると、もう片方を誰も見ないため）。
    作成側が人間・メインセッション・サブエージェントのいずれでも、表の強度は変えない。
- 差分が全面的に書き換わる成果物（章構成の入れ替えなど）は、diff だけでなく HEAD の全文も読ませる（diff だけでは論旨の整合性を判定できないため）。
- 画面の表示や操作が変わる差分では、repo の検証手段（検証用 skill、Storybook、e2e など）も渡し、diff を読んだうえで実際に表示・操作して確かめさせる。
  作成側は意図した通りに表示されていると思い込みやすく、見た目の崩れは diff とテストでは見つけにくいため。
  dev サーバーで確かめさせるなら、依頼者が先に起動して URL を渡す（レビュアーごとに起動させると、ポートが衝突し、プロセスも残るため）。
  スクリーンショットなどの証拠は作業ツリーの外に置かせ（追跡外のファイルを作業ツリーに残させないため）、指摘に添えさせる。

#### レビュアーに求めること

- レビュアーは read-only（コードを変更しない）。
- レビュアー自身はさらにサブエージェントを起動しない。
- 返却フォーマット: Issues / 範囲外の論点と見なかった範囲 / Assessment の 3 つの見出し
- Issues は blocking と non-blocking に分類し、通し番号（#1, #2...）を付与させる（再レビューでその番号を参照するため）。各項目には直し方の案も添えさせる。
- Issues の各項目には、箇所（ファイルと行）と、どの入力・状態で何が起きるかを書かせる。文章ならどの読み手がどの場面でどう読み違えるか、設計ならどの変更や運用で誰が何に困るかを書かせる。
  箇所と何が起きるかを書けない指摘は挙げさせない（「確認してください」だけの指摘では、依頼者が直すかを決められないため）。
- 差分が持ち込んでいない既存の問題は Issues に入れさせない。差分によって新たに実行経路に乗った既存の問題と、差分が影響範囲を広げた既存の問題は、差分が持ち込んだものとして扱わせる。
  それ以外の既存の問題は、データの損失・破損、脆弱性、主要な場面で使えなくなるものだけを、「既存」と明記して範囲外の論点に挙げさせ、それ未満のものは挙げさせない。
  既存の問題を直すかは、今回の変更を受け入れるかとは別に依頼者が決めるため。
- 「範囲外の論点と見なかった範囲」には、検討したうえで計画や要件の範囲外として判定を見送った挙動や論点を、理由付きで 1 行ずつ挙げさせる（なければ「なし」と書かせる）。
  範囲外としてよいかをレビュアーだけで確定させず、依頼者が決めるため。
- 同じ見出しに、見なかった範囲（読めなかったファイル、実行できなかったテスト、動かせなかった画面、途中で打ち切った箇所）も 1 行ずつ挙げさせる（なければ「なし」と書かせる）。
  指摘がないことを、見なかった範囲に不具合がないことと取り違えないため。
- Assessment には、受け入れてよいかと、残っている blocking の番号だけを答えさせる。

### 3. 結果に対応する

#### 分類の上げ下げ

- データの損失や脆弱性につながる指摘は、レビュアーが non-blocking と付けていても blocking に上げる（戻せない損害の可能性を残したまま変更を受け入れないため）。
- エッジケースや異常系への備えを求める指摘は、頻度と被害を 1〜10 で採点し、レビュアーの分類によらず点数で扱いを決める（起こりにくい場面への備えは、防げる被害に比べて読む量と保守の手間を大きく増やすため）。
  前の項に当たるものは前の項に従い、要件やプランが明示しているものはレビュアーの分類のままにする。どちらも採点しない。
  - 頻度は、その成果物を使う全員を合わせた頻度を対数の目盛りで付ける。
    1 = 年 1 回未満か、故障や設定ミスが 2 つ重ならないと起きない、3 = 月 1 回、5 = 週 1 回、7 = 毎日、9 = 一部の利用者で毎回、10 = 全員で毎回。
  - 被害は、ほかの防御が働いたあとに残るものを、頻度と同じく対数の目盛りで付ける。
    1 = 見た目が崩れるか、再読み込みで直る、3 = 1 人の操作が失敗し、やり直しで済む、5 = 一部の機能や利用者が止まり、手作業で直す。
    7 = 全体が止まるか、締め切りに間に合わない、9 = データの破損や消失で復旧が要る、10 = 漏えいなど取り返しがつかない。
  - 決めきれない点数は高いほうを採る（採点するのは作成側でもある依頼者で、低く付けた誤りを確かめる人がいないため）。
  - 被害 9 以上か、頻度と被害の和が 10 以上なら blocking として扱う（被害 9 以上を和によらず blocking にするのは、まれでも取り返しのつかない被害を non-blocking に下げないため）。
  - 和が 8〜9 なら non-blocking に下げる。数行で直せるなら直してよく、直さなければ follow-up として記録する。
  - 和が 7 以下なら non-blocking に下げ、直さず、follow-up にも積まない。
  - 下げた指摘は、残っている blocking に数えない。
  - 積でなく和で決める（どちらもおおよそ対数の目盛りなので、点数の和が、実際の頻度と被害を掛けた大きさの桁に当たる。点数どうしの積はこの大きさに対応せず、片方が 1 のとき他方が高くても低く出る）。
  - 下げて直さなかった指摘は、1 件 1 行で、番号、数語の要約、頻度と被害の点数、blocking から下げたかを完了報告に書く（直すかをユーザーが決めるため。レビュアーの報告はユーザーに見えない）。
    和 8〜9 は次のアクションの follow-up の行に点数を添えて書き、和 7 以下は次のアクションに入れず、採点で見送った指摘として別に書く。

#### 何が起きるかが書かれていない指摘

- 何が起きるかが書かれていない指摘は、non-blocking なら直さず、理由を添えて記録する。
  blocking（データの損失や脆弱性の項で blocking に上げたものを含む）なら、「blocking の指摘」の確認に回す（書き方が足りないだけの本物の blocking を見送らないため）。

#### blocking の指摘

- blocking の指摘は、書かれたことが実際に起きるかを確かめてから修正する。
  - コードなら実行経路をたどり、テストで再現できるなら失敗するテストを先に書く。文章なら該当の記述を読む。
  - 起きないと示せたものは、「反論と再レビュー」に従う。確かめきれなければ修正する（誤指摘を直す損より、本物の blocking を見送る損のほうが大きいため）。
  - 再レビューの上限が 0 回なら、修正を SKILL.md の「依頼と受け入れの既定」のとおり確かめて受け入れる。解消できなければユーザーに報告する。

#### non-blocking の指摘

- non-blocking の指摘は後回しにしてよいが記録を残す（採点で下げた指摘は、「分類の上げ下げ」の採点に従う）。
  - 記録先の既定は完了報告の次のアクションとし、follow-up として指摘の番号と 1 行の要約を書く。
  - リポジトリに plan doc や decisions-log があれば、そこにも書いてよい。
  - PR 本文や issue への書き込みは外部への書き込みなので、ユーザーから明示的に指示されていなければ承認を得てから行う。

#### 判定を見送った論点

- 判定を見送った挙動や論点は 1 行ずつ、範囲外のままでよいかを決める。
  - 範囲外のままにしたものは、番号を振らずに完了報告の次のアクションへ 1 行ずつ書く。
  - 「既存」と付いたものは、範囲外のままにするなら、次のアクションでなく完了報告の先頭に書く（重い問題を埋もれさせないため）。
  - 範囲内と判断したものは、指摘と同じく blocking か non-blocking に分けて扱う。
    直したものは再レビューで自己発見の修正として一覧に加える。再レビューの上限が 0 回なら、blocking の修正と同じく確かめて受け入れる。

#### 見なかった範囲

- 見なかった範囲は、種類ごとに次のように扱う。
  - 読めなかったファイルと途中で打ち切った箇所は、同じ役割の新規サブエージェントに、その部分だけを範囲として依頼する（作成側が自分で読み直しても独立レビューの代わりにならないため）。
    見なかった範囲を出したラウンドと同じ形式（初回なら初回の形式、再レビューなら `re-review.md` の形式）で頼み、範囲を絞る。そのラウンドの続きなので、再レビューの回数に数えない。
    再レビューの形式で頼むときは、判定させる番号も、絞った範囲に修正か反論の根拠があるものに限る（修正も反論の根拠も範囲の外にある番号を、未解消や見なかった範囲と書かせないため）。
    この依頼は見なかった範囲を出したレビュアー 1 本につき 1 回までとし、依頼したレビュアーがまた見なかった範囲は、もう依頼せず完了報告の未確認事項に書く（再レビューの回数に数えず、上限では止まらないため）。
  - 実行できなかったテストは自分で実行し、動かせなかった画面は自分で表示・操作して確かめる。
  - 上の対処ができなかったものは、完了報告の未確認事項に書く。

#### 反論と再レビュー

- レビュアーの指摘が誤っていると判断した場合は、客観的根拠（コードやテスト結果）を示して反論する。
  反論して直さなかった blocking は、番号と根拠を完了報告に書く。再レビューを依頼するなら、前回の指摘一覧に「反論」として根拠と一緒に添え、判定させる。
- 再レビューの条件（`SKILL.md` の「読むファイル」の re-review.md の項）に当たれば、`re-review.md` に従って再レビューを依頼する。
  観点別の自己点検に切り替えた場合は、再レビューの代わりに `self-check.md` の 5 に従う。
