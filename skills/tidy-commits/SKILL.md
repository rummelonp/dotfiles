# コミットの整理

作業ブランチの `<base>..HEAD` にあるコミット列を組み直す。
base への追従（rebase や merge）と push は `pr-workflow` に従う。

## 着手前の判定

1. 進行中の操作を確かめる。
   `git rev-parse --git-path rebase-merge` が指すディレクトリがあり、自分が始めた操作でなければ、ユーザーが `rebase -i` の途中にいる。
   - 止まっているコミットの評価と、そのコミットへの `commit --amend` だけを行う。
     amend は「直して」と頼まれたときだけ行い、評価を頼まれただけなら直し方の提案で止める。
   - `--continue`、`--skip`、`--abort` は実行しない。
   - 手直しを評価するときは、元のコミット（`done` の末尾にある SHA）との差分、メッセージとの整合、そのコミットの時点のツリーで成り立つか（検査があればその場で実行し、なければ参照先がそのツリーにあるかを確かめる）を見る。
     手直しが、`git-rebase-todo` に残っている後のコミットの変更を先取りしていないかも確かめる。
2. 書き換えてよいかを決める。
   ユーザーの明示（「amend して」「積んで」「fixup で」）が常に優先し、明示がなければ次で決める。
   - **未 push、または Draft PR**：書き換えてよい。
   - **Ready の PR**：書き換えず、新規コミットを積む。
   - **どちらとも言えない場合**（push 済みで PR がないなど）：書き換えるか積むかを確認する。
   - 書き換えてよい状態で「任せる」と言われたら、積まずに畳む。
3. 範囲にマージコミットがあれば、組み直す前に方針を確認する。
   rebase はマージコミットを落とすので、マージで解消した競合や取り込んだ変更が失われることがある。
4. 未コミットの変更を仕分ける。
   依頼に含まれると判断できない変更（別セッションの編集など）は、コミットに入れない。
   `rebase.autostash` が有効な環境では rebase がその変更を stash に退避して戻すが、戻すときに競合すると変更は stash に残るので、その旨を報告する。

## 粒度の基準

- 1 コミットに 1 つの意図を入れ、レビュアーがコミット単位で読んで判断できるようにする。
- 依存の追加、生成物（lockfile、コード生成の出力）、整形や rename などの機械的な変更は、それぞれ単独のコミットにする。
  単独にしておけば、レビュアーはそのコミットを読まずに済ませられる。
- リファクタと振る舞いの変更は分ける。
- 各コミットの時点で整合させ、後のコミットで入るものを参照しない。
- 最終状態が最初から計画されていたかのようなコミット列にする。
  試行錯誤、レビュー指摘への対応、誤字の修正は、それを入れたコミットへ畳む。
  追加して直後に直すような、中間状態が不自然な連続コミットは 1 つにする。
- コミットメッセージは畳んだ後の内容に合わせて書き直し、言語と形式はリポジトリの規約と既存の履歴に従う。
- リポジトリの規約に粒度の定め（1 設定 1 コミットなど）があれば、そちらを優先する。
- 既に基準を満たしていれば何もせず、その旨を報告する。

## 手順

- **元の先端の固定**：書き換える前に `git tag tidy/<目的> HEAD` を打つ。
  backup にブランチは使わない。
  `rebase.updateRefs` が有効だと、範囲内のコミットを指すブランチは rebase で新しい先端へ一緒に動くので、元の先端が残らない。
- **既存コミットへの修正**：`git commit --fixup=<sha> -- <paths>` を対象ごとに作り、`GIT_SEQUENCE_EDITOR=true git rebase -i --autosquash <base>` で畳む。
  対象は `git log --oneline <base>..HEAD -- <path>` や `git log -S '<直す箇所の文字列>'` で、直す行を入れたコミットを探す。
- **全面的な組み直し**：`git reset <base のハッシュ>` で差分を作業ツリーに戻し、意図ごとに add と commit を繰り返す。
  1 ファイルの変更を複数のコミットに分けるときは、途中の状態に編集してコミットし、`git checkout tidy/<目的> -- <path>` で最終版に戻してから次をコミットする。
  途中の状態はファイル編集ツールで作り、シェルのリダイレクトでは書かない（`noclobber` が有効だと上書きが失敗し、最終版のままコミットしてしまう）。
  commit の前に `git diff --cached` の本文を読み、そのコミットに入れる変更だけになっていることを確かめる。
- **並べ替え、drop、reword**：todo を書き換えるスクリプトを `GIT_SEQUENCE_EDITOR` に渡す。
  `sed -i` は GNU と BSD で構文が違うので、`perl -i -pe` を使う。
- **共通の注意**：
  - `git add` はパスを明示し、`-a`、`-A`、`.` を使わない。commit の前に `git diff --cached --stat` を見る。
  - エディタが開く操作には `GIT_EDITOR=true` か `commit -F` を使う。
  - reset 先はハッシュで書く。`HEAD~N` は、別の操作で HEAD が動くと指す先が変わる。

## 検証

- `git diff tidy/<目的> HEAD` が空であることを確かめる。
  依頼に内容の変更（手直しの取り込みなど）が含まれるときは、差分がその変更だけであることを確かめる。
  説明できない差分が出たら、元の先端からやり直す。
- 未コミットの変更を残したときは、着手前の `git diff` をリポジトリの外に保存し、整理後の `git diff` と一致することを確かめる。
  タグとの比較はコミット済みのツリーしか見ないので、作業ツリーの変更が失われても気づけない。
- 各コミットがその時点で成り立つかを確かめる。
  - 短時間で終わる検査（`package.json` の scripts、`Makefile`、CI の設定から探す）があれば、`git rebase -x '<検査コマンド>' <base>` で各コミットを検査する。
  - 検査がない、または依存が入っておらず実行できなければ、各コミットの差分を読み、参照している名前やファイルがそのコミットまでに入っているかを確かめる。報告には、実行した検査ではなく差分を読んで確かめたと書く。
- 検証が通ったらタグを消し、元の先端のハッシュを報告に残す。

## 報告

- 新しいコミット列（ハッシュと件名）
- 元の先端のハッシュ
- ツリー差分の結果と、実行した検査
- push の要否（書き換えた場合は force push が要る）。push 自体は `pr-workflow` に従い、指示か承認を得てから行う。
