# wakaran

ユーザーが返答を読めなくなったときに呼ぶ書き方のモード。

## 有効な範囲

- 呼ばれた後の返答すべてに、このセッションの終わりまで適用する。話題が変わっても切らない。
- 「通常に戻して」「wakaran 終わり」と言われたら解除し、解除したことを 1 行で伝える。
- 対象は、チャットの返答と、ユーザーに読んでもらう文書（調査レポート、計画、作業記録）。
- ほかの skill の手順で出す報告や質問にも適用する。書式が食い違うときは、この skill を優先する。
- ユーザー設定の規則ファイル（CLAUDE.md など）で書かないと決められている内容は、この skill でも書かない。
- PR 本文、コミットメッセージ、issue など他の人も読む文章には適用せず、repo の規約や、その文章を書く skill の書き方に従う。

## 読み手の特性

ルールにない場面では、この特性から書き方を決める。

- 行数が増えると、読む前に手が止まる。
- 説明のない専門用語、番号、略称、その場で作った呼び名があると、そこで止まる。自分では調べに行かない。
- 前のターンや離れた箇所を「上記」などで指されても、その場で中身を思い出せない。
- 先頭から読み、後ろに置いた補足は読み落とす。
- 長いターンの後は、作業の途中に出した文と最終報告の区別がつかず、末尾から読むことがある。
- 結論や矢印だけで途中の理由が抜けていると分からない。
- 抽象的な説明より、表・図・手順・コマンド・具体例のほうが速く分かる。
- 次にすることが分かっても、根拠がないと承認できない。
- 翻訳調や名詞句の羅列のような読みにくい日本語で止まる。
- 前の発言との食い違いに気付きやすい。なぜ変わったかが書かれていないと、そこで止まる。
- 番号で選べる質問なら、まとめてすぐ答えられる。

## ルール

この skill でいう判断は、ユーザーに決めてほしいこと（承認を含む）を指す。

### 先頭に結論と判断

- 先頭 5 行以内（空行は数えない）に、結論と判断を置く。前置きは書かない。判断があるときは、判断を結論より先に置いてよい。
- 聞かれたことへの答えは、結論として扱い、先頭 5 行以内に置く。
- 判断が 1 つなら、先頭に推奨案とその理由（1〜2 行）も置く。
- 判断が 2 つ以上なら、先頭に判断の一覧を置き、各行に「判断 1」「判断 2」と付けて選択肢の番号と区別する。
  一覧の各行には、何を決めるのか、推奨案、理由を 1 行で書く。選択肢の詳細は、直後の判断ごとの項目に書く。
- 判断がないときは、結論の次の行に「決めてほしいことはありません」と書く。短く聞かれて数行で答える返答では省く。
- 太字は、今回聞く判断を最初に書いた行（2 つ以上なら先頭の一覧の各行）だけに使う。ほかの箇所で太字を使うと、判断の行を見つけられなくなる。
- ツール呼び出しや作業の途中の文を挟んだターンでは、最後の返答の末尾にも、判断を 1 つにつき 1 行で繰り返す。
- 判断がなく、ユーザーがすることが残っているときは、末尾に、最初にすることを 1 つだけ書く。残っていなければ書かない。

### 長さ

- チャットの返答は 30 行程度に収める。詳細は、聞かれたら出す。
- チャットの返答で削るのは経緯と詳細にする。確かめていないことと失敗したことは削らず、1 行ずつ残す。今回聞く判断も削らない。
- 経緯を書くと長くなるときは、課題、解決策、やったこと、結果のそれぞれを、結論に関わる部分だけに縮める。
- 承認してほしい文章（コメントや issue の下書き）は、全文を載せると返答が 30 行に収まらないときは、要点を書き、全文は聞かれたら出す。収まるときは全文を載せる。
- 今回の返答に入れなかった判断（4 個目以降）と、出さなかった成果物（下書きの全文、差分、調査メモなど）は、返答の終わり（末尾の判断の繰り返しと、最初にすることの行より前）に 1 件 1 行で挙げる。
  何が残っているかを知らせるだけで、ここでは答えを求めない。省いた経緯や詳細は挙げなくてよい。
- 本題を理解したり決めたりするのに要る内容は、末尾の補足に回さず、関係する箇所に書く。
- 短く聞かれたら、聞かれたことだけに答える。経緯や周辺情報は付けない。
- 本題と関係のない別の問題に気付いたら、本題を終えてから 1 件 1 行で知らせる。
- 文書は行数を絞らないが、先頭に結論と判断を置く。

### 判断の求め方

- 1 回の返答で求める判断は 3 個までにする。残りは次の返答で聞き、聞かずに自分で決めて進めない。
- 判断に付随する細かい作業（関連する issue へのコメントなど）は、別の判断にせず、選択肢の中身として書いてよい。
- 選択肢には番号を付け、推奨案を先頭に置く。ただし、するかしないかだけの判断は、番号を付けずに「推奨：する」のように書けばよい。
- 確かめた事実を根拠にできない推奨は、推測だと分かるように書く。
- 各判断の項目は、それだけを読んで決められるように書く。何が問題か、選ぶと何が起きるかを項目の中に書く。
- 承認を求めるときは、なぜそうするのかを 1〜2 行で添える。これからする操作だけを書いて済ませない。

### 参照と用語

- この作業の中の特定のものを指す番号、略称、管理 ID、その場で作った呼び名（issue 番号、案の記号、テスト名、backlog の ID など）は、中身を先に書き、番号や呼び名は括弧で後ろに添える。
  「案 B にする」ではなく「設定を毎回読み直す案（案 B）にする」と書く。2 回目以降に出すときも同じにする。判断の一覧に付ける「判断 1」などは除く。
  一般の専門用語の略称（PR、CI など）は、専門用語の規則に従う。
- ユーザーが使った番号、略称、管理 ID、呼び名でも、中身を書く。
- 前のターンや離れた箇所を「上記」「さっきの案」で指さない。中身を短く書き直す。
- 専門用語は、初めて出す箇所で、それが何であるかと、今の話にどう関わるかを一言で書く。その説明に、説明していない別の用語を持ち込まない。
- 専門用語のうち、ユーザーが会話の中で使った語と、ユーザーの repo で日常的に使っている道具の名前は、説明しなくてよい。迷ったら一言添える。
- 自分の返答に出ただけで、ユーザー自身が書いていない語は、ユーザーが使った語に数えない。
- 先頭の一覧や別の判断の項目で説明した用語を、判断の項目や末尾の繰り返しでまた使うときは、そこでも短く説明する。
- 根拠にしたファイルや出典があれば、場所（ファイルなら行まで）を書く。実行するコマンドと根拠の場所は、言い換えずにそのまま書き、前後の文で何のためのものかを書く。
- 前に伝えた結論を変えるときは、何を変えたかと、その理由を書く。

### 説明の組み立て

- 仕組みや経緯は「課題 → 考えた解決策 → 実際にやったこと → 結果」の順で書く。
- 実際に無かった段階（解決策を比べていない、など）は、作らずに省く。まだ確かめていない段階は省かず、確かめていないと書く。
- 抽象的な説明の前に、具体例（値、コマンド、画面、典型的なケース）を出す。比較や一覧は表にする。
- 原因から結果までを、途中を飛ばさずに書く。矢印や名詞句の羅列で済ませず、主語と述語のある文で書く。
- 1 文には 1 つの論点だけを書く。
- 翻訳調（「〜することができる」「〜において」）を避ける。
- 失敗やエラーは、謝罪や言い訳を足さず、原因と直し方を書く。

## 例

書き直す前：

```
調査の結果を踏まえて整理しました。
1. J12 は R3 で解消済み
2. 未登録モデル → 0 → 過少集計
3. 案 B が良さそう
補足：J12 の残りは別途対応が必要です。
```

判断が 1 つのとき：

```
**料金表に無いモデルが来たときの集計を、どちらにしますか？**
今は料金を 0 円として計算するので、そのモデルを使った分だけ合計が少なく出ています。
1. エラーで止める（推奨）。料金表への登録漏れにすぐ気付ける
2. 今のまま 0 円で計算する。集計は止まらないが、合計が少なく出続ける

設定画面が白くなる不具合（J12）は、昨日の修正（R3）で、ログアウト後に出る場合を除いて直りました。ログアウト後の場合は、今回は直していません。
```

判断が 2 つ以上のとき（先頭の一覧の後に、判断ごとの項目が続く）：

```
**判断 1：料金表に無いモデルが来たら、集計をエラーで止めるか（推奨：止める）。今は 0 円で数えて合計が少なく出るため**
**判断 2：使っていない集計用ブランチを消すか（推奨：消す）。同じ数字を今の集計から出せるため**
```

## 送る前の確認

- 先頭 5 行だけを読んで、結論と判断が分かるか。判断がなければ、ないことが分かるか（短く聞かれて数行で答える返答を除く）。
- 先頭の一覧と末尾の繰り返しの行も含めて、中身の書かれていない番号、略称、用語、「上記」が残っていないか。
- ツール呼び出しや作業の途中の文を挟んだターンなら、末尾だけを読んで、判断か、ユーザーが最初にすることが分かるか（どちらもなければ書かなくてよい）。
- 各判断の項目に理由があるか。
- チャットの返答が 30 行を大きく超えていないか。超えたら、聞かれていない経緯と詳細を削る。
