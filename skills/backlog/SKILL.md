# バックログ

作業の**項目**を「ID、状態、種別、依存」の表で持ち、同梱のスクリプトで着手できる項目と依存を引く。
表を置いた 1 つの Markdown ファイルを**計画**、1 つの置き場所にある計画の全体を**バックログ**と呼ぶ。
表の書式は置き場所によらず同じにする。
複数の項目を並列に進めるときは `parallel-lanes` skill に従う（同 skill がこの skill で項目を引き、状態の更新も同 skill が定める）。

## 書式

スクリプトが読むのは、ヘッダが `| # | 状態 | 種別 | 依存 |` で始まる表だけである。
5 列目以降は自由に足してよい（`内容` を置くことが多い）。
表以外の行（見出し、frontmatter、本文）は読み飛ばす。

```markdown
| # | 状態 | 種別 | 依存 | 内容 |
|---|---|---|---|---|
| C1 | 完了 | 実装 | — | 保存形式を決める |
| C2 | 未着手 | 実装 | C1 | 保存を実装する |
| C3 | 未着手 | 判断 | C1 | 同期の方式を選ぶ |
| C4 | 未着手 | 集約 | C2、C3 | 保存と同期 |
```

- **ID**：`^[A-Za-zα-ω]+[0-9]+[a-z]?$` に合う文字列。
  接頭辞は計画を作るときに 1 つ決め、同じバックログのほかの計画と重ねない。
  後から間に挟む項目には `C2a` のように接尾辞を付ける。
- **状態**：未着手、進行中、完了、取りやめ、保留のいずれか。依存を満たすのは完了だけである。
  - **取りやめ**：やらないと決めて閉じた項目。
    判断の項目で「やらない」と結論したときは、判断は済んだので完了にする。
    取りやめは、判断すること自体をやめたときに使う。
    取りやめの項目に、取りやめでない項目（集約を除く）が依存していると `check` の違反になる。
    依存を満たさないので、そのままでは後ろの項目が着手できないまま残る。
  - **保留**：開いたまま、今は手を付けない項目。`ready` に出ず、`status` の末尾に並ぶ。
- **種別**：既定は次の 5 つ。
  - **実装**：自律で着手できる唯一の種別。
    `subagent-delegation` skill の役割名の「実装」とは別で、種別が実装でも上位実装の役割に任せることがある。
  - **人手**：実機での確認や外部サービスの設定など、人が手を動かす作業。人を待つ項目として扱う。
  - **判断**：人が決めること。人を待つ項目として扱う。
  - **改善候補**：レビューの non-blocking な指摘など、ユーザーが選ぶまで着手しない follow-up（後述の「follow-up を残す」）。
    自律で着手するのは、ユーザーか repo の宣言が範囲に含めたときだけである（`parallel-lanes` skill の follow-up の扱い）。
    状態の保留と違い、`ready` の改善候補の列に出る（ユーザーが選ぶ候補として見せるため）。
    ユーザーが着手すると決めたら、種別を実装に変える。
    着手すると決めた項目を止めるときは、種別を改善候補にせず状態を保留にする（改善候補の項目はユーザーの不在中の実行で候補になり、止めた理由と再開の条件も残らないため）。
  - **集約**：依存に挙げた項目（子）の状態から導く項目で、手で状態を決めない。
    状態は取りやめの子を除いて導き、次のうち最初に当たるものになる。
    - 残りの子がなければ取りやめ
    - 全部完了なら完了
    - 完了していない子が全部保留なら保留
    - 未着手と保留だけなら未着手
    - それ以外は進行中

  ほかの種別は、repo が `--kind` で足せる。
  足した種別には自律で着手しない。
- **依存**：依存がなければ `—`。複数は `、` で区切る。
  `C2〜C9`（波ダッシュは U+301C）は範囲を表し、範囲内の接尾辞付き ID も含む。

ほかの規則は次のとおり。

- 完了か取りやめにした項目をやり直すときは、行の状態を戻さず、新しい ID を足す。
  保留の項目は、再開を決めたら未着手に戻す。
- 番号は使い回さない。次の番号は、その接頭辞でこれまでに使った最大の番号に 1 を足したものにする。
- 表に収まらない詳細は、表の下に `### <ID>` の節を作って書く（スクリプトは読まない）。
- 行は消さない。
  表が repo で追跡しない場所（追跡しないファイル、メモリ）にあるときと、ユーザーが指示したときに限り、どの行からも依存されていない完了と取りやめの行を消してよい。
  範囲の依存 `C2〜C9` に含まれる行も、依存されているとみなす。
  消すときは、消した中で最大の ID を表の下に `消した最大の ID: C9` のように 1 行残す（番号の使い回しを防ぐため）。
  表の行の形にすると項目として読まれるので、表の外に書く。

## 置き場所

| 置き場所 | 向いている場面 | 状態を更新する人 |
|---|---|---|
| GitHub の issue | issue と PR で作業を進める repo | PR のマージで閉じる（`Closes` で閉じられない取り込みでは、取り込んだ人が閉じる） |
| repo で追跡する文書 | 計画を履歴に残してよい repo | 項目を完了させるコミット |
| repo の追跡しないファイル（gitignore したディレクトリ） | 履歴に残したくないが、repo の近くに置きたい | メインセッションだけ |
| エージェントのメモリ（Claude Code なら自動メモリの `backlog.md`） | 個人 repo | メインセッションだけ |

追跡しないファイルとメモリは、別の worktree で動く作業者からは見えない（メモリも worktree ごとに別の場所になる）。
そのため状態の更新は、作業者の報告を受けたメインセッションが行う。
GitHub の issue へ書き込む（状態を変える、コメントする）のは外部への書き込みなので、ユーザーの指示か承認を得てから行う。

どこを使うかは、repo の指示ファイル（`AGENTS.md`、`CLAUDE.md` など）かエージェントのメモリの「バックログ」節の宣言で決まる。
宣言がないときは、既定の場所（追跡する文書は `docs/backlog/`、追跡しないファイルは `.claude/backlog/`）のうち、計画のあるものをすべて使う。
宣言も既定の場所の計画もないとき、置き場所を作るとき、宣言を書き直すとき、宣言に follow-up 用の別の種別（`--kind=follow-up` など）があるときは、`<この skill のディレクトリ>/references/setup.md` を読む。
置き場所が GitHub の issue なら、`<この skill のディレクトリ>/references/github-issues.md` も読む（宣言に書くこと、引き方、issue への書き込み）。

## 引く

```sh
node <この skill のディレクトリ>/scripts/plans.ts <コマンド> [--kind=<種別>]... -- <ファイルかディレクトリ>...
```

コマンドごとの出力は次のとおり。

- `status`：計画ごとの状態の集計と、以下の項目。どれも集約を含み、項目には実装以外の種別を添える。
  - 進行中の項目
  - 依存待ちの未着手の項目（直接待っている未完了の項目を添え、保留のものには `（保留）` を付ける）
  - 保留の項目
- `ready`：依存がすべて完了で、まだ着手していない項目。
  種別ごとに、その項目が片付くまで着手できない未完了の項目の多い順に並ぶ。
  この数には間接に依存する項目も含め、集約と、保留の項目およびそれに直接か間接に依存する項目は含めない。
- `deps [<ID>...]`：指定した項目が待っている未完了の項目と、指定した項目を待っている項目（間接のものを含む）。ID を省くと全件。
- `graph [<ID>...]`：Mermaid の依存グラフ（全体を見たいときだけ使う）。
- `check`：書式と整合性の違反。

コマンドは省略できない。
違反があると、`check` 以外のコマンドも違反を出して終了コード 1 で止まる。
引数の誤り（未知のコマンドやオプション、存在しない ID）と、読めないファイル（ディレクトリ内の壊れた symlink を含む）は終了コード 2 になる。
項目の表は行頭から書く。インデントやリスト、引用の中に置いた表と、閉じていないコードフェンスは違反になる。

- ディレクトリを渡すと、直下の `*.md` から `README.md` と `_` で始まるファイルを除いて読む。
  ファイルを直接渡したときは名前によらず読む。
- `--kind=<種別>` で、自律で着手しない種別を足す（例: `--kind='PO 判断'`、`--kind=磨き`）。語彙にない種別は `check` の違反になる。
- `ready` で待っている項目の数が同じ項目は、ファイルの絶対パス（symlink はリンク先）の順、ファイル内では表の順に並ぶ。
  表の並びを優先順位として扱う。
- Node 22.18 以上で動く（TypeScript の型除去が既定で有効になる版）。
  repo が古い Node に固定されていても repo の設定は変えず、版を管理するツールの exec などで 22.18 以上の Node を指定して実行する。
- バックログを見せるときは `status` と `ready` を引く。
  閉じていない項目（未着手、進行中、保留）はすべて、この 2 つのどちらかに内容ごと出るので、表を読み直さない。
- 1 つの計画だけを見せるときも、使っている置き場所の全体を渡し、出力からその計画の項目を抜き出す。
  計画をまたぐ依存は、渡さなかった計画の ID が存在しないという違反になる。
- 1 項目だけ見たいときは `rg -n '^\| <ID> \|' <ファイル>` で行を引き、計画を全文読まない。
- CI や pre-commit で `check` を走らせる repo は、`references/setup.md` の「CI で `check` を走らせる」に従う。
- GitHub の issue のバックログは、スクリプトを使わず `references/github-issues.md` の「引く」に従って引く。

## 足す、更新する

- **項目を足す**：接頭辞の次の番号を振り、種別と依存を決めて行を足す。足したら `check` を走らせる。
- **状態を変える**：置き場所の表の「状態を更新する人」に従う。集約の行は、`check` が導いた状態に合わせる。
  保留か取りやめにする、保留から戻す、判断の項目を完了にする、ユーザーの言葉で項目を止める、のいずれかのときは、先に `<この skill のディレクトリ>/references/updating.md` を読む。
  止める言葉が保留か取りやめかを読み分けられなければ、確かめるまで状態を変えない。
  取りやめにする項目に後ろの項目があるときと、「やらない」で完了にする判断の項目にその結論で要らなくなる後ろの項目があるときは、後ろの項目の扱い（取りやめか依存から外すか）が範囲を変えるので、ユーザーに確かめるまで前の項目も変えない。
- **follow-up を残す**：レビューの non-blocking な指摘など、後回しにした作業は、新しい項目として足すか、既存の項目の `### <ID>` 節に追記する。
  新しい項目の種別は改善候補にする（実装にすると、ユーザーが選ぶ前に `ready` に出て自律の作業の対象になる）。
  未着手か進行中の実装の項目の節には追記しない。
  `### <ID>` 節の書き方と依存の決め方は、`references/updating.md` の同名の節を読む。
- **重い問題を知らせる**：作業の範囲外で見つけた問題のうち、データの消失や破損、セキュリティ、主要な場面で使えなくなるものは、判断の項目として足し、完了報告の先頭に書く。
  種別を改善候補にしない。`### <ID>` 節の書き方は、`references/updating.md` の同名の節を読む。

## 常に守ること

- `check` の違反を残したまま終えない。
- 計画の中身（設計、判断、項目の範囲）は、ユーザーの確認なしに書き換えない。状態の更新と、決まった作業の追加は確認なしでよい。
- 追跡しないファイルやメモリに置いたバックログの ID（`C3` など）は、読み手が引けないので、コミットメッセージ、PR のタイトルと本文、コード、コメントに書かない。追跡する文書の ID と GitHub の issue の番号は引けるので書いてよい。
