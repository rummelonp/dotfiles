# バックログ

作業の**項目**を「ID、状態、種別、依存」の表で持ち、同梱のスクリプトで着手できる項目と依存を引く。
表を置いた 1 つの Markdown ファイルを**計画**、1 つの置き場所にある計画の全体を**バックログ**と呼ぶ。
表の書式は置き場所によらず同じにする。
複数の項目を並列に進めるときは `parallel-lanes` skill に従う（同 skill がこの skill で項目を引き、状態の更新も同 skill が定める）。

## 書式

スクリプトが読むのは、ヘッダが `| # | 状態 | 種別 | 依存 |` で始まる表だけである。
5 列目以降は自由に足してよい（`内容` を置くことが多い）。
表以外の行（見出し、frontmatter、本文）は読み飛ばす。

```markdown
| # | 状態 | 種別 | 依存 | 内容 |
|---|---|---|---|---|
| C1 | 完了 | 実装 | — | 保存形式を決める |
| C2 | 未着手 | 実装 | C1 | 保存を実装する |
| C3 | 未着手 | 判断 | C1 | 同期の方式を選ぶ |
| C4 | 未着手 | 集約 | C2、C3 | 保存と同期 |
```

- **ID**：`^[A-Za-zα-ω]+[0-9]+[a-z]?$` に合う文字列。接頭辞は計画を作るときに 1 つ決め、同じバックログのほかの計画と重ねない。後から間に挟む項目には `C2a` のように接尾辞を付ける。
- **状態**：未着手、進行中、完了、見送りのいずれか。
- **種別**：自律で着手できるのは実装だけである（`subagent-delegation` skill の役割名の「実装」とは別で、種別が実装でも上位実装の役割に任せることがある）。集約は、依存に挙げた項目（子）の状態から導く項目で、手で状態を決めない。既定の種別はほかに人手（実機での確認や外部サービスの設定など、人が手を動かす作業）と判断（人が決めること）があり、どちらも人を待つ項目として扱う。repo は、自律で着手しない種別を `--kind` で足せる（後回しにした follow-up など。後述）。足した種別に自律で着手するのは、ユーザーか repo の宣言が範囲に含めたときだけである（`parallel-lanes` skill の follow-up の扱い）。
- **依存**：依存がなければ `—`。複数は `、` で区切る。`C2〜C9`（波ダッシュは U+301C）は範囲を表し、範囲内の接尾辞付き ID も含む。

ほかの規則は次のとおり。

- 完了した項目をやり直すときは、行の状態を戻さず、新しい ID を足す。
- 番号は使い回さない。次の番号は、その接頭辞でこれまでに使った最大の番号に 1 を足したものにする。
- 表に収まらない詳細は、表の下に `### <ID>` の節を作って書く（スクリプトは読まない）。
- 行は消さない。
  表が repo で追跡しない場所（追跡しないファイル、メモリ）にあるときと、ユーザーが指示したときに限り、どの行からも依存されていない完了と見送りの行を消してよい（範囲の依存 `C2〜C9` に含まれる行も依存されているとみなす）。
  消すときは、消した中で最大の ID を表の下に `消した最大の ID: C9` のように 1 行残す（番号の使い回しを防ぐため。表の行の形にすると項目として読まれる）。

## 置き場所

| 置き場所 | 向いている場面 | 状態を更新する人 |
|---|---|---|
| GitHub の issue | issue と PR で回す repo | PR のマージで閉じる（`Closes` が効かない取り込みでは、取り込んだ人が閉じる） |
| repo で追跡する文書 | 計画を履歴に残してよい repo | 項目を完了させるコミット |
| repo の追跡しないファイル（gitignore したディレクトリ） | 履歴に残したくないが、repo の近くに置きたい | メインセッションだけ |
| エージェントのメモリ（Claude Code なら自動メモリの `backlog.md`） | 個人 repo | メインセッションだけ |

表は勧める順に並べてあり、向いている場面に当たるもののうち上にあるものを勧める。
どれに当たるか分からなければ、追跡する文書を勧める。
issue を先頭にするのは、PR に紐づけた issue がマージで閉じ（PR の base が既定ブランチの場合）、ほかの置き場所と二重に持たずに済むため。
追跡する文書を追跡しないファイルより先にするのは、別の worktree からも読め、状態の更新が履歴とレビューに残るため。
メモリを追跡しないファイルより後にするのは、ほかのエージェントから読めないため（Claude Code のメモリは Codex や Gemini から読めない）。

追跡しないファイルとメモリは、別の worktree で動く作業者からは見えない（メモリも worktree ごとに別の場所になる）。
そのため状態の更新は、作業者の報告を受けたメインセッションが行う。
GitHub の issue へ書き込む（状態を変える、コメントする）のは外部への書き込みなので、ユーザーの指示か承認を得てから行う。

どこを使うかは、repo の指示ファイル（`AGENTS.md`、`CLAUDE.md` など。どれもなければ `AGENTS.md` を作る）の「バックログ」節で宣言する。
宣言には、置き場所と、計画のファイルかディレクトリ（メモリならその名前）を書く。
repo が種別を足していれば、その `--kind` の値も書く。follow-up に使う種別を `--kind` で足していれば、それも書く（名前は repo が決める。例: `後回し`、`follow-up`）。
GitHub の issue なら、範囲にする issue の条件（ラベル、マイルストーン、Project など）をユーザーに尋ね、種別に写すラベルか issue type とともに書く。

```markdown
## バックログ

repo で追跡する文書 `docs/plans/` に置く（`backlog` skill の書式）。
```

メモリに置く場合は、そのメモリの索引から引ける名前にする。
宣言がなければ、次の順に探す。

1. 表のヘッダを持つファイル：`rg -l --hidden --no-ignore -g '*.md' -g '!.git' -g '!node_modules' -g '!.agents/lanes' '^\| # \| 状態 \| 種別 \| 依存 \|'`（追跡しないファイルも探すため、ignore を外す。`.agents/lanes/` は `parallel-lanes` が実行ごとに置く記録（バックログがないときは表を含む）なので除く。同 skill の宣言で別のディレクトリにしていれば、そちらを除く）
2. 散文のバックログ：`TODO.md`、`ROADMAP.md`、`docs/` や `plans/` の下の計画など
3. エージェントのメモリの索引
4. GitHub の issue：`gh` が使え、repo で issue が使われている場合

repo の中に置いた別の worktree（`git worktree list` に出る、メインの worktree 以外のパス）で見つかったものは同じ計画の写しなので除く。
見つけたものをすべて挙げてユーザーに確かめ、認められたら上の形で宣言する（次のセッションで探し直さないため）。
何もなければ「整える」に進む。

## 引く

```sh
node <この skill のディレクトリ>/scripts/plans.ts <コマンド> [--kind=<種別>]... -- <ファイルかディレクトリ>...
```

| コマンド | 出力 |
|---|---|
| `status` | 計画ごとの状態の集計と、進行中の項目 |
| `ready` | 依存がすべて完了か見送りで、まだ着手していない項目。種別ごとに、その項目が片付くまで着手できない未完了の項目（間接に依存するものを含み、集約は数えない）の多い順に並ぶ |
| `deps [<ID>...]` | 指定した項目が待っている未完了の項目と、指定した項目を待っている項目（間接のものを含む）。ID を省くと全件 |
| `graph [<ID>...]` | Mermaid の依存グラフ（全体を見たいときだけ使う） |
| `check` | 書式と整合性の違反 |

コマンドは省略できない。
違反があると、`check` 以外のコマンドも違反を出して終了コード 1 で止まる。
引数の誤り（未知のコマンドやオプション、存在しない ID）と、読めないファイル（ディレクトリ内の壊れた symlink を含む）は終了コード 2 になる。
項目の表は行頭から書く。インデントやリスト、引用の中に置いた表と、閉じていないコードフェンスは違反になる。

- ディレクトリを渡すと、直下の `*.md` から `README.md` と `_` で始まるファイルを除いて読む。ファイルを直接渡したときは名前によらず読む。
- `--kind=<種別>` で、自律で着手しない種別を足す（例: `--kind='PO 判断'`、`--kind=磨き`）。語彙にない種別は `check` の違反になる。
- `ready` で待っている項目の数が同じ項目は、ファイルの絶対パス（symlink はリンク先）の順、ファイル内では表の順に並ぶ。表の並びを優先順位として扱う。
- Node 22.18 以上で動く（TypeScript の型除去が既定で有効になる版）。repo が古い Node に固定されていても repo の設定は変えず、版を管理するツールの exec などで 22.18 以上の Node を指定して実行する。
- 1 項目だけ見たいときは `rg -n '^\| <ID> \|' <ファイル>` で行を引き、計画を全文読まない。
- CI や pre-commit で `check` を走らせる repo は、`scripts/` を `package.json` ごと repo にコピーし（`plans.ts` だけでは CommonJS の repo で動かない）、コピー元の dotfiles のコミットを冒頭のコメントに書く（dotfiles のない環境でも動かすため）。

### GitHub の issue から引く

issue には表がないので、スクリプトを使わず、gh の出力を同じ語彙に写して判断する。
宣言で範囲にした issue を 1 つの計画として扱い、範囲の条件は `--label`、`--milestone`、`--search`（Project などほかの条件）で渡す。

```sh
gh issue list --state all --limit 200 \
  --json number,title,state,stateReason,assignees,labels,issueType,blockedBy,parent,subIssues,closedByPullRequestsReferences
```

| 表の列 | issue での対応 |
|---|---|
| ID | `#<番号>` |
| 状態 | closed で `stateReason` が completed なら完了、not planned なら見送り。open で担当者か紐づく PR があれば進行中、なければ未着手 |
| 依存 | `blockedBy` |
| 集約 | `subIssues` を持つ issue（状態は子から導く） |
| 種別 | repo が宣言したラベルか issue type との対応。宣言がなければ実装として扱わず、ユーザーに確かめる |

## 整える

置き場所がまだないときは、次の順に進める。

1. 置き場所の表の候補を、向いている場面と勧める 1 つとともに示し、ユーザーに選んでもらう。
2. 最初の項目をアプリの概要や要件から起こすときは、項目の案（ID、種別、依存、内容）を表の形でユーザーに見せ、確認を得る。
   まだ決まっていない前提（データの形式、方式の選択など）は判断の項目にし、それを使う実装の項目の依存に入れる。
3. 選ばれた置き場所を「置き場所」節の宣言の例の形で宣言し、計画を書いて `check` が通ることを確かめる。
   追跡する文書なら、計画は `docs/plans/<主題>.md` を既定にし、冒頭に見出しと概要を置いてよい。

散文で書かれたバックログ（箇条書きの TODO など）を表に移すときは、1 項目を 1 行にし、依存を ID で書き直す。
書き換える前に、移した結果を元の内容と並べてユーザーに見せる。
項目の順序は、散文での優先順位をそのまま表の順に写す。

## 足す、更新する

- **項目を足す**：接頭辞の次の番号を振り、種別と依存を決めて行を足す。足したら `check` を走らせる。
- **状態を変える**：置き場所の表の「状態を更新する人」に従う。集約の行は、`check` が導いた状態に合わせる。
- **follow-up を残す**：レビューの non-blocking な指摘など、後回しにした作業は、新しい項目として足すか、既存の項目の `### <ID>` 節に追記する。
  新しい項目の種別は実装にせず、宣言にある follow-up の種別にし、内容を「〜を直す」の形で書く（実装にすると `ready` の実装の列に並び、ユーザーが選ぶ前に自律の作業へ流れるため）。
  宣言になければ判断にし、内容を「〜を直すか決める」の形で書く。
  あわせて、follow-up の種別を `--kind` で宣言に足すかを、対話中ならその場で、そうでなければ完了報告で尋ねる（判断のままでは、本来の判断の項目と見分けられないため）。
  足さないと決まったら、そのことを宣言に書く（次から尋ねないため）。
  未着手か進行中の実装の項目の節には追記しない（その項目と一緒に、ユーザーが選ぶ前に自律の作業へ入るため）。
  新しい項目の `### <ID>` 節には、場面（誰が、どの環境で、どのくらいの頻度で踏むか）と手間の目安を 1 行ずつ書く（ユーザーが ID ではなく条件でまとめて選ぶ材料にするため）。
  指摘の出どころ（どの項目のレビューか）も節に書く。
  依存には、同じ箇所を触る実装など、直す前に終えておく未完了の項目だけを挙げ、関係があるだけの項目は節に書く（完了した元の項目を依存にしても `ready` は変わらず、関係があるだけの項目を依存にすると `ready` に出なくなるため）。
  ユーザーが着手すると決めたら、種別を実装に変え、「〜を直すか決める」の内容は「〜を直す」に書き直す。
- **重い問題を知らせる**：作業の範囲外で見つけた問題のうち、データの消失や破損、セキュリティ、主要な場面で使えなくなるものは、follow-up の種別にせず判断の項目として足し、完了報告の先頭に書く（follow-up に混ぜると、ほかの細かい項目に埋もれるため）。

## 常に守ること

- `check` の違反を残したまま終えない。
- 計画の中身（設計、判断、項目の範囲）は、ユーザーの確認なしに書き換えない。状態の更新と、決まった作業の追加は確認なしでよい。
