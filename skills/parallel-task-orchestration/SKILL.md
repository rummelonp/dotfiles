# 並列タスク統括

サブエージェント（Task / Agent / Subagent 相当のツール）を持たない環境では本スキルを適用しない。
単一の小規模タスクや、依存関係がなく分割の利点が薄いタスクにも適用しない。

## いつ使うか

以下のいずれかに該当する場合のみ使用する（該当しなければ自力で進める）。

- 並列化できる複数の独立した作業がある
- 読む量や作業量が多く、メインセッションのコンテキスト消費を抑えたい
- 独立した視点での実装が必要
- 事前に読む量が不明な場合は、件数や行数を数える 1 呼び出しを先に行ってから判断する

直列依存のあるタスクを無理に並列化しない。
fan-out（並列展開）はディレクトリや年月など自然な単位で分割し、1 本のサブエージェント / セッションが 1 回で完遂できる粒度にする。全対象を機械的に分割して一斉に投入する無秩序な fan-out は禁止とする。分割の単位は依存関係とファイル所有権（担当範囲）に基づいて決定する。

## プランファイル

統括の状態は 1 つのプランファイル（Markdown）のみで管理する。専用の `state.json` は保持しない。
プランファイルには、少なくとも以下の情報を含むタスク表を配置する。

| 列 | 内容 |
|---|---|
| id | タスク識別子 |
| depends_on | 依存する id（なければ空） |
| owner | 担当セッション / サブエージェント（役割と作業ツリー種別を記録。モデルは `model-routing` の記録規則に従う） |
| files | 担当するファイル / ディレクトリの範囲 |
| status | 未着手 / 進行中 / 完了 / 要修正 |
| log | 進捗や結果の要約（詳細ログや diff 全文は貼らない） |

## Wave 実行

1. `depends_on` に基づいてタスクの依存関係グラフを作成する。
2. 依存がない、または依存先がすべて完了しているタスク群を 1 つの wave とする。
3. **ディスパッチ前のファイル所有権チェック**: 同一 wave 内の複数タスクで `files` 列の対象ファイル / ディレクトリに重複がないか突合する。重複がある場合は wave を分割するか依存関係を追加し、担当範囲の競合や抜け漏れを未然に防ぐ。
4. wave 内のタスクを並列にディスパッチする。ディスパッチ時のブリーフィングには Objective / Owned Files / Requirements / Interface Contract / Acceptance Criteria / Out of Scope を含める。曖昧な点は判断基準を添えて委譲し、都度の確認往復による停滞を防ぐ。
5. wave が完了したらプランファイルの status を更新し、次の wave に進む。
6. 不備が見つかったタスクは元の担当者へ差し戻す（ただしマージやコンフリクト解消などの統合作業自体は差し戻しの対象としない）。

## エージェント別 Dispatch Profile

各コーディングエージェントのツール仕様と並行実行モデルに応じて、タスクを以下のようにディスパッチする。
各タスクの担当の役割は `model-routing` skill で選び、プランファイルの `owner` 列に `model-routing` の記録規則どおりに記録する（検収時に `risk-based-review` のレビュー段を決めるときに必要になる）。

| エージェント | 起動ツール |
|---|---|
| **Claude Code** | `Agent`（`subagent_type` に役割名を指定） |
| **OpenAI Codex** | `spawn_agent` |
| **Antigravity (Gemini)** | `invoke_subagent` |

### エージェント別の並行ディスパッチと作業領域分離

- **Claude Code**:
  - 並行実行: 同一 wave 内の独立タスクを複数の `Agent` ツール呼び出しで並列に起動する。
  - 作業領域分離: 原則としてサブエージェント（同一ツリー内でのファイル所有権分離）で処理する。複数パッケージにまたがる作業、数時間規模に及ぶ作業、開発サーバーや E2E テストの長時間稼働、作業途中にユーザーが介入・確認する可能性がある場合、会話を保存し後から再開・追加依頼したい場合のみ別セッション（worktree + branch）を立てる。
- **OpenAI Codex**:
  - 並行実行: `spawn_agent` により複数のエージェントをディスパッチする。
  - 作業領域分離: 原則としてサブエージェントで処理する。複数パッケージにまたがる作業、数時間規模に及ぶ作業、開発サーバーや E2E テストの長時間稼働、作業途中にユーザーが介入・確認する可能性がある場合、会話を保存し後から再開・追加依頼したい場合のみ worktree で分ける。
- **Antigravity (Gemini)**:
  - 並行実行: `invoke_subagent` の `Subagents` 配列に複数エントリをまとめて指定し、1 回のツール呼び出しで並行起動する（メインのコンテキスト保護と往復オーバーヘッド削減）。
  - 作業領域分離: `Workspace` は既定で親と同じ作業ツリー（`inherit`）を使う。親の作業ツリーを触られたくない並行作業、複数パッケージ、数時間規模、サーバーや E2E の長時間稼働では `share` や `branch` を指定する。

## 外部への書き込み

外部サービスへの変更系操作（GitHub への push / issue 作成 / PR 作成 / コメント投稿、クラウドリソースの変更、外部 API への POST など）は、明示的に指示された場合のみ実行する。指示がない場合は実行前に必ず確認する。
参照系操作（読み取り、`terraform plan` など）や、ローカルでの編集・コミットは自由に実行してよい。

wave を自律的に進行している最中であっても、外部への書き込みを伴うタスクの事前確認は省略しない。ホスト環境が「エスカレーション基準に該当しない作業は自律継続してよい」方針であっても、外部への書き込み確認は例外なく必須とする。
外部書き込みを伴うタスクが発生した場合は、そのタスクのみ実行を一時停止して確認を求め、他の wave やタスクの進行は妨げない。

## 含めないもの

- 常駐チームメイトやペルソナ方式、およびその常駐表示の仕組み（worktree + サブエージェント委譲という実行モデルと異なるため不採用）。
- 5 段階レビューパイプライン（既存のコードレビュー・セキュリティレビュー相当の仕組みと重複するため不採用）。
- 全タスクへの TDD 強制や外部ドキュメント取得の必須化（汎用スキルとして過剰なため不採用）。

## レビューとの関係

wave 完了後の個別タスクの検証やレビューは本スキルの範囲外とする。
完了前の自己チェックには `completion-verification`（完了直前の再検証ゲート）を、独立レビューには `risk-based-review`（リスクに応じた独立レビュアーのディスパッチ手順）を組み合わせて使用する。
