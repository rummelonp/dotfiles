# 並列タスク統括

サブエージェント（Task/Agent 相当のツール）を持たない環境ではこの skill は適用しない。
単一の小さなタスクや、依存関係が無く分割の意味が薄いタスクにも適用しない。

## いつ使うか

以下のいずれかに当たるときだけ使う。当たらなければ自分でやる。

- 並列化できる複数の独立した作業がある
- 読む量や作業量が多く、メインセッションのコンテキストを汚したくない
- 独立した視点での実装が要る
- 読む量が事前に分からない場合は、件数や行数を数える 1 呼び出しを先に置いてから判断する

直列に依存するタスクを無理に並列化しない。fan-out はディレクトリや月などの自然な単位で分け、
1 本のサブエージェント/セッションが 1 回で完遂できる量にする。全対象を機械的に分割して
一斉に投げる盲目的な fan-out は禁止。分割の単位は依存関係とオーナーシップで決める。

## プランファイル

統括の状態は 1 個のプランファイル（Markdown）だけで表現する。専用の state.json は
持たない。プランファイルには少なくとも次の情報を持つタスク表を置く。

| 列 | 内容 |
|---|---|
| id | タスク識別子 |
| depends_on | 依存する id（無ければ空） |
| owner | 担当セッション/サブエージェント |
| files | 担当するファイル/ディレクトリの範囲 |
| status | 未着手 / 進行中 / 完了 / 要修正 |
| log | 進捗や結果の要約（詳細ログや diff そのものは貼らない） |

## Wave 実行

1. `depends_on` からタスクの依存グラフを作る。
2. 依存が無い、または依存先が全て完了しているタスクの集合を 1 wave とする。
3. **ディスパッチ前のファイル所有権チェック**: 同一 wave 内の複数タスクが `files` 列で
   重複するファイル/ディレクトリを持っていないか突合する。重複があれば wave を割り直すか
   依存関係を追加する。委譲ブリーフィングの齟齬（担当範囲の重複や欠落）はここで防ぐ。
4. wave 内のタスクを並列にディスパッチする。ディスパッチ時のブリーフには
   Objective / Owned Files / Requirements / Interface Contract / Acceptance Criteria /
   Out of Scope を含める。曖昧な点は判断基準ごと委譲時に渡し、都度の確認往復で
   停滞させない。
5. wave が完了したらプランファイルの status を更新し、次の wave に進む。
6. 不備が見つかったタスクは元の担当へ差し戻す。ただし統合作業（マージやコンフリクト解消）
   自体は差し戻しの対象にしない。

## サブエージェント/セッションのモデル選定

安価な順に Sonnet、Opus、Fable の 3 段から役割で選ぶ。統括セッションのモデルは選択に
影響させない。

- **調査、探索、fan-out、機械的な修正**: Sonnet。
- **実装、執筆の起草と書き換え**: 既定は Sonnet。Opus へ上げるのは、`risk-based-review` の
  高リスク以上、複数 package にまたがる実装、難度が高いと判断した成果物、Sonnet が複数回
  失敗したものに限る。
- **レビュー、bias-free 評価、指摘を返すだけの推敲**: `risk-based-review` の表の段と、作った
  側の一段上の、高いほうを採る。再レビューの上限も同 skill。
- **設計判断、構成の検討、難しい原因分析**: Fable。大量生成や定型作業には使わない。

wave のタスクを割り当てるときは、どのモデルで作らせたかをプランファイルに記録する。
検収時のレビューの段がこれで決まる。

迷ったら安価な方から試し、品質不足なら一段上げる。一段上のモデルが無いか起動に失敗したら、
元の段のまま続ける。

## 外部への書き込み

外部サービスへの変更系操作（GitHub への push / issue 作成 / PR 作成 / コメント投稿、
クラウドリソースの変更、外部 API への POST など）は明示的に指示されたものだけ実行する。
指示がない場合は実行前に必ず確認する。参照系（読み取り、`terraform plan` 等）と
ローカルの編集やコミットは自由に行ってよい。

wave を自律的に回している最中でも、外部への書き込みを伴うタスクの実行前確認は
省略しない。ホスト環境が「エスカレーション基準に該当しない作業は自律的に継続して
よい」のような方針を採っていても、外部への書き込みに関するこの確認だけは必ず行う。
あるタスクが外部書き込みを伴う場合、そのタスクの実行だけを止めて確認を挟み、他の
wave/タスクの進行は妨げない。

## 含めないもの

- 常駐チームメイトやペルソナ方式とその常駐表示の仕組み。worktree + サブエージェント
  委譲という実行モデルと根本的に異なるため採用しない。
- 5 段階レビューパイプライン（quality/arch → security/perf → testing/docs →
  best-practices → report）。既存の code-review/security-review 相当の仕組みと重複する。
- 全タスクへの TDD 強制、外部ドキュメント取得の必須化。汎用スキルとして過剰。

## レビューとの関係

wave 完了後の個別タスクの検証やレビューはこの skill の範囲外。`completion-verification`
（完了を宣言する直前に検証コマンドを実行し直して確認する自己チェックゲート）と
`risk-based-review`（リスクに応じて独立したレビュアー subagent をディスパッチする
手順）を別途使う。
