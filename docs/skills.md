# skill の書き方

`skills/`、`claude/skills/`、`codex/skills/`、`gemini/skills/` の skill を作る・直すときの方針。

SKILL.md の本文は、起動のたびに全文が読まれる。`references/` のファイルは、本文が「〜のときは読む」と案内したときだけ読まれる。
本文を短く保つと毎回のコンテキストの消費が減るが、分けた分岐をほぼ毎回読むなら、案内の行と読む回数が増えるだけで減らない。

## 区分

skill は次の 3 つに分ける。
区分は、ファイルから読み取れる依存と、本文の外のファイルの有無で決める。

- **単体（本文だけ）**：ほかの skill と規則ファイルを前提にせず、SKILL.md だけで成立する。目的が 1 つなので、本文がよほど長くならない限り分けない。
- **単体（ディレクトリごと）**：ほかの skill と規則ファイルを前提にしない点は単体（本文だけ）と同じだが、本文の外にファイル（`references/`、`scripts/`）を持つ。ディレクトリ全体がコピーされる前提で書く。
- **組で使う**：下の判定の 3 点のどれかに当たる。

単体かどうかは次の 3 点で判定する。どれにも当たらなければ単体とする。
- ほかの skill を、差し込み口（「あれば従い、なければこの既定」）なしに要求している。
- 規則ファイルの定めを前提に、危うい操作（外部への書き込み、push 済みの履歴の書き換え、破壊的な操作）を進めている。
- skill の外にあり、環境ごとに用意して調整するもの（エージェント定義とモデルの割り当て、repo の宣言、自動メモリの分類のような個人の語彙）を前提にしている。

今の区分は次のとおり。
- 単体（本文だけ）：tidy-commits、pr-workflow、completion-verification、grilling、japanese-tech-writing、title
- 単体（ディレクトリごと）：risk-based-review、backlog、empirical-prompt-tuning
- 組で使う：final-pass、parallel-lanes、subagent-delegation、learn

## 分割の判定

上から順に当てはめる。

1. 上流から改変していない skill は分けない（上流との diff が取れなくなる）。
2. 移すのは、その節を読むかどうかが節を読む前に決まる節だけにする（backlog の置き場所が issue である、PR で取り込む repo である、前の実行の記録が残っている、など）。決めるのに節を読む必要があるなら移さない。
3. 起動のうち、その節を読むものが半分を超えるなら移さない（案内の行と節を読む分が、節を読まずに済む分を上回るため）。移した後に半分を超えると分かったら、本文へ戻す。
4. 字数は補助に使い、分ける前の本文の字数で見る。4k 字未満なら分けない。10k 字を超えたら、2・3 に当てはまる節がないかを見直す。

ほかに守ること。
- 判定 2・3 の「節」には、見出しの節のほか、箇条の 1 項目も含める。ただし 300 字未満のものは移さない（移して減る字数より、毎回読む案内の行のほうが多くなりやすい）。
- 判定 3 の割合は、その skill を主に使う repo での起動で見積もる（同じ節でも、repo によってほぼ毎回読むこともまったく読まないこともある）。
  主に使う repo が決まらなければ起動全体で、起動の記録が無ければ、節を読む条件がどれだけの起動で成り立つかで見積もる。
- サブエージェントが毎回全文を読むファイルにも、判定 4 の字数を本文と同じように当てはめる（起動のたびにサブエージェントのコンテキストを消費する点が本文と同じ）。分けるより先に、スクリプトへ出せるものと写しを消せるものを探す。
- 組で使う 2 つの skill が共通で読むように分けたファイルは、判定 3・4 の例外とする（本文へ戻すと、もう一方の skill へ写すことになる）。
- 分ける前に、読むのをサブエージェントに任せて済むかを見る（読む主体がサブエージェントなら、メインセッションのコンテキストを消費しない）。
- ほかの skill が名指しで参照する定義（役割名、観点の定義など）は本文に置き、手順だけを `references/` へ出す。
- `references/` のファイルから、ほかの `references/` のファイルを読ませる案内は増やさない（読む順がたどりにくくなる）。
- 本文の案内は `<この skill のディレクトリ>/references/<名前>.md`（スクリプトは `<この skill のディレクトリ>/scripts/<名前>`）と書き、`references/` のファイルの冒頭には、いつ読むかを 1 行で書く。

## 本文から外すもの

上流から改変していない skill には当てはめない（上流との diff が取れなくなる）。

- まれな分岐は、次の順に当てはめて扱いを決める。まれかどうかは、その skill を読むエージェントごとに見る。
  1. 安全側の既定なら本文に残す。手順と混ざっていたら、既定を 1 文に抜き出して本文に残し、残りの手順だけを 2・3 に当てはめる。
  2. 消しても、エラーで止まるか、エージェントが状況に気付いて止まる（ユーザーに聞くか、報告して終える）なら消す。誤った結果に気付かないまま進むなら消さない。
  3. 消さない分岐は、分割の判定に従う。`references/` へ移す場合でも、分岐に入るかを毎回検出する必要があるなら、検出の 1 文を本文に残す。
- 3 行以上のシェルや jq の断片と、入力だけで機械的に決まる判定の文章は、`scripts/` のスクリプトに出す。ただし、permission ルールを用意できず、呼び出しのたびに承認が要る skill では出さない（承認で止まる箇所が増える）。
  本文には呼び出し方と、出力ごとの扱いを残す。スクリプトの挙動を本文に写した説明は消す（スクリプトを直したときに本文がずれる）。
- 本文には今の手順と書式だけを残す。過去の例や履歴の表は、手順の意図を伝えるのに要る 1 例を除いて外す。
- skill を直す人だけが読む節（規範の更新の手順、経緯）は、本文とは別の保守用ファイル（`MAINTAINING.md` など）へ移す。実行時には読まないので、`references/` には置かない。
  同じ内容がほかのファイルに既にあれば、移さずに消す。
  保守用ファイルは、区分を決める本文の外のファイルに数えない（持っていても単体（ディレクトリごと）にはしない）。
- 上流から入れた skill の出所と改変は `skills/README.md` に書く。

## 安全側の既定

- 危うい操作の既定と、ユーザーに確かめるかの既定は、区分によらず本文に無条件の 1 文で置く。`references/` には手順だけを置く。
- 既定が本文にあれば、`references/` を読めない環境でも安全側に倒れるので、「読めなければ〜」という補足は書かない。
- ユーザー向けに既定を緩める許可は規則ファイルに置き、skill は「規則ファイルが許している場合か、ユーザーが承認した場合」という差し込み口で受ける。

## 区分ごとの書き方

単体の skill は既定を書く。
- ほかの skill を前提にしない。使う skill を見つける入口としての 1 行の案内（「並列なら `parallel-lanes`」など）はよい。数行の重複は許す。
- 呼び出し元ごとの条件分岐（「`final-pass` から使うときは〜」など）は書かず、呼ぶ側に置く。単体の skill は差し込み口だけを持つ。
- ユーザーが直接呼んだときにも要る規則は、単体の skill に残す。

組で使う skill は次のように書く。
- 判定の 3 点に当たるもの（ほかの skill、規則ファイル、環境ごとに用意するもの）を前提にしてよい。
- 規則ファイルに定めがあっても、危うい操作の既定を本文から外したり緩めたりしない。規則ファイルはエージェントごとに別なので、既定を規則ファイルに任せると、規則ファイルどうしの記述のずれがエージェントごとの skill の挙動の差になる。
- 既定や手順には理由を添える。後で直すときに理由が残っていれば、既定の意図が引き継がれる。本文には理由を 1 句で残し、経緯や過去の事例は保守用ファイルへ移してよい。
- ほかの skill の定義を写さない（2 か所に写すと一方だけ直されてずれ、どちらを正とするかが決まらなくなる）。2 つの skill が同じ定義を使うなら、定義を置く skill を 1 つに決め、もう一方からはパスで参照する。

## モデルが変わったとき

古いモデル向けに足した指示が、新しいモデルでは要らない制約として残ることがある（防いでいた失敗が起きなくなっても、指示は守られ続ける）。
Claude のモデルが新しく出たら、そのモデルのセッションを dotfiles で開いて `/doctor prompt-audit` を実行し、削除案を出させる（監査はセッションのモデルを基準にするため。Claude Code 2.1.308 で確認）。
- 監査の範囲は skill より広く、プロジェクトの CLAUDE.md・AGENTS.md と `~/.claude/CLAUDE.md`、`.claude/` と `~/.claude/` の下の skills・agents などに及ぶ。dotfiles の外で `~/.claude/skills/` に置いた skill も含む。settings.json などの設定ファイルは読まない。
- 削除案を採るかは 1 件ずつ、その指示が防いでいた失敗が新しいモデルでも起きるかで決める。
- `skills/` の skill は Codex と Gemini も読むので、そちらでも要らないかを併せて見る。`claude/CLAUDE.md` の削除案は、`AGENTS.md` の規則に従って `codex/AGENTS.md` と `gemini/GEMINI.md` の対応箇所も見る。
- 上流から入れた skill への案は採らない（上流との diff が取れなくなる）。
